VNC File Transfer via the Connection's Side Channel

Backlog · not implemented GitHub Issue: #3770 (follow-up to #3472) docs/concepts/backlog/vnc-clipboard-file-transfer.html

Recommendation — option (b): no RFB file-transfer extension. Move files over the side channel the VNC connection already has: the SSH tunnel (open an SFTP subsystem on the same authenticated SSH session) or the agent (its connection.files.* service on the agent host). Drag files onto the VNC canvas to upload; a toolbar Files button uploads or opens the existing file browser on that host for downloads. Off by default, per-connection opt-in, never in view-only sessions. Direct VNC connections with neither an SSH tunnel nor an agent get no file transfer (a later phase may let them link a saved SSH connection).

Overview #

RDP sessions can move files through the clipboard (CLIPRDR FileGroupDescriptorW, #1765 / #1778 / #1779 / #1793). VNC cannot: #3472 implemented the RFB Extended Clipboard for UTF-8 text and dib images, but its files format bit is, in the community specification's own words, "Currently reserved but not defined" — no file list, no names, no sizes, no chunking. No server sends or accepts it. #3770 asks which mechanism VNC should use instead, or whether to support none.

The survey below shows that every RFB-level file-transfer mechanism is either vendor proprietary and closed (RealVNC, Apple), or limited to one Windows server family with an undocumented, CVE-laden message set (UltraVNC, TightVNC — and their two TightVNC generations are mutually incompatible). The servers termiHub users most often reach — TigerVNC, x11vnc as shipped, wayvnc, GNOME/KDE, macOS Screen Sharing — expose none of them to a third-party viewer. What those hosts almost always do have is SSH, and termiHub's VNC connections already ride SSH (the editor's SSH Tunnel group) or an agent (#3241, port-forward tunnel). So the file path should be that side channel, not RFB.

Goals

  • Drag-and-drop a local file onto a VNC session and have it land on the remote desktop host, with progress, when the connection has an SSH tunnel or an agent.
  • Fetch files from that host back to the local machine using the existing file browser and transfer queue — no second implementation of browsing, progress or cancel.
  • Keep the RDP bounds philosophy: opt-in and off by default, never in view-only sessions, remote-chosen names never trusted, bytes move only on an explicit user gesture, streaming (no whole-file buffering).
  • Zero new untrusted parser surface in the RFB client (vendor/vnc-rs).

Non-Goals

  • Implementing UltraVNC rfbFileTransfer, either TightVNC file-transfer protocol, RealVNC or Apple extensions, or inventing a files layout for the Extended Clipboard.
  • True clipboard semantics for files (copy in the remote file manager, paste locally). RFB gives no signal that the remote copied files; the remote-side gesture is "pick in the browser" instead.
  • File transfer for direct VNC connections without SSH tunnel or agent in the first phases (see Phase 4 for an optional linked-SSH-connection route).
  • Changing the RDP clipboard file transfer.

UI Interface #

File transfer adds three surfaces to the shared remote-desktop view (RemoteDesktopTab / RemoteDesktopToolbar) and one setting to the VNC connection editor. Nothing changes in the Clipboard panel: its text/image behaviour (#3472) stays as is, and its "Remote files" block remains RDP-only because it is driven by a real remote clipboard copy, which VNC cannot observe.

  1. Drop target on the canvas. Dragging files from the OS over a VNC tab shows a dashed overlay naming the exact destination (folder, host, route). Dropping uploads; the overlay never appears for in-app drags (tabs, panels).
  2. Files button in the floating toolbar (lucide folder-open, after Clipboard). Opens a small popover: route line, Upload files…, Upload to folder…, Browse remote files, and the session's in-flight transfers.
  3. Browse remote files opens the existing File Browser sidebar rooted at the destination folder on the side-channel host — downloads, uploads, cancel and progress all reuse the file browser and the Transfers queue.

General Handling #

Route resolution (once per session start / reconnect)

  • SSH tunnel route — the VNC config has use_ssh_tunnel. Files travel on an SFTP subsystem channel opened on the same authenticated SSH session the tunnel already holds: no second login, no new credential, and the host key was already verified by the tunnel's trust flow. The file host is the SSH host.
  • Agent route — the connection carries agentId (#3241 port-forward). Files travel through the agent's host-level connection.files.* RPCs (list/stat/read_range/write_range/mkdir, no connection_id), the same service the file browser uses for agent hosts. The file host is the agent host.
  • Same-host check — the route's file host is "the desktop host" when the VNC target as seen from it is loopback (localhost, 127.0.0.0/8, ::1) or equal to the SSH/agent host name. If not, the feature still works when enabled, but every label names the real file host, and the editor warns when the box is ticked.
  • No route — direct VNC: the Files button is disabled with a tooltip and drops show the "unavailable" overlay. (Phase 4: optional linked SSH connection.)
  • Precedence if both exist (agent-hosted and SSH tunnel): agent, because the tunnel then runs from the agent host and the agent already owns the file service.

Upload (drop or "Upload files…")

  1. Resolve the destination folder: per-session choice → connection's Default folder (if set) → ~/Desktop if it exists → ~. Resolved with SFTP realpath / agent stat.
  2. For each dropped item (files and folders, recursive; symlinks are not followed — matching #1779), enqueue an upload in the existing Transfers queue keyed by this session id. Bytes stream in the queue's existing chunk size; nothing is buffered whole.
  3. Name collisions at the destination: keep both — name (1).ext, mirroring RDP's dedupe; never overwrite silently.
  4. Completion toast: "Uploaded 2 files to ~/Desktop on tiger-box" with Reveal (opens Browse remote files there).

Download ("Browse remote files")

  1. Open the File Browser sidebar on the side-channel host, rooted at the destination folder. The user picks files and uses the browser's existing Download action.
  2. The local destination is chosen by the user (save dialog / Downloads); the remote supplies only names inside a listing the user browsed, and the existing local-path sanitiser applies (no .., absolute paths, drive letters, reserved device names).

Bounds — RDP clipboard-file philosophy mapped to the side channel

RDP rule (#1765/#1778/#1793) VNC side-channel equivalent
Off by default, per-connection opt-in "Allow file transfer" in the VNC editor, default off; no global switch.
View-only never pushes local data View-only hides the Files button and refuses drops — both directions, because the remote file browser can also mutate the host (rename/delete).
Server-chosen names sanitised Remote names only reach local paths through the existing download sanitiser; the remote never pushes files unsolicited (there is no remote-initiated direction at all).
Sizes capped / streamed in bounded chunks Transfers stream through the queue's chunked, cancellable path; the size is shown before and during transfer. No in-memory payload exists to cap.
Delayed fetch — bytes move only on a paste gesture Bytes move only on drop, Upload, or Download — an explicit gesture each time.
Remote selects an index, never a path Moot: paths are chosen by the local user in a picker; the remote is never asked which file to serve.
Received files confined to one shared folder Uploads go only where the user points (default folder shown on the overlay before drop). Downloads go only to a user-chosen local folder.

Edge cases

  • SFTP subsystem disabled on the SSH server → first use fails with "SFTP is not enabled on tiger-box"; the Files button shows a warning dot, VNC keeps running.
  • Permission denied / disk full on the destination → the transfer row fails with the server's message; other queued items continue.
  • Tunnel or agent drops mid-transfer → in-flight transfers fail (resumable only if the queue's relaunch logic already supports the route); VNC reconnect re-resolves the route; nothing auto-retries uploads.
  • App quit mid-transfer (#4205) → the row is kept in the persisted queue with the saved VNC connection and the route (host, account, agent — never a secret). After a restart it shows paused, "VNC session unavailable — reconnect to resume", and continues from its byte-verified offset once a session of that connection is active and its side channel is ready. A route that now leads to a different host fails the row instead of continuing the partial file there.
  • Desktop user ≠ SSH user (VNC session owned by another account) → files land in the SSH user's home; the route line shows user@host so this is visible.
  • Windows host via OpenSSH → ~/Desktop resolves to the user profile's Desktop; paths are shown as the SFTP server reports them.
  • Session closed → its queued transfers are cancelled with the session (same rule as SFTP sessions keyed by session id).
  • Drag of an in-app object (tab, file-browser row) over the canvas → no overlay; only OS file drags qualify. A file-browser row dragged onto the canvas is a later nicety, not in scope.

Preliminary Implementation Details #

Based on develop at concept creation (2026-10). The RFB client (vendor/vnc-rs) is not touched; the Extended Clipboard keeps skipping a files provide within its decompression budget (#3472).

core/src/backends/vnc/config.rs New fields file_transfer: bool (default false), file_transfer_dir: Option<String>; schema group "File Transfer" after SSH Tunnel.
core/src/backends/vnc/tunnel.rs Keep the authenticated SSH session handle reachable from the backend (today it lives only inside the forwarder task) so an SFTP channel can be opened on it via ssh::sftp::open_sftp_subsystem.

src-tauri/src/files/transfer/, transfers_projection/ Accept a graphical session's side channel as a transfer endpoint (SFTP channel or agent files), keyed by the graphical session id; collision "keep both" naming.

docs/ user guide (remote desktop) Document routes, the setting, and why direct VNC has no file transfer.

Risks #

  • Expectation gap: users coming from UltraVNC/TightVNC viewers expect file transfer on direct connections to Windows hosts. Mitigation: the unavailable overlay explains how to get it (SSH tunnel / agent); revisit trigger for (a1).
  • Wrong-host confusion with gateway tunnels. Mitigation: route line and overlay always name the real file host; editor warning; same-host detection.
  • Different account: files land in the SSH user's home, which may not be the VNC desktop owner's. Mitigation: user@host in the route line; configurable default folder.
  • Tunnel refactor: keeping the SSH session reachable from tunnel.rs touches reconnect/teardown. Mitigation: SFTP channel lifetime bound to the tunnel's cancellation token; covered by Phase 1 tests.
  • Scope creep into clipboard semantics for files. Mitigation: explicitly a non-goal; RFB cannot signal a remote file copy.
