Overview & Goals #

termiHub today runs as a single application window that hosts every session tab, split, and tab group. Users on multi-monitor setups repeatedly ask to spread work across screens — a build tailing on one monitor, an SSH session on another. This concept assesses whether termiHub can host multiple native windows and move live session tabs between them without tearing down the underlying backend session.

The verdict is: feasible, with real caveats. The architecture is unusually well-suited to it in one dimension and awkward in another. Session state already lives in the Rust backend, keyed by session id and completely independent of any window, and the backend already supports the exact primitive multi-window needs — detach a view and re-attach it later with scrollback replay (built for persistent/agent sessions and tab groups). That makes re-parenting a session tab a view operation, not a teardown. The awkward dimension is the front end: separate native windows are separate JavaScript contexts with no shared memory, and the current tab drag-and-drop stack (@dnd-kit) cannot cross a native window boundary. So the hard limits cluster on gesture and coordination, not on session survival.

Goals

  • Tear out a session tab into a brand-new window (drag-out or a "Move to New Window" command).
  • Create additional windows (empty, or seeded from a tab group).
  • Move tabs between existing windows without restarting the backend session (its PTY / SSH channel / serial port / RDP connection keeps running).
  • Preserve scrollback on move to the extent the backend replay buffer allows.

Non-Goals

  • Sharing one live session's terminal view across two windows simultaneously (mirrored view). Out of scope — a tab lives in exactly one window at a time.
  • Multi-window support for non-session tabs (Settings, Log Viewer) — see the matrix.
  • Detachable sidebar panels (connection tree, network tools) into their own windows.
  • Multi-process windows. Windows are additional webviews in the one Tauri process.

Current Architecture (as-is) #

Every claim below is grounded in the current tree. The picture that matters: the backend is the authoritative, window-independent owner of session state; the frontend holds only view state; and events are already delivered app-wide by broadcast.

One window today

  • Tauri v2 (src-tauri/Cargo.toml: tauri = { version = "2", … }; config schema config/2).
  • Exactly one window is declared — tauri.conf.json → app.windows[] has a single entry titled termiHub. Its runtime label is "main".
  • Nothing creates a second window. The only window lookups are app.get_webview_window("main") (src-tauri/src/lib.rs:262, src-tauri/src/spawn/handler.rs:275). No WebviewWindowBuilder / WindowBuilder exists in production code. The frontend only ever calls getCurrentWindow() (src/App.tsx:39,209) — never new WebviewWindow(...).

Session state lives in the Rust backend, keyed by id

  • SessionManager (src-tauri/src/session/manager.rs) holds a sessions map keyed by session_id. A session is a backend process (PTY, SSH channel, serial port, agent proxy) — it has no notion of which window, tab, or even tab group is displaying it. This is the single most important fact for this feature: a session already survives independently of any view.
  • Graphical (RDP/VNC) sessions are owned by a separate GraphicalSessionManager (built at src-tauri/src/lib.rs:429), keyed by connection type id, also window-independent.
  • The backend keeps a replayable scrollback buffer: a 1 MiB RingBuffer (core/src/buffer/mod.rs, doc'd for "serial 24/7 capture, daemon PTY output replay, and reconnect replay"), plus persistent/agent session scrollback replay and RemoteProxy::reconnect_existing (manager.rs ~L920, ~L1195, ~L2854). This is the re-parenting enabler.

Events are a global broadcast; input is an id-keyed IPC call

  • Output is emitted with AppHandle::emit("terminal-output", event) — a global broadcast to every webview (manager.rs:114–125). Same for terminal-exit, persistent-session-state-changed, and every graphical stream: remote-desktop-frame / -cursor / -clipboard / -state / -cert-prompt (graphical_manager.rs:115–127).
  • The frontend registers one global listener per stream and fans out by session_id — SessionEventDispatcher in src/services/events.ts. Consequence for multi-window: because output is already broadcast to all windows, a second window that subscribes and filters by the same session_id automatically receives that session's output. No emit_to retargeting is required for correctness — only as an efficiency improvement (see State & Retargeting).
  • Input / control (write, resize, close) are Tauri command calls keyed by session_id, so they work identically from whichever window currently owns the tab.

Frontend view state — the Zustand store

  • src/store/appStore.ts (~6.4k lines) holds tabGroups: TabGroup[], activeTabGroupId, and the live rootPanel: PanelNode (a recursive split/leaf tree — src/types/terminal.ts). A tab (TerminalTab) carries a sessionId, a contentType, and its config — the view of a backend session, not the session itself.
  • Tab groups are the closest existing analog to windows. Each group is an "independent panel tree that stays alive when hidden" (implemented concept tab-groups.html): the active group uses the live rootPanel, every other group keeps its own rootPanel in tabGroups[]. Multi-window is essentially "let a tab group (or a subset of tabs) live in its own OS window" — except groups today all share one JS context and one store; windows do not.
  • Cross-panel and cross-group tab movement already exists — moveTab, moveTabToGroup, addTabGroupWithTab, splitPanelWithTab in the store. These are the natural seams to extend to cross-window movement.

Tab drag-and-drop uses @dnd-kit (single-document)

  • Tab drag/reorder/tear-to-split is built on @dnd-kit (src/components/SplitView/SplitView.tsx, PanelDropZone.tsx): pointer sensors, DndContext, DragOverlay. It uses no native HTML5 dataTransfer. @dnd-kit is fundamentally single-document — its pointer tracking and drag overlay live entirely inside one webview's DOM and cannot follow the cursor across a native window boundary. This is the crux of the drag limitation below.
  • The one place termiHub does use OS-level drag is Tauri's onDragDropEvent for external file drops into the file browser — a different, OS→webview channel, not webview→webview tab drag.

Persistence & lifecycle have no window dimension

  • Workspaces (src/types/workspace.ts, WorkspaceDefinition) capture tabGroups[] with a layout tree — but there is no window field anywhere. A restored workspace has nowhere to record "this group is in window 2." Same for last-session restore.
  • Lifecycle is handled in src-tauri/src/lib.rs via RunEvent::WindowEvent { CloseRequested / Destroyed } and RunEvent::ExitRequested (~L918–930). With one window, "window closed" ≈ "app quit." Multi-window breaks that identity and needs an explicit policy.
  • No single-instance plugin is used. Portable mode and the CLI workspace launch (tauri.conf.json → plugins.cli) are orthogonal — multi-window is multi-webview-in-one-process, not multi-process.

UI Interface #

The interaction design — the drag-to-tear gesture and its command fallback, the drag-between-windows affordance, the "New Window" entry points, the empty-window state, and every edge-case surface — is step 2. The technical constraints those mockups must respect are: (a) native drag cannot cross windows with today's stack, so a command/menu path is mandatory and a drag gesture is at best an enhancement; (b) graphical tabs may need a "moving…" placeholder while the framebuffer repaints; (c) an empty window is a real state (a window can exist with zero tabs). See Limitations for the full list the UX must design around.

Proposed Approach — the three capabilities #

All three capabilities reduce to the same core move: detach a tab's view from window A and re-attach it in window B, while the backend session keeps running untouched. They differ only in whether window B already exists.

(a) Tear a tab out into a new window

  1. User invokes "Move to New Window" (command / tab context menu; a drag-out gesture is a later enhancement — see limits).
  2. Backend creates a new WebviewWindow (label e.g. win-2) loading the same frontend bundle. It boots a fresh, empty store.
  3. A hand-off record for the moved tab (its TerminalTab view-model + desired placement) is passed to the new window (via an init argument or a backend-brokered claim — see State & Retargeting).
  4. Window B builds a leaf panel, creates a fresh xterm.js instance, subscribes to the global output stream filtered by session_id, and requests a scrollback replay to repaint history.
  5. Window A removes the tab from its store and disposes its xterm instance. The backend session never restarted.

(b) Create additional windows

A "New Window" command opens an empty window (empty store, no tabs) — or seeds it from a chosen tab group. Mechanically identical to (a) minus the hand-off; the empty-window state is a first-class UI state the UX must design.

(c) Move a tab between two existing windows

Same hand-off as (a) but window B already exists, so the flow is just: window B claims the tab, attaches + replays; window A releases it. The only genuinely new problem is the gesture — dragging a tab from A's tab bar onto B's tab bar is not expressible with @dnd-kit across native windows, so the shipping mechanism is a command ("Move to Window ▸ <name>"), with drag as a research item (open question).

Session Re-parenting Mechanism #

Re-parenting a tab is a pure view operation. The backend session is keyed by session_id and knows nothing about windows, so "moving" a tab never touches it. In one paragraph: window B instantiates a new xterm.js (or canvas) surface, begins listening to the already-broadcast output stream for that session_id, and asks the backend to replay the ring-buffered scrollback so the fresh surface repaints history; window A then drops its view and disposes its surface. Input keeps flowing because write/resize are id-keyed IPC calls issued from whichever window holds the tab. termiHub already does exactly this when a persistent/agent tab is closed and later re-attached — multi-window reuses that machinery across a window boundary instead of across time.

State Ownership & Event Retargeting #

This boundary is the whole feature. Separate webviews are separate JavaScript contexts — no shared DOM, no shared module memory, no shared Zustand store. What is authoritative in the backend moves cleanly; what is in-memory per-window must be rebuilt on the far side.

State Where it lives today On move
Backend session (PTY/SSH/serial/RDP, process, channel) Rust SessionManager/GraphicalSessionManager, keyed by id Authoritative — untouched. Survives the move entirely.
Scrollback (replayable) Backend RingBuffer (1 MiB) + agent/persistent replay Replayed into window B's fresh xterm — bounded by buffer size.
xterm.js instance, rendered scrollback, viewport, selection In window A's JS memory / DOM Discarded. Rebuilt in B from replay; anything beyond the buffer is lost.
Tab view-model (TerminalTab: title, config, badges, placement) Window A's Zustand store Serialized into the hand-off record; re-hydrated in B; removed from A.
Graphical framebuffer (RDP/VNC canvas pixels) Window A's <canvas> memory Discarded; repaint on next full frame. Possible blank flash — see matrix.
Tab ↔ window ownership (who shows which session) Implicit — one window, so unambiguous today New: needs an explicit coordinator so a tab is shown in exactly one window.

Event retargeting — needed for hygiene, not correctness

Because output is a global broadcast (AppHandle::emit), the moment window B subscribes to terminal-output and filters for the session's id, output "follows" the tab with zero backend change — this is a genuine gift of the current design. Two non-blocking concerns remain:

  • Efficiency. Every window deserializes every session's bytes even for tabs it does not own. At a handful of windows this is fine; at scale it argues for switching hot streams to emit_to(window_label, …) and having the backend track a session_id → owning_window map, updated on each move. That map is also the natural ownership coordinator above.
  • Ownership coordination. Two windows must never simultaneously render the same live tab (double input, fighting resizes). The cleanest home for the authoritative session → window assignment is the backend (it already holds the session); windows claim/release through it. A pure-frontend broadcast-channel scheme is possible but more fragile across crashes.

Resize is a real subtlety: a PTY has one size. When a tab moves to a differently sized window, exactly one window must own the resize for that session — the one currently displaying it — and the backend must apply the new dimensions once, not race two windows.

Per-Session-Type Feasibility Matrix #

"Moves cleanly" = backend session survives and only the view re-attaches. The contentType values are from src/types/terminal.ts.

Session / tab type Move difficulty Why
Local shell / PTY (+ xterm.js) Easy Backend PTY survives; fresh xterm + RingBuffer replay. Scrollback beyond 1 MiB is lost.
SSH (local or agent-mediated) Easy Same stream model. Agent/persistent sessions already support detach + re-attach with replay — the exact primitive.
Serial Easy 24/7 RingBuffer capture already exists; re-attach replays. Port stays open in backend.
Telnet / Docker / WSL Easy Identical PTY/stream + id-keyed IPC model.
Agent sessions (remote daemon) Easy Detach/adopt/attach is already built (adopt_persistent_session, scrollback fetch). Best-supported case.
File browser / SFTP / FTP (file-browser, terminal-less) Medium Backend SFTP session (keyed in SftpManager) survives, but current dir / selection are frontend-only and must serialize. In-flight transfers use a shared Transfer Queue (src/components/TransferQueue) — a move must not abort them; the queue is app-scoped, so its ownership across windows is an open question.
RDP / VNC graphical (remote-desktop, <canvas>) Hard (command-only) Backend graphical session survives (frames broadcast on remote-desktop-frame), but the framebuffer is canvas memory in window A. Window B repaints only on the next full frame — there is no on-demand keyframe today — so expect a blank/stale flash. Cursor/clipboard/cert-prompt state is per-webview. Recommend command-based move with a "reconnecting view…" placeholder; a backend "request full frame on attach" hook would materially improve this.
Editor (editor, Monaco) Medium Unsaved buffer + cursor live in window A's Monaco. Moving means re-opening the file in B and transferring dirty state — non-trivial; may restrict to saved files in v1.
Non-session tabs: Settings, Log Viewer, Connection/Tunnel/Workspace editors, Network Diagnostic N/A / restrict No backend session; some are effectively singletons (Settings, Log Viewer). Moving is pure view transfer but often meaningless. Likely non-goal — restrict to session-bearing tabs, or allow but forbid duplicates.

Per-Platform Constraints #

PlatformConstraint
macOS (WKWebView) Closing the last window conventionally does not quit the app (stays in Dock) — needs an explicit policy vs. Windows/Linux. Also: tauri-driver has no macOS WKWebView driver (ADR-5), so multi-window E2E cannot be automated on macOS — verification is manual there.
Windows (WebView2) / Linux (WebKitGTK) Last-window-close typically quits. Each new window is a full webview → real RAM cost (another React app + xterm instances). No cross-window native tab drag on any platform with the current stack.
All platforms Cross-window webview→webview drag is not provided by Tauri; @dnd-kit is single-document. Tab-tear/inter-window drag must fall back to commands. Each window re-runs the full frontend bundle (memory + startup cost per window).

Limitations · Non-Goals · Open Questions #

Hard limitations (these shape the UX)

  1. No cross-window native drag. The tab DnD stack (@dnd-kit, SplitView.tsx) is single-document and cannot follow the cursor across a native window boundary; Tauri exposes no webview→webview drag. Tear-out and drag-between-windows must ship as commands / context-menu items ("Move to New Window", "Move to Window ▸ N"); a drag gesture is at best a future enhancement, not the v1 mechanism.
  2. Graphical (RDP/VNC) tabs move via command only, with a repaint flash. The framebuffer is canvas memory in the source window; the destination repaints only on the next full frame (no on-demand keyframe today), so the canvas may be blank/stale briefly. Live drag is especially unsuitable here.
  3. Scrollback fidelity is bounded by the backend replay buffer (1 MiB RingBuffer). The source window's fully-rendered xterm scrollback is discarded (separate JS context — DOM/memory cannot transfer); the destination shows only what the backend can replay. Very long histories are truncated on move.
  4. Separate JS contexts — no shared store. Each window is its own React/Zustand instance. Cross-window features (tab counts, "move to" menus listing other windows, ownership) require a coordination channel (backend-brokered is recommended over a frontend broadcast channel).
  5. No window dimension in persistence. WorkspaceDefinition and last-session restore have no field for window assignment. Saving/restoring a multi-window layout needs a schema addition (a window id per tab group / per tab) and new multi-window restore lifecycle.
  6. Window-close policy is new. Closing a window with live tabs must choose detach-vs-terminate (persistent/agent sessions should detach, not die); "last window closed → quit" differs by OS (macOS keeps the app alive).
  7. Resize ownership. A PTY has one size; exactly one window may own a session's resize at a time, and the backend must apply it without racing two windows.
  8. Per-window memory cost. Each window re-runs the full frontend bundle and its own xterm/canvas instances — a real RAM multiplier, relevant to the app's resource footprint.
  9. Automated-test gap on macOS. tauri-driver has no macOS driver (ADR-5), and the Python bridge harness would need multi-window awareness. Multi-window behavior on macOS is manual-test-only.

Non-goals

  • Mirroring one live session into two windows at once.
  • Detaching sidebar panels (connection tree, network tools) into windows.
  • Moving non-session/singleton tabs (Settings, Log Viewer) — likely restricted.
  • Multi-process windows — these are additional webviews in one Tauri process.

Open questions (need the human or the UX step)

  • Do windows map onto tab groups? Tab groups are already independent panel trees. The cleanest model may be "a window owns one or more tab groups," reusing that substrate — but that couples the two features. Product decision.
  • Is a drag-out gesture worth prototyping given @dnd-kit can't cross windows? (An OS-drag-image + drop-detection hack is conceivable but unproven in Tauri — research item.)
  • Detach-vs-terminate default when closing a window with non-persistent live tabs.
  • Are graphical tabs allowed to move at all in v1, or deferred until a "request full frame on attach" backend hook exists?
  • Transfer-queue ownership when an SFTP/FTP tab with in-flight transfers moves windows.
  • Should the Open Connections panel and workspace save/restore become window-aware, or stay window-agnostic in v1?

Preliminary Implementation Details #

Based on the architecture at concept-creation time. Directional, not a build plan.

AreaChange
src-tauri/src/lib.rs / new window module New — WebviewWindowBuilder to create labelled windows (win-N); a backend session→window ownership map + claim/release commands; window-aware close/quit policy in the RunEvent handler.
src-tauri/src/session/manager.rs Add an on-demand scrollback replay for a specific window path (reuse the existing persistent/agent replay) and, later, optional emit_to(window_label, …) targeting instead of global broadcast for hot streams.

Tab context menu / command palette (SplitView, TabBar) New — "Move to New Window" / "Move to Window ▸ N" commands (the primary mechanism; drag is a later enhancement).
