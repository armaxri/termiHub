Overview #

When a user opens an SSH connection with X11 forwarding enabled, a remote GUI program (xclock, wireshark, a vendor tool) is an X client — it needs a running X server on the local machine to draw into. Today termiHub forwards the X protocol correctly but assumes the user has already installed and configured a local X server. On Windows that is almost never true, and on macOS it requires a manual XQuartz install. The result: X11 forwarding "silently does nothing" for most users.

This concept adds a subsystem that ensures a usable local X server exists before an X11-forwarding session starts, so remote GUI apps open as independent native windows with zero manual setup — the model popularized by MobaXterm ("the app provides the X server; the user never installs one").

The transport half exists: enable_x11_forwarding sets up reverse port-forwarding, injects DISPLAY + an xauth cookie on the remote shell, and proxies X channels to a local display (connector.rs, tested via tests/docker/ssh-x11/). This concept specifies the provisioning half: detect-or-provide the local X server the transport half proxies into.

Goals

  • Make remote GUI apps "just work" as native windows when X11 forwarding is enabled — no manual X-server install on the common path.
  • On Windows, install (via winget) and manage a real X server (VcXsrv) transparently.
  • On macOS, detect XQuartz and offer a guided, consent-based install when it is missing.
  • On Linux, detect the already-present Xorg/XWayland and give a targeted hint only in the rare gap cases.
  • Reuse an already-running user X server instead of spawning a duplicate.
  • Surface the managed server in the Open Connections panel so it can be inspected and killed like any other connection.

Non-Goals

  • Rendering remote GUIs inside termiHub's own window (they stay independent OS windows).
  • Native x11-req SSH channel support (the existing reverse-port-forward transport is sufficient).
  • Implementing an X server ourselves — no embeddable X-server library exists; we ship/spawn an external binary (as MobaXterm does with its "MobaX" X.Org fork).
  • Bundling an X server on macOS or Linux (not possible / not advisable respectively).
  • Wayland-native remote display (XWayland covers forwarded X11 clients).

UI Interface #

A schema-driven setting provideXServerAutomatically (rendered by DynamicForm, default on for Windows) controls whether termiHub may provision a local X server; a companion stopXServerWhenIdle (default on) stops the managed server once the last X11 session closes. The existing per-connection X11 Forwarding toggle (enableX11Forwarding) is unchanged. Nothing is downloaded or installed without explicit consent.

General Handling #

  • Provision is lazy & consent-gated. Nothing is downloaded/installed until a user opens an X11-forwarding connection and confirms the prompt. A user who never uses X11 forwarding never downloads an X server.
  • Reuse before spawn. If a reachable X server already exists (DISPLAY set, /tmp/.X11-unix socket on Unix, or TCP 127.0.0.1:6000 open on Windows), termiHub adopts it instead of starting its own.
  • One shared managed server per termiHub instance, reused by all X11 sessions (display :0, port 6000). Not one server per connection.
  • Idle shutdown (Windows managed server). When the last X11-forwarding session closes and stopXServerWhenIdle is on, the managed server is stopped; it is always stopped on app exit (no orphan vcxsrv.exe).
  • Per-platform strategy: Windows → guided install of VcXsrv via winget; macOS → guided install of XQuartz via Homebrew; Linux → detect + guide (never bundle).
  • Failure is actionable, never silent. If provisioning fails at any stage, the session surfaces a clear error with a retry/skip path rather than forwarding into a void.
  • Security: the managed server uses MIT-MAGIC-COOKIE-1 auth by default (not -ac), matching the cookie the transport half installs on the remote side.

Edge cases

Scenario Behavior
User already runs VcXsrv / X410 / Xming on :0 Adopt it (TCP 6000 probe); do not spawn a duplicate
Port 6000 taken by a non-X process Pick the next free display number; register that display
winget install fails Surface winget's error verbatim (never run a partial install)
winget (App Installer) absent Guide the user to install App Installer (open the Microsoft Store), with a manual VcXsrv download fallback — never silent
VcXsrv already installed Skip the install; launch the managed server directly
Managed VcXsrv dies mid-session ensure_running() restarts it on next use
App exit with sessions still open Managed server killed (no orphan); adopted external server left running
macOS without XQuartz, user declines install Session opens without GUI display; clear hint shown, no silent failure
Linux Wayland-only session without XWayland Detect gap; hint to install xwayland; do not bundle
Flatpak/Snap sandbox blocks the X socket Detect; hint to adjust sandbox --socket=x11; packaging-level fix
provideXServerAutomatically off, no server present Warn only; never download/install

Windows: VcXsrv install (decision)

Install VcXsrv via winget (winget install -e --id marha.VcXsrv --accept-package-agreements --accept-source-agreements -h), the analog of macOS's brew install --cask xquartz. Detect the installed binary at its canonical location (C:\Program Files\VcXsrv\vcxsrv.exe, or the (x86) tree); the managed launcher spawns that path. When winget (App Installer) is absent, guide the user to install it (open the Microsoft Store), with a manual VcXsrv download fallback (sourceforge.net/projects/vcxsrv). Rationale: no hosted/pinned .zip, no checksum machinery, and — because winget (or the user) fetches VcXsrv and termiHub only runs it as a separate process — no GPL-3.0 redistribution obligation (dropping the burden of the earlier download approach, #1076/#1056). Symmetric to the macOS path (#1318).

Windows: launch, auth, DISPLAY

Launch a single shared server vcxsrv.exe :0 -multiwindow -clipboard -auth <xauthfile> (-multiwindow → each remote app is its own native window; -nowgl as a GL fallback). Generate a per-start MIT-MAGIC-COOKIE-1 (16 random bytes → 32 hex), write a standard-format .Xauthority for localhost:0, pass via -auth, and hand the cookie to the transport half directly (bypassing read_local_xauth_cookie(), which shells to xauth — absent on Windows). MVP fallback: -ac (loopback-only, documented security tradeoff).

Detection fix (x11.rs)

detect_local_x_server() scans /tmp/.X11-unix and read_local_xauth_cookie() shells to xauth — both no-ops on Windows. Two changes: add a Windows TCP 127.0.0.1:6000 probe fallback for user-installed servers, and wrap detection in ResolvedXServer::detect_user_run() so a user-run server (DISPLAY / Unix socket / Windows TCP:6000) resolves into ResolvedXServer { info, cookie } in one place. LocalXServerInfo already has a TCP-loopback form (tcp_loopback(n) → 127.0.0.1:6000+n), so no new transport type is needed. Unix behavior stays unchanged.

Managed resolution lives in the orchestrator, not in core detection (#1087). After the seam collapse, detect_local_x_server() is only the user-run fallback: it does not consult any manager. The desktop ensure_x_server() resolves a managed (spawned) or adopted server into a ResolvedXServer (TCP 127.0.0.1:6000+n + the cookie known up front for a managed server, or read via xauth for an adopted one) and threads it straight to X11Forwarder::start(resolved: Option<ResolvedXServer>), which uses it as-is with no second probe. The retired ManagedXServerSource trait / SingleManagedServer adapter from the pre-#1087 design no longer exist — observable behavior is identical; the seam simply moved up a layer into the app.

macOS & Linux

  • macOS: detect /opt/X11 + XQuartz.app; if absent, run brew install --cask xquartz when Homebrew is present. When Homebrew is absent, don't host/redistribute a notarized .pkg — instead guide the user through installing Homebrew by opening a local terminal tab pre-loaded with the official installer command (the user drives the real sudo / RETURN prompts, never a silent install), then re-detect brew and continue with the cask install. If the user declines Homebrew, fall back to a deep link (xquartz.org) for a manual install — help ends there. If XQuartz is present, open -a XQuartz and let ssh -X/-Y set DISPLAY (:0 fallback). Cannot bundle. Because Homebrew or the user fetches XQuartz, termiHub never redistributes it (no APSL-2.0 hosting obligation, #1056).
  • Linux: the existing /tmp/.X11-unix detection covers the normal case. Classify gaps (Wayland-only without XWayland, headless, Flatpak/Snap X-socket sandbox) and show a targeted hint; never bundle or auto-install.

Orchestrator & IPC

ensure_x_server() dispatches per platform and is called from connector.rs X11 startup. Tauri commands (x_server_status, x_server_ensure, x_server_stop, x_server_install_dependency) and progress events reuse the agent-deploy event shape.

Licensing

termiHub no longer hosts or redistributes VcXsrv — winget (or the user) fetches it, and termiHub only runs it as a separate process (no linking). So the earlier GPL-3.0 redistribution obligation (ship the GPL-3.0 text + a source offer for the exact pinned build, #1076/#1056) no longer applies to this path; the residual posture is just the standard "we run a package-manager-installed program". XQuartz (MIT + APSL2) is likewise installed via Homebrew on macOS, not redistributed. Confirm the reduced footprint with #1056.

Implementation order

  1. Windows install (windows.rs) — detect VcXsrv + winget install, guided App Installer fallback (#1318).
  2. Lifecycle manager (manager.rs) — spawn/supervise/reuse/idle-shutdown.
  3. Auth + DISPLAY (auth.rs) — cookie + .Xauthority, wire into transport.
  4. Detection fix (x11.rs) — managed-aware + Windows TCP probe.
  5. Orchestrator + Tauri commands/events; hook into connector.rs.
  6. UI — settings toggle, first-run/progress prompt, Open Connections "X Servers" section.
  7. macOS guided install; Linux detect-and-guide.
  8. Integration/manual tests + docs.
