Overview

termiHub expands ${VAR} / $VAR placeholders and a leading ~ in connection settings at connect time, via expand_config_value in core/src/config/mod.rs. Every PTY backend calls its config's .expand() in the connect path — except WSL. WSL's connect() (core/src/backends/wsl.rs) parses the settings JSON and spawns wsl.exe directly, never calling WslConfig::expand(). As a result, WSL path and command values are already passed through literally today.

The problem is a schema/behaviour mismatch, not a runtime bug. WSL's settings schema advertises expansion that never happens: the startingDirectory field declares both supports_env_expansion and supports_tilde_expansion, and initialCommand and env both declare supports_env_expansion. Those flags are a promise the connect path does not keep. Worse, the "obvious fix" of just wiring WslConfig::expand() into connect() would be actively wrong:

expand_config_value resolves ~ and ${VAR} against the Windows host — host home_directory() (from USERPROFILE) and the host process environment. But a WSL startingDirectory is a Linux path handed to wsl --cd. Host-side expansion would rewrite ~ to something like C:\Users\foo and corrupt the path — a valid Linux directory would be destroyed before it ever reached the guest.

Maintainer decision (2026-08-07): leave WSL paths literal. Host-side expansion does not apply to WSL, and the supports_env_expansion / supports_tilde_expansion flags on WSL fields are corrected to advertise no expansion, so the schema matches the connect path. This concept documents that decision and specifies the exact code changes.

Goals

  • The WSL settings schema accurately reflects the connect path: no field advertises expansion that does not happen.
  • WSL startingDirectory, initialCommand, and env values are documented as passed through literally to the WSL guest.
  • The dead, never-called WslConfig::expand() is removed so no future change can silently reintroduce host-side (path-corrupting) expansion.

Non-Goals

  • Guest-side expansion — expanding ~ / ${VAR} against the WSL Linux distribution (its $HOME and its environment). Rejected; see General Handling.
  • Any change to expansion for the other backends (telnet, docker, ssh, serial, ftp, local shell) — they expand against the host correctly and are unaffected.
  • Changing the shared SettingsField struct. The supports_*_expansion fields stay; only WSL's values change to false.

UI Interface

This is a backend semantics concept with no visible UI change. The WSL connection form (rendered by DynamicForm from the schema) keeps the same fields. The supports_*_expansion flags are advisory schema metadata; they are carried in src/types/schema.ts but not currently rendered as an expansion hint by any form component, so users see no on-screen difference. The correction is about the contract the schema declares, not about pixels.

The one user-facing effect is behavioural honesty: a value like ~/projects in a WSL Starting Directory reaches wsl --cd ~/projects verbatim, and WSL/the login shell resolve ~ on the Linux side as they always have. termiHub does not — and now does not claim to — pre-expand it.

General Handling

Why literal (and not host-side expansion)

Host-side expansion is wrong for WSL because the namespaces differ. A WSL startingDirectory lives in the Linux filesystem; expanding ~ against the Windows USERPROFILE produces a Windows path that is meaningless (or actively misdirecting) inside the distribution. Passing the value through literally lets the Linux side own resolution: wsl --cd and the shell interpret the path in the namespace that actually contains it.

Rejected alternative: guest-side expansion

The considered alternative was to expand ~ / ${VAR} against the WSL guest — resolving the distribution's own $HOME and environment before spawning. It was rejected:

  • It duplicates what the guest already does. wsl --cd and the login shell already resolve ~ and environment references on the Linux side. Pre-expanding adds a second, redundant resolution path that can only drift from the shell's own.
  • It needs a guest round-trip. Reading the distribution's $HOME/env correctly means running a probe command inside WSL before the real spawn (distributions, users, and env differ per distro), adding latency and a new failure mode for no behaviour the guest does not already give for free.
  • Literal is already correct. The connect path never expanded, so shipping "literal + honest schema" is a no-op on runtime behaviour and simply removes a false promise — the lowest-risk outcome for a ventilator-grade release.

Preliminary Implementation Details

Based on the codebase at concept-creation time (verified against develop). The shared SettingsField struct (core/src/connection/schema.rs) keeps its supports_env_expansion / supports_tilde_expansion fields — they are used correctly by other backends. Only WSL's values change, and the never-called WSL expand() is removed.

File Change
core/src/backends/wsl.rs — settings_schema() Set the expansion flags to false on every WSL field that currently claims expansion:
  • startingDirectory: supports_env_expansion: true → false and supports_tilde_expansion: true → false
  • initialCommand: supports_env_expansion: true → false (tilde already false)
  • env: supports_env_expansion: true → false (tilde already false)
  • distribution and shellIntegration are already false for both — leave unchanged.
core/src/backends/wsl.rs — test schema_has_starting_directory Invert the two assertions that currently require the flags to be true: assert!(!f.supports_tilde_expansion) and assert!(!f.supports_env_expansion). Consider adding equivalent false assertions for initialCommand and env so the literal contract is regression-guarded.
core/src/config/mod.rs — WslConfig::expand() Remove the never-called impl WslConfig { fn expand(..) } (host-side expansion that would corrupt Linux paths). Removing it prevents a future change from re-wiring it into the connect path and silently reintroducing the bug.
core/src/config/mod.rs — test wsl_config_expand_replaces_placeholders Remove this test — it exercises the deleted WslConfig::expand(). No replacement is needed; the schema-flag assertions in wsl.rs now guard the literal contract.
docs/architecture.md Add a short note that WSL is the deliberate exception to per-field expansion: WSL values are passed to the guest literally because host-side expansion would corrupt Linux paths, and the WSL schema advertises no expansion. Natural spot: near the ADR-8 line "Supports environment variable expansion (${VAR}) and tilde expansion markers per field".

Verification

  • cargo test -p termihub-core — the updated schema_has_starting_directory passes and the removed WslConfig::expand() / its test no longer compile-block.
  • cargo build --workspace — confirm no remaining caller of WslConfig::expand() (there are none in the connect path; the only reference today is the test being removed).
