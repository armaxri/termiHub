Overview #

The SSH tunnel state machine has two authorities that are only loosely reconciled: a declared TunnelStatus enum, and the runtime truth in active_tunnels: Mutex<HashMap>. Status is never stored — get_statuses() recomputes it purely from set membership (in the active map → Connected; connecting → Connecting; else Disconnected). There is no field that can hold Error or Reconnecting. This produces three user-facing defects that this concept fixes:

  • Dead tunnels stay green and leak (GAP 1). When the bastion drops, the laptop sleeps, or the server reboots, the SSH session dies but nothing observes it. The accept loops just break and log; the ActiveTunnel (with its pooled endpoint / gateway PooledRef guards) lingers in the active map. The sidebar dot stays green “connected”, every localhost:port connection fails, and the only control is Stop. The leaked tunnel also vanishes from the Open Connections kill panel (its filter only counts connected/connecting).
  • False “Connected” on accept-loop death (GAP 2). Forwarders bind synchronously (good), then tokio::spawn the accept loop and immediately return Ok. Any post-bind failure lands after Connected was already reported — green dot, zero traffic.
  • No reconnect, stale stats (GAP 5, GAP 6). The reconnect_on_disconnect toggle is persisted but never read. The tunnel-stats-updated event is wired end-to-end on the frontend but has no Rust emitter, so ↑/↓ bytes and N conn freeze at 0 for the tunnel’s whole lifetime.

The redesign makes session death observable, turns Error into a real, persisted, queryable resting state (surfaced in the sidebar and Open Connections), implements opt-in reconnect with backoff, and gives tunnels live throughput / connection-count stats. It also adds the missing controls the correct machine needs: Retry, Reconnect, View last error, and force-Stop of a stuck/errored tunnel from the canonical kill panel.

Goals

  • Detect SSH session / accept-loop death and transition Connected → Error, dropping the active_tunnels entry and its pool guards (GAP 1, GAP 2).
  • Make Error a persisted resting state that survives reload and is returned by get_statuses(), with its last-error message (GAP 3).
  • Implement reconnect_on_disconnect with capped exponential backoff (GAP 5).
  • Emit tunnel-stats-updated periodically for live throughput & connection counts (GAP 6).
  • Expose Retry, Reconnect, View-last-error and force-Stop in the TunnelSidebar and Open Connections.

Non-Goals

  • GAP 4 (re-entrancy Start/Stop double-fire guard) — tracked separately; the audit stages it between GAP 3 and GAP 5, but it is a small store-level guard, not part of the lifecycle redesign.
  • Confirm-before-delete for active tunnels (GAP 7) and Kill-panel drift (GAP 9 details).
  • Reworking the tunnel editor form beyond the reconnect toggle’s meaning.
  • Persisting tunnel traffic history — stats are live/instantaneous only.

UI Interface #

The tunnel surface gains a fourth resting colour — red = Error — alongside green (connected), amber (connecting/reconnecting) and grey (disconnected). An errored row shows the last-error text inline and swaps its action buttons for Retry and View last error. A connected row shows live throughput and connection count, plus a Reconnect (force-reconnect) control. The same Error tunnels now appear in Open Connections so they can be force-Stopped from the canonical kill panel.

General Handling #

Session death mid-tunnel

A supervisor task per active tunnel waits on a liveness signal (see the design decision in §Behavior). When the signal fires it removes the entry from active_tunnels, drops the pool guards (draining the shared endpoint / gateway sessions), records the last error, and — depending on reconnect_on_disconnect — either emits Error or enters the reconnect loop. The user sees the row turn red with the cause, and Open Connections stops listing it as a live connection.

Accept-loop exit right after bind (GAP 2)

The accept loop breaking is treated identically to session death: it is one of the liveness signals. An early exit (e.g. the socket is reclaimed, or a remote-forward local target is unreachable so every relay fails) transitions the tunnel to Error rather than leaving a green dot with zero traffic. Per-connection relay failures that do not kill the loop stay best-effort (logged), but a run of them does not falsely keep the tunnel “healthy” because throughput/conn stats now update live and the liveness watch covers the session.

Error persisting across reload

The manager keeps a last_errors: Mutex<HashMap<String, TunnelError>> set on the Error branch and cleared on a successful start / explicit stop / Retry. get_statuses() returns Error{error} for those ids, so a window reload (loadTunnels overwrites the whole frontend map from get_statuses) no longer launders Error back to Disconnected. “Never started” and “died with an error” become distinct, durable states.

Reconnect backoff

With reconnect_on_disconnect enabled, session death enters Reconnecting and re-runs the start path under a capped exponential backoff (e.g. 1s, 2s, 4s, 8s, 16s; max ~5 attempts, configurable default). Each wait emits the Reconnecting status with the attempt number so the sidebar can show the countdown. Success returns to Connected; exhausting the attempts falls through to Error (“reconnect failed after N attempts”). A user Stop at any point cancels the reconnect loop (via a per-tunnel CancellationToken, mirroring the existing connect-cancel path) and returns to Disconnected. If reconnect is off, death goes straight to Error and the “Reconnecting” branch never runs — no dead toggle.

Stats polling vs event

Stats are pushed, not pulled. A single periodic task (e.g. every 1s while any tunnel is active) reads each forwarder’s live ForwarderStats atomics and emits tunnel-stats-updated per tunnel; the already-wired useTunnelEvents hook merges them into the store. This matches the existing frontend plumbing (which today receives nothing) and avoids the sidebar re-polling get_statuses. The pull API (get_statuses) still returns a stats snapshot for the initial loadTunnels and reloads.

Edge cases

  • Reconnect vs. Stop race: Stop always wins — it cancels the token before the next attempt and clears any pending backoff timer.
  • Shared pooled session: when a pooled endpoint / gateway session dies, multiple tunnels may error at once; each supervisor independently drops its guard so the pool ref-count returns to zero and the session drains exactly once.
  • App shutdown during reconnect: stop_all cancels every reconnect loop so no zombie backoff task survives teardown.
  • Retry on a stale-but-green tunnel: the Reconnect control force-tears-down and re-starts even if liveness hasn’t fired yet, covering cases the watch is slow to notice.

Design decision — the liveness mechanism

The core question is how a tunnel learns its SSH session died. Three options:

Option How it works Pros Cons
A. Accept-loop-exit only Treat the forwarder’s accept loop break (and every relay failing) as the death signal via a watch/oneshot the loop fires on exit. Cheapest; no new SSH machinery; catches GAP 2 directly. Local/dynamic accept loops don’t exit when only the SSH session dies — the listener is still bound; only new relays fail. So pure session death (bastion drop, sleep) can go undetected until the next connection attempt. Weak for GAP 1.
B. SSH keepalive / channel-watch Observe the shared SshSession liveness — a keepalive/heartbeat or a closed-notification from russh — and fire the death signal centrally. Detects true session death promptly and proactively, independent of traffic; the natural GAP 1 fix. Requires a liveness hook on SshSession (russh Handle) that the pool exposes; more plumbing; keepalive interval is a new tunable.
C. Both (recommended) Supervisor selects over both a session-liveness watch (B) and the accept-loop-exit signal (A); whichever fires first wins. Covers GAP 1 and GAP 2 with no gap: proactive session-death detection plus catching post-bind forwarder failures the session watch can’t see. Slightly more wiring; two signals to reason about.

Recommendation: Option C. Option A alone leaves the audit’s critical GAP 1 (silent session death while the listener stays bound) largely unaddressed; Option B alone misses GAP 2’s post-bind forwarder deaths. A supervisor that tokio::select!s over a session-liveness watch (surfaced from the pooled SshSession) and a forwarder accept-loop-exit channel closes both gaps. If the russh session-liveness hook proves costly, ship Option A first (S2) as the accept-loop signal + a lightweight periodic keepalive probe, then upgrade to the native watch — the supervisor shape is identical either way.

Preliminary Implementation Details #

Grounded in the code at concept time. The manager is src-tauri/src/tunnel/tunnel_manager.rs; the forwarders are local_forward.rs / remote_forward.rs / dynamic_forward.rs; the enum lives in src-tauri/src/tunnel/config.rs. Status is recomputed in get_statuses() (there is no stored status today), events go through emit_status → tunnel-status-changed, and the frontend mirror is appStore.tunnelStates fed by useTunnelEvents.

Staging

Per the issue and the audit’s recommended order: S1 = GAP 3 (persisted queryable Error), S2 = GAP 1 + GAP 2 (supervisor + liveness → real Error), S3 = GAP 5 + GAP 6 (reconnect loop + live stats). S1 lands the persisted Error plumbing and UI first so S2 has a resting state to transition into; S3 builds the reconnect loop and stats emitter on the S2 supervisor.
