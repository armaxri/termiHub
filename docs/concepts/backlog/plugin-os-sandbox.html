Overview #

Today a native plugin backend (a cdylib speaking the frozen 1.x C ABI in termihub-plugin-api) is dlopened by core/src/plugin/host.rs straight into the main termiHub process. Once loaded it can read the decrypted credential vault from memory, use SSH_AUTH_SOCK, read ~/.ssh, open any socket and tamper with every live session. The permission model (network, filesystem, …) and the capability bridge are honest about this: they mediate only what a cooperating plugin routes through them. For 0.1 the risk is contained by policy — native plugins are default-off, each one needs a hash-bound trust acknowledgement (#3296), and plugin types are terminal-only (PLG-004). The maintainer decided on 2026-09-25 that a real OS sandbox is a pre-v1.0 requirement (audit finding SEC-002).

This concept moves every native plugin into its own sandboxed helper process. The helper loads the unchanged plugin library, the OS confines the helper, and the host talks to it over a narrow, framed IPC channel. The frozen ABI is kept inside the helper: plugins do not change and are not rebuilt.

Recommendation in five lines

  1. One sandboxed helper process per plugin (not per session, not per trust domain). A new small binary, termihub-plugin-runner, ships as a Tauri sidecar. It loads the plugin's library inside itself and proxies the 1.x C ABI over IPC, so plugins stay binary-compatible and the ABI gets no version bump.
  2. The IPC channel is an inherited socket pair (Unix UnixStream::pair, Windows a private named pipe handle). Frames are length-delimited. Terminal bytes travel raw; control messages use MessagePack. Budget: at most +0.5 ms p99 echo latency and at least 80 % of in-process throughput.
  3. Per-OS confinement: macOS uses a Seatbelt profile applied by the helper to itself with sandbox_init (no signing needed, so it works for the unsigned beta). Linux uses landlock + seccompiler + no_new_privs, with namespaces as optional extra hardening. Windows uses a per-plugin AppContainer with no capabilities plus a job object.
  4. Deny by default. The plugin can touch only its own install folder (read-only) and its data folder (read-write). It cannot create sockets, start programs or reach devices. Declared network/filesystem permissions are honoured only through the existing capability bridge, which now runs in the host across the IPC boundary. Socket handles are passed to the helper after the host has checked the request.
  5. Fail closed. If full isolation cannot be set up (mostly Linux kernels without landlock), the plugin does not load, unless the user records a hash-bound reduced-isolation acceptance. A crash or hang kills only that plugin's sessions, with up to 3 restarts and then auto-disable. In-process loading is removed before v1.0.

Goals

  • A compromised or malicious native plugin cannot read termiHub's memory (credentials, other sessions), the user's files outside its data folder, or the SSH agent. It cannot open network connections the user did not allow, start processes, or persist outside its data folder.
  • The frozen 1.x plugin ABI (ADR-15) keeps working with no change to plugin code or builds: every ABI 1.0/1.1 plugin that loads today loads inside the helper.
  • A plugin crash, panic = "abort", segfault, out-of-memory or hang never takes down the termiHub host process.
  • Declared permissions become real sandbox rules, enforced by the kernel rather than by plugin cooperation.
  • Users see the sandbox: each plugin shows its isolation status, what it can reach, and clear crash and permission-denied feedback.
  • Automated escape tests run on every OS in CI and prove that the confinement holds.

Non-Goals

  • Sandboxing frontend (JS/theme) plugins. They already run in a least-privilege Web Worker (src/plugins/sandbox/).
  • Widening the capability ceiling. Plugins stay terminal-only (PLG-004). New surfaces (file browser, monitoring, devices, process spawn) each need their own permission and sandbox rule, designed together later.
  • Protecting against terminal-content attacks. A plugin legitimately controls the bytes shown in its tab, so it can draw a fake password prompt. The trust acknowledgement stays for this reason (see Trust after the sandbox).
  • Hosting plugins on remote agents. Agents do not run a PluginHost.
  • Kernel or zero-day sandbox escapes. The sandbox raises the cost of an attack; it is not a guarantee against OS bugs.

UI Interface #

The sandbox runs mostly in the background. It shows up in the UI in three places: the Native Plugins section of Settings → Plugins (isolation status, what the plugin can reach, process status), the plugin's terminal tab when the helper crashes or stops responding, and a rate-limited toast when the host refuses a plugin request (for example, a network connect without the network permission).

Copy and placement rules

  • Crash overlay heading: "The plugin stopped unexpectedly". The subheading always names the plugin and says that termiHub and other sessions are unaffected. The error box shows the exit reason (signal / exit code / "stopped responding" / "used too much memory").
  • Permission toasts are rate-limited: at most one per plugin per 30 s, later ones fold into "and N more". Every denial is logged under the plugin log target (Log Viewer) with the manifest id, like the existing services log callback.
  • Only bridge denials raise a toast, because they are the ones the host observes with full context. Kernel-level denials (a direct socket() call returning EPERM) are logged best-effort, without a toast. See Denial reporting.

General Handling #

Process model — decision

Option Isolation Cost ABI semantics Verdict
Helper per plugin Plugins are isolated from the host and from each other. Each helper gets a profile built from that plugin's own permissions. One process per enabled plugin (~5–15 MB RSS), idle-reaped. Preserved: one dlopen, termihub_plugin_init once, many create_backend calls, global plugin state shared across sessions exactly as today. Recommended
Helper per session Strongest: sessions are isolated from each other too. One process per tab. The 40-concurrent-terminal goal turns into 40 processes, plus a cold start (spawn + sandbox + dlopen) on every connect. Changes semantics: init/shutdown run per session and a plugin can no longer share state between its sessions. Rejected as the default. A possible later per-plugin opt-in.
Helper per trust domain (publisher) Weaker. The profile must be the union of all its plugins' permissions, and one plugin's crash or compromise affects its siblings. Fewest processes. Preserved, but several libraries share one address space. Rejected
Re-exec the main termiHub binary as the helper Same as per plugin. Loads the Tauri/WebKit/GTK dependency closure into every helper. That means a larger read allow-list and more memory. Preserved. Rejected in favour of a small dedicated termihub-plugin-runner sidecar.

Lifecycle

  • Spawn on load. When the plugin manager would load a native plugin today (enable, startup, trust granted), the host spawns its helper. The helper checks the library digest (the existing PinnedLibrary logic), applies the sandbox, then dlopens the library and runs the existing ABI gate, toolchain rule and termihub_plugin_init. It reports PluginInfo plus the enforced sandbox report back to the host. The host no longer dlopens any native plugin itself.
  • Sessions are multiplexed over the helper's single channel with a host-assigned session_id.
  • Idle reap. 5 minutes after the last session closes, the host sends Shutdown (the plugin's termihub_plugin_shutdown runs) and the helper exits. The next session respawns it lazily and re-verifies the digest. This keeps "many plugins installed" cheap.
  • Disable / revoke / uninstall / app quit: cancellation flags are set, then close runs for every session (2 s budget), then Shutdown (2 s budget), then the helper is killed. The host never waits on a plugin without a deadline.
  • Parent death. The helper must never outlive the host. Linux uses PR_SET_PDEATHSIG(SIGKILL). On all OSes the helper exits on EOF of the IPC socket. Windows adds a job object with KILL_ON_JOB_CLOSE.

Crash isolation and restart policy

  • A helper exit while sessions are open (signal, abort, non-zero exit, OOM kill) ends those sessions with the crash overlay. The host and all other sessions keep running. This also contains panic = "abort" plugins, which today would abort the whole app.
  • The existing RestartTracker (MAX_RESTART_ATTEMPTS = 3) counts crashes. The helper is respawned immediately, so new sessions work, but crashed sessions are not auto-recreated, since plugin types have no reconnect or resume protocol (PLG-004). The user decides with Restart session. On the 4th crash the plugin is auto-disabled ("Disabled after 3 crashes"). The budget resets after 10 minutes without a crash, or on Re-enable.
  • Hang detection. The host pings every 5 s. Without a pong for 10 s the helper is "Not responding", gets killed and counts as a crash. Each request/response call (bridge replies, close) has its own deadline.
  • Resource limits (defaults, overridable per plugin only by the host, never by the manifest): memory 512 MiB (Windows job memory limit, Linux RLIMIT_AS; macOS has no hard per-process limit, so the host polls RSS and kills at 1 GiB), file descriptors 256, no child processes.

Capability model — what a terminal-only plugin may access

The principle is deny by default, mediate through the host. The sandbox blocks every resource the plugin does not strictly need to run. Anything a declared permission grants goes through the capability bridge, which already exists and already checks PermissionSet, FilesystemScope and ConnectionPolicy. Its callbacks are simply served by the host over IPC instead of in-process. One enforcement point, the same on all three OSes.

Why declared filesystem paths are not opened up directly in the sandbox. Granting the declared roots as landlock/Seatbelt/ACL rules was considered. It was rejected for v1 for three reasons. On Windows it would mean rewriting ACLs on user directories. It would widen the kernel-visible surface for a permission no shipped plugin uses. And the bridge already is the documented API (plugin-authoring.md). A later minor can add "direct access to declared paths" as an opt-in if a plugin needs streaming file I/O.

Trust after the sandbox

  • The hash-bound trust acknowledgement (#3296) stays. The sandbox limits what a plugin can reach, not what it shows. A trusted plugin still draws its terminal and can phish there. The acknowledgement gains one optional field, reducedIsolationAccepted, with the same fail-closed rules as unverifiedToolchainAccepted: a plain or older acknowledgement never carries it.
  • The global native default-off toggle stays for 1.0 (recommended). Whether to flip the default once the sandbox has soaked is a maintainer decision for after the extended-testing period, not part of this concept.
  • There is no "run unsandboxed" switch for users. A toggle back to in-process would bring back the inverted trust model SEC-002 describes. The in-process path survives only as a debug-build developer flag until it is removed (phase 7).
  • The ABI 1.0 toolchain acceptance stays required. The helper's FFI assumptions are the same as the host's today; only the blast radius shrinks. Relaxing it is a separate later decision.

Plugin-author impact

  • No rebuild, no ABI change. The ABI is not bumped. The SDK crate stays publish = false.
  • Behaviour that changes: direct std::net / std::fs outside the data folder now fails with a permission error, so use the bridge. Plugins cannot spawn processes. HOME/TMPDIR point into the data folder. These rules are documented in docs/plugin-authoring.md. No third-party plugins have shipped yet, so the installed base affected is effectively zero.

Preliminary Implementation Details #

Based on the architecture at concept time (October 2026, plugin ABI 1.1). The codebase may change before implementation. This section describes the planned approach given the current state.

Components

Location Change
plugin-runner/ (new workspace member, bin) New — termihub-plugin-runner. Small, with no Tauri/webview dependencies. Parses one argument (protocol version), reads Configure from the inherited fd, applies the sandbox, then reuses core::plugin::host's loading code (load_backend_library_with, PinnedLibrary, ABI/toolchain gates). The loading code moves into a shared module that does not pull in the rest of core. IPC surface

  • Transport. Unix uses std::os::unix::net::UnixStream::pair(). The child's end is inherited as fd 3 (close-on-exec cleared only for it); everything else is closed. Windows uses a duplex named pipe with a random 128-bit name, created by the host with a DACL for the user SID and the plugin's AppContainer SID only. The host connects the client end and passes it via PROC_THREAD_ATTRIBUTE_HANDLE_LIST. No filesystem rendezvous path exists, so nothing can squat it, and the plugin cannot open new IPC endpoints.
  • Framing. Each frame is a 4-byte big-endian length followed by a 1-byte kind and the payload; max frame 1 MiB. The host uses tokio_util::codec::LengthDelimitedCodec (already a dependency); the runner uses a small synchronous reader with the same format. Hot-path kinds (Input, Output) carry u32 session_id + raw bytes, with no serialisation. Control kinds (Hello, Configure, SandboxReport, Loaded, CreateSession, Resize, Close, Cancel, BridgeRequest/Reply, Log, Ping/Pong, Shutdown) are MessagePack via rmp-serde (already a dependency). ipc-channel (Servo) was considered and rejected: it brings its own serialisation and macOS Mach-port transport, which is more surface than one socket pair needs.
  • Handle passing for bridge sockets uses SCM_RIGHTS on Unix (via rustix/nix, already in the tree) and DuplicateHandle on Windows (decided in the spike, #4181). The runner drives the passed socket as a plain overlapped file handle (ReadFile/WriteFile) and never loads Winsock, because Winsock cannot start under LPAC. WSADuplicateSocketW works into a plain AppContainer but not into LPAC. The StreamData proxy stays only as the fallback for a socket that is not a kernel file handle (a non-IFS layered provider).
  • Semantics delta, host side only. write_input and resize become asynchronous. The host queues them with a bounded queue (backpressure, no unbounded growth), and a plugin error arrives later as a session error. Inside the helper the plugin still sees the synchronous ABI call and returns its PluginStatus exactly as specified. is_alive becomes an event the runner pushes on change.
  • Untrusted peer. The host validates every frame: length cap, known kind, known session_id, Log lines capped at 8 KiB and sanitised (the existing services rules), and a per-plugin output rate cap. Any violation kills the helper.

40 concurrent sessions in one plugin no frame starvation; fairness within 2× 40 echo sessions pumping 64 MiB each through one helper at once (released together; 8 MiB finished inside one scheduler quantum on a 3-vCPU CI runner, #4233)
Helper cold start (spawn + sandbox + dlopen + init) ≤ 150 ms p95 per-OS CI timing, 40 load/unload cycles after one unmeasured first start
Idle helper memory ≤ 15 MB RSS per-OS CI measurement

Why throughput is absolute only (#4190). The first measurement (#4182) showed the in-process echo baseline is a plain memory copy (about 35 GB/s), while the helper moves about 3.5 GB/s over the socket: roughly 10 % of in-process, yet 35 times the 100 MB/s floor and far above anything a terminal needs. No cross-process transport can reach 80 % of a memory copy, so the relative figure is reported, not enforced. The latency budget stays relative (p99 added), because there the baseline is meaningful.

Output frames are written with a single writev/WriteFile per send. No artificial coalescing delay is added; the plugin's own chunking decides the batching.

Per-OS sandbox

macOS — Seatbelt via sandbox_init (proven in the spike)

  • The runner calls sandbox_init_with_parameters on itself, after opening the IPC fd and pinning the library but before dlopen. The profile is a generated SBPL string: (deny default), allow read + map-exec of the install folder and system libraries, read/write of the data folder, (deny network*), (deny process-exec process-fork), deny iokit-open, and only the few mach-lookup services dyld and libsystem need. This is the mechanism Chromium, Firefox and WebKit use for their renderer/content processes.
  • Works for the unsigned beta: it needs no code signature, entitlement or provisioning profile.
  • Caveat: the API is formally deprecated or private, but it has been stable for over a decade and is relied on by every major browser. The fallback, should Apple ever remove it, is the App Sandbox (below).
  • Decided in the spike (#4181): a hand-written FFI wrapper, not birdcage. birdcage is GPL-3.0-or-later (fails the deny.toml licence allowlist), only offers a spawn-a-child API instead of confining the calling process, and its fixed base profile allows mach*, ipc*, sysctl*, process-fork and global file-read-metadata. The FFI wrapper is ~60 lines. The proven profile needs no mach-lookup at all. See Spike results.
  • App Sandbox entitlements — rejected for now. They need a signed helper carrying com.apple.security.app-sandbox. Ad-hoc signing makes container behaviour unreliable, and the container is static per bundle id: dynamic per-plugin paths would need security-scoped bookmarks. Revisit once Developer-ID signing lands (macos-code-signing-notarization).
  • sandbox-exec (CLI) — rejected. It wraps the same mechanism, but adds a dependency on a deprecated binary and a profile passed on argv.

Linux — landlock + seccomp + no_new_privs (namespaces optional)

  • Required layers: PR_SET_NO_NEW_PRIVS, a seccomp-bpf allow-list built with seccompiler (AWS Firecracker; pure Rust, no libseccomp dependency), and a landlock filesystem ruleset built with landlock (the official rust-landlock crate, with its best-effort compatibility mode reporting what was actually enforced).
  • Seccomp actions: EPERM for "soft" calls a plugin might reasonably try (socket, connect, bind, listen, open_by_handle_at, fork and clone without CLONE_THREAD — so a plugin's std::process::Command fails cleanly instead of ending its runner, as the spike and the escape probe expect). KILL_PROCESS for escape primitives (execve*, ptrace, process_vm_*, pidfd_getfd, mount, bpf, keyctl, perf_event_open, io_uring_*, unshare, setns). Everything outside the allow-list answers ENOSYS (including clone3, see below).
  • Network is closed by the seccomp socket() denial on every kernel. landlock ABI v4 (Linux 6.7+) adds TCP bind/connect denial as a second layer. An unprivileged user + net namespace is attempted as extra hardening but is not required: Ubuntu 23.10+ restricts unprivileged user namespaces via AppArmor, and containers often forbid them.
  • Fallback: the only layer with a meaningful kernel floor is landlock (5.13+). Kernels without it (e.g. Debian 11, RHEL 8) get seccomp plus the env scrub but no filesystem confinement. The runner reports this as reduced, the plugin stays unloaded unless reducedIsolationAccepted is recorded, and the row names the missing layer. If seccomp itself fails, the plugin never loads.
  • extrasafe and birdcage were considered as all-in-one wrappers. The two focused crates give exact control over the enforced-layer report, which the fail-closed policy depends on. Confirmed in the spike (#4181): landlock 0.4 + seccompiler 0.5 confine the runner before dlopen with FullyEnforced on Ubuntu 24.04 (kernel 6.17) and inside Docker's default seccomp profile (kernel 6.12). Seccomp must answer clone3 with ENOSYS so glibc falls back to the inspectable clone. See Spike results.

Windows — Less-Privileged AppContainer + job object (proven in the spike)

  • A per-plugin AppContainer profile (CreateAppContainerProfile, name termiHub.Plugin.<sha256(id)[..16]>) with zero capabilities: no internetClient, no loopback, no user-profile access. The runner is spawned with PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES. The host adds ACEs for the AppContainer SID on the runner's folder and the install folder (read+execute) and the data folder (modify), and removes the profile on uninstall.
  • Decided in the spike (#4181): Less-Privileged AppContainer (LPAC), zero capabilities. The runner is also spawned with PROC_THREAD_ATTRIBUTE_ALL_APPLICATION_PACKAGES_POLICY = PROCESS_CREATION_ALL_APPLICATION_PACKAGES_OPT_OUT. LPAC loads the plugin and its dynamic CRT (VCRUNTIME140.dll, api-ms-win-crt-*) fine. A plain AppContainer can still open HKCU\Software (other apps' saved sessions live there); LPAC denies it. Do not add the registryRead capability: it makes Winsock work again but re-opens HKCU\Software. Under LPAC Winsock cannot start (WSAStartup = 10107), which shapes bridge-socket passing (see Spike results).
  • Job object (via the win32job crate or the windows crate directly): KILL_ON_JOB_CLOSE, active-process limit 1, process memory limit, UI restrictions. Add the PROCESS_CREATION_CHILD_PROCESS_RESTRICTED mitigation policy.
  • Bindings come from Microsoft's windows crate (already in the tree). No mature dedicated AppContainer crate exists, so this is a thin, well-tested wrapper.
  • Restricted token + integrity level (Chromium-style) — rejected as the primary mechanism. It is much more code to get right, and AppContainer gives network-off and profile-off by default. Kept as a fallback idea only if AppContainer breaks a class of plugins.

Denial reporting

  • Bridge denials are fully observable in the host and drive the toast and log (phase 6).
  • Kernel denials are best-effort. On Linux the runner installs the EPERM rules as SECCOMP_RET_TRAP with a SIGSYS handler that sets the return value to -EPERM and queues a Denied{syscall} Log frame (the technique Chromium uses). macOS and Windows only log the denial on the plugin's own error path. This is acceptable because these are bugs or attacks, not user workflows.
  • As built (#4236). The handler counts each trapped call in a fixed table of atomics (async-signal-safe, no allocation, no system call); a runner thread drains it once per second into one Denied{syscall} Log frame per system call with the number of refused calls (the rate limit). The frame is an additive denied field on Log; the host checks the name, records the denial next to the bridge denials (DenialReason::Syscall) and logs it through the plugin's log rate limiter. Process creation (fork, vfork, non-thread clone) is not trapped: libc blocks every signal around that clone (posix_spawn), and the kernel kills a thread whose forced SIGSYS is blocked, so those denials stay a silent EPERM. rt_sigaction(SIGSYS, <new>) fails with EPERM, so a plugin cannot replace the handler to fake a success; the denied call is never executed either way.

Testing strategy

  • Escape-probe plugin (core/tests/plugin_fixture/escape-probe, test-only cdylib). It tries, and reports the result of each attempt to: read a canary in a temp HOME/.ssh and in the app config dir; write outside the data folder; connect to a canary TCP listener the test owns; resolve DNS; exec /bin/sh or cmd.exe; fork; ptrace the host or read its /proc/<pid>/mem; read SSH_AUTH_SOCK; connect to the ADR-13 spawn socket or pipe; open a serial device; on Windows, open the user profile and HKCU. The test asserts that every attempt fails and that the canary listener saw zero connections. It also runs positive controls (data-folder write, bridge connect with network) to prove the sandbox is not simply broken.
  • Where it runs: every PR that touches core/src/plugin/**, plugin-runner/** or plugin-api/**, on ubuntu, macOS and windows, by extending the existing per-OS .github/workflows/plugin-packaging.yml lane that already packages, trusts and dlopens echo-backend. These are safety tests, so they are never moved to the post-merge lane.
  • Fallback coverage: a debug-only TERMIHUB_SANDBOX_SIMULATE_MISSING=landlock forces the reduced path, so states and acknowledgement gating are tested on any kernel. A Docker job with the default seccomp profile (which blocks unshare) covers the "no user namespaces" path.
  • Crash and hang fixtures: plugins that segfault, abort, spin, allocate without bound, and send garbage frames. They assert the host survives, the states follow the diagram, and the restart budget leads to auto-disable.
  • Fuzzing: cargo-fuzz targets for the frame decoder in both directions plus a structured round trip (plugin-runner/fuzz/), run for 60 s each with a cached corpus on the nightly lane (#4190).
  • Performance gate: the ignored test core/tests/plugin_runner_perf.rs measures in-process and sandboxed echo-backend and fails on any breach of the budget table, listing every breach. The nightly plugin-sandbox-nightly.yml lane runs it optimised on Linux and macOS (#4190). The budgets are absolute ceilings, not "20 % worse than the last run": hosted runners vary by more than 20 % from run to run, so a stored baseline would flap.
  • ABI preservation: the existing core/tests/plugin_abi_1_1.rs (1.0 and 1.1 plugins, toolchain rule) and plugin_package_load.rs run unchanged through the sandboxed host.

Spike Results (Phase 0, #4181) #

Each prototype runs the same steps as the planned runner: open the IPC channel and canary listeners, apply the sandbox to itself, then load the real echo-backend example plugin, create a session and round-trip hello sandbox through it. macOS — Seatbelt

Why not birdcage. Version 0.8.1 is licensed GPL-3.0-or-later, which the deny.toml licence allowlist rejects for a distributed binary. Its API only applies the sandbox and then spawns a child (Sandbox::spawn(Command)), which does not fit a runner that confines itself and then calls dlopen. Its fixed base profile also allows mach*, ipc*, sysctl*, system*, process-fork and file-read-metadata on every path. Any one of these rules it out.

The profile that works. Paths are canonicalised before the sandbox is applied and passed as parameters, never spliced into the string. No mach-lookup rule is needed: the dyld shared cache and libSystem are already mapped when the profile is applied. 

(version 1)
(deny default)
(allow file-read* file-map-executable
  (subpath "/usr/lib") (subpath "/System/Library")
  (subpath "/System/Cryptexes/OS") (subpath "/System/Volumes/Preboot/Cryptexes/OS"))
(allow file-read* (literal "/dev/urandom") (literal "/dev/random"))
(allow file-read* file-write-data (literal "/dev/null"))
(allow file-read* file-map-executable (subpath (param "INSTALL_DIR")))
(allow file-read* file-write* (subpath (param "DATA_DIR")))
(allow sysctl-read)
(allow process-info* (target self))
(allow signal (target self))
(deny network*)
(deny process-exec* process-fork)
(deny iokit-open)

Windows — AppContainer, LPAC and socket passing

Run on the windows-latest runner (Windows Server 2025, build 26100) through a temporary workflow on a throwaway branch, since deleted. The host process creates the profile termiHub.Plugin.spike4181 with zero capabilities, grants its SID RX on the runner and install folders and M on the data folder, and spawns the runner with CREATE_SUSPENDED, a handle list holding only the stdout pipe, PROCESS_CREATION_CHILD_PROCESS_RESTRICTED and a job object (kill on close, active-process limit 1). While the runner is suspended, the host passes it two connected loopback sockets: one with WSADuplicateSocketW, one with DuplicateHandle. Both the plugin and the runner link the dynamic CRT (VCRUNTIME140.dll, api-ms-win-crt-runtime/heap, checked with dumpbin /dependents).

  • LPAC is viable and the stronger choice. It loads the plugin with its dynamic CRT, and it is the only variant that closes HKCU\Software, where other applications keep saved sessions (PuTTY, WinSCP). Error 367 is ERROR_CHILD_PROCESS_BLOCKED: the child-process mitigation fires before the job's process limit. System files stay readable, which is expected and harmless.
  • Winsock cannot start under LPAC (WSAStartup returns WSASYSCALLFAILURE). registryRead fixes that but re-opens HKCU\Software, so it is not granted. As a result, a passed socket is driven as a kernel file handle. Rust's std::net panics inside an LPAC process (its lazy Winsock init asserts), so a plugin that bypasses the bridge and uses std::net crashes its own helper. This is contained, but plugin-authoring.md must say so.
  • Spawn plus sandbox plus LoadLibrary takes 15–60 ms end to end on the runner, within budget.

Linux — landlock + seccomp

Run in Docker (rust:1.98-bookworm, kernel 6.12, Docker's default seccomp profile, as root and as nobody) and on the ubuntu-latest runner (Ubuntu 24.04, kernel 6.17). On both, landlock reports FullyEnforced (fs and net, ABI v6, with no_new_privs). Every probe is denied: file reads return EACCES from landlock; network, exec and fork return EPERM from seccomp. The plugin still loads and echoes, and the sandbox takes about 0.3–0.6 ms to apply. One finding: clone3 must return ENOSYS, because its flags sit behind a pointer that seccomp cannot inspect. glibc then falls back to clone, whose CLONE_THREAD bit the filter checks.

Changes to later phases

  • Phase 1: on Windows the runner must not call Winsock at all, including through std::net. Its IPC is the inherited pipe handle, which the spike showed works through PROC_THREAD_ATTRIBUTE_HANDLE_LIST into LPAC.
  • Phase 2: Windows bridge sockets use DuplicateHandle into the suspended or running helper. The runner builds PluginTcpStream over overlapped ReadFile/WriteFile/CancelIoEx. Shutdown and socket options are done host-side over IPC, because the runner has no Winsock. The StreamData proxy is built only as the fallback for a socket that is not a kernel file handle. Unix stays SCM_RIGHTS.
  • Phase 4: seccomp needs the clone3 → ENOSYS rule. Docker's default profile allows the landlock syscalls (Docker 29), so the "Docker no-userns" job should see the full layer set.
  • Phase 5a: no birdcage; ship the profile above, generated with parameters. Measure the first-launch Gatekeeper cost on the signed bundle.
  • Phase 5b: LPAC with zero capabilities. Grant the AppContainer SID RX on the runner's own folder, not only the plugin install folder. Add HKCU\Software to the escape probe as an explicit assertion.
  • Phase 7: plugin-authoring.md states that direct std::net/Winsock use from a plugin fails on Windows (and is denied everywhere). Network goes only through the bridge.
