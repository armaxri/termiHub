Overview #

The remote-agent transport lifecycle (deploy → setup → connect → reconnect → sessions on agent) works on its happy path but breaks at the edges. The #1131 audit found eleven gaps (G1–G11) that cluster into three failure families:

  • Stuck — an in-flight connecting handshake to a slow or unreachable host cannot be aborted (G1); deploy/setup have a Cancel button that only closes the dialog while the SFTP upload keeps running (G10); after auto-reconnect exhausts there is no first-class Retry (G3).
  • Leak / invisible — a reconnecting (or connecting) agent owns a live SSH session plus a tokio task yet is filtered out of the Open Connections panel (G2); a failed reconnect leaves a dead AgentConnection in the backend map (G6); non-recovered session output senders linger across reconnect (G7).
  • Race / ambiguous — connectionState has two writers (the optimistic store action and the agent-state-change event) that race and duplicate work (G4); the tab-strip dot reads a third source that no agent transition updates (G5); Disconnect overloads two intents — detach the transport vs. shut down remote sessions (G9).

This concept redesigns the lifecycle into an honest, cancellable, observable state machine. The core rule: the backend is the single writer of connectionState via the agent-state-change event, and every long-running phase (connect, deploy, setup, reconnect) carries a CancellationToken that the UI can fire. Every transport-owning state — including connecting and reconnecting — is visible and killable in the Open Connections panel.

Goals

  • Single-writer connectionState: backend event is authoritative; the store action never writes terminal states.
  • Cancellable connect, deploy, and setup; Cancel actually aborts the network work.
  • connecting and reconnecting agents visible in Open Connections with a Cancel/Kill action.
  • First-class Reconnect affordance on the agent header after reconnect exhaustion, carrying the stored last error.
  • Clear Disconnect (detach) vs. Shutdown (stop remote) distinction, with a detached-session count as feedback.
  • Zombie backend entries reaped; a manual Prune dead agents escape hatch.
  • Session/monitoring output keys reconciled against the freshly-listed session ids on reconnect.

Non-Goals

  • Changing the remote agent JSON-RPC wire protocol or the daemon frame format.
  • Redesigning agent deploy/update strategy (see the separate remote-agent-update-strategy concept).
  • Persistent-session semantics on the host (daemon survival is unchanged).
  • New backoff policy — the 10-attempt / 2ⁿ-capped-30s schedule stays as is.

UI Interface #

The redesign touches four user-facing surfaces: the Open Connections panel (now shows connecting/reconnecting agents with Cancel/Kill), the agent header in the sidebar (Cancel-connect, Reconnect-with-error, Disconnect-vs-Shutdown), the connect / deploy / setup progress (Cancel that aborts), and a Prune dead agents action. The mockups below use the real termiHub BEM classes and lucide icons; they are authoritative for layout.

General Handling #

Cancel mid-handshake (G1)

When the user fires Cancel on a connecting agent (sidebar or Open Connections), the frontend calls a new cancel_connect_agent command, which triggers the per-connect CancellationToken. The blocking connect_and_authenticate + initialize handshake is wrapped in a tokio::select! against the token; on cancel it drops the russh channel and the backend emits disconnected. Because the backend is the single writer of connectionState, the sidebar returns to disconnected only when the event lands — no optimistic clobber.

Reconnect exhaustion & manual retry (G3)

After 10 failed backoff attempts the io-task emits disconnected carrying the last error. The redesign stores that error on the RemoteAgentDefinition (lastError), so the agent header can render a Reconnect button with the reason as a tooltip. Reconnect just re-invokes the normal connect path (disconnected → connecting). No automatic infinite retry is added.

Zombie reap & Prune (G6)

On exhausted reconnect the io-task currently sets alive=false and returns without removing its AgentConnection from the manager map. The redesign has the task remove its own entry on terminal failure (via a self-reference to the manager), and adds a Prune dead agents action in Open Connections that sweeps any alive=false entries as a manual escape hatch. Routing is already safe (is_connected() returns false), so this is pure resource hygiene.

Detach vs. shutdown (G9)

Disconnect maps to disconnect_agent — it drops the transport and leaves persistent daemon-backed remote sessions running on the host (they re-list on the next connect). Shutdown maps to the existing shutdown_agent path, which stops remote sessions and reports detached_sessions; the UI shows that count as a success toast. The two intents are no longer collapsed into one control.

Session / monitoring key reconciliation on reconnect (G7)

The io-task's session_outputs / monitoring_outputs maps survive a reconnect so surviving sessions re-link by id. On a successful reconnect, the redesign reconciles those maps against the freshly-listed session ids and drops senders for sessions that did not recover — closing the minor leak of stale senders keyed by dead ids.

Spawning-tab feedback during a drop (G8)

A tab still mid-connection.create (no sessionId yet) is today skipped by the reconnecting overlay and lands ambiguously. The redesign routes such tabs to the waiting/retry path (terminalWaitingForAgent) on reconnecting rather than skipping them, so every agent tab gets honest feedback during a drop.

Single-writer & tab-dot agreement (G4, G5)

The store action connectRemoteAgent no longer writes connecting/connected/disconnected; it only kicks off the request and consumes returned capabilities. All terminal-state writes flow through the agent-state-change event (single writer). The agent-state-change handler additionally calls setRemoteState(tab.sessionId, state) for each agent tab so the compact tab-strip dot agrees with the terminal overlay. The redundant duplicate refreshes are de-duped.

Preliminary Implementation Details #

Grounded in the current code cited by the audit. Two cross-cutting rules anchor the whole redesign:

  • Single-writer connectionState: the backend agent-state-change event (emit_agent_state, agent_manager.rs:1319) becomes the only writer. connectRemoteAgent (appStore.ts:3002/3018/3032/3047) stops setting connecting/connected/disconnected and only kicks off the request + consumes capabilities. setAgentConnectionState (appStore.ts:3054) is driven solely by the event listener in TerminalView.tsx.
  • CancellationToken threading: mirror the existing pattern from commands/connection_path.rs (cancel_connection_path_probe, :206) and commands/session.rs (cancel_connecting, :60) — a per-operation token registry in the manager, keyed by agent id.

Suggested implementation order

Per the audit's summary: fix G4 (single writer) first — it collapses the race and de-dupes work and is a prerequisite for clean state transitions. Then G1 + G2 (cancellable + visible connect/reconnect), then G5 / G3 / G9 to make transitions observable and reversible, and finally G6–G8, G10 hygiene/cancellation.
