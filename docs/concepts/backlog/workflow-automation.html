Overview #

termiHub already ships macros (epic #1670): a macro is a named, stored sequence of recorded terminal input that is captured from the xterm input stream and replayed byte-for-byte into a session with a chosen timing mode. Macros are excellent for "type this again", but they are a single, opaque, record-and-replay stream: they cannot mix in other actions, they cannot invoke a script, and they only ever exist because a human recorded keystrokes.

The request in #1826 — verbatim, "I would like to have something stronger than simple macros, with standard workflows to trigger scripts" — is a different, larger feature. A workflow is an authored (not necessarily recorded), ordered list of heterogeneous steps that can send commands, run scripts, replay an existing macro, and pause between steps, optionally launched automatically by a trigger (manual, on-connect, or hotkey). Where a macro answers "replay what I typed", a workflow answers "run this standard procedure against this session."

This is a substantial subsystem (a step model, an execution engine, a step editor, a trigger registry, and a script-invocation seam with real security implications). Per the repo's AI-driven concept workflow it is captured here as a design-first concept for maintainer review before any implementation, rather than being force-fit into the macro epic.

Goals

  • A workflow = an ordered list of typed steps a user can add, remove, and reorder — authored in an editor, independent of raw macro capture.
  • Steps go beyond replaying keystrokes: send a command line, run a saved script (a sequence of commands) into the session, replay an existing macro, or wait.
  • A workflow can be triggered manually (palette / sidebar / button), on connect (when a session for a given connection opens), or by a hotkey.
  • Reuse the shipped macro plumbing: the same send_input injection seam, the same JSON-file storage pattern, the same sidebar/dialog UI idioms, the same palette/keybinding trigger surfaces.
  • Run against the currently active terminal with a visible progress and cancel affordance, exactly as macro playback does today.

Non-Goals

  • A general branching/scripting language. Workflows are linear ordered steps in v1. Conditionals, loops, and output-driven expect/send branching are explicitly deferred (see Open Questions).
  • Time-based scheduling / cron. Triggers in v1 are manual, on-connect, and hotkey only — not "run at 03:00".
  • Broadcast to many terminals at once. That depends on the broadcast-input plumbing (concept broadcast-input.html, #516) and is additive later.
  • Parameterization / template variables ({{hostname}} prompts) — a meaningful design surface deferred from #1670; noted here as a natural future extension, not built in v1.

Relation to the macro system #

Workflows are a layer on top of macros, not a replacement. The shipped macro system (src-tauri/src/macros/, src/components/MacroSidebar/, src/services/macroPlayback.ts) already provides the two hard seams a workflow engine needs, so the engine largely orchestrates existing pieces:

Concern Shipped macro seam reused by workflows
Inject text into a session TerminalRegistry.sendInputToTerminal → send_input command → SessionManager::send_input (line-ending normalization included). Every workflow step that sends anything goes through this one choke point — the same one macro playback uses.
Step scheduling with delays + cancel macroPlayback.ts already schedules an ordered list of { data, delayMs } steps with timing modes, a max-delay clamp, progress hooks, and cancellation. The workflow runner generalises this to a list of typed steps.
Persist user data macros/storage.rs (resolve_config_dir() + a versioned JSON store) is mirrored for workflows.json.
Manager UI + trigger surfaces MacroSidebar / MacroEditorDialog are the direct analog for WorkflowSidebar / WorkflowEditorDialog; the command palette (services/commands.ts) and keybinding registry (services/keybindings.ts) are the same trigger surfaces.

The key new idea a workflow adds is the run-macro step and the run-script step: a macro becomes one possible step inside a workflow, and a workflow can additionally carry authored command/script steps that were never recorded. This makes the shipped record/replay macro the primitive, and the workflow the composition over it.

Workflow model #

A Workflow mirrors the shipped Macro shape (id, name, description, tags, timestamps) but replaces the homogeneous MacroStep[] with a list of discriminated step types and adds a list of triggers.

Step types (v1)

Step type What it does Executes via
send-command Sends a single authored command line into the active session (with a trailing newline). The everyday building block — "run git status". send_input seam
run-script Sends a saved multi-line script (an authored sequence of commands) into the session, line by line, with an optional per-line delay. This is the core of "trigger scripts": the script's text is streamed into the remote shell — it is not executed locally. Optionally the script body can be referenced from an on-disk file. send_input seam
run-macro Replays an existing stored macro by id — reuses the macro's own timing mode. macroPlayback.ts
wait Pauses for a fixed number of milliseconds before the next step. scheduler timer
run-local-process guarded Spawns a local helper process/script (not on the remote host), reusing the app's existing local-process spawning. Security-sensitive; gated behind an explicit opt-in setting and a confirm-on-first-run — see Open Questions. May be deferred past v1. local process spawn
"Trigger scripts" is deliberately answered two ways: the safe, terminal-native path (run-script streams command text into the session over the same seam macros already use, so it works on any remote host) and the heavier local path (run-local-process, guarded). v1 should ship the first; the second wants a maintainer decision on the security model first.

Triggers (v1)

Trigger Fires when Binding surface
manual User runs it from the palette, the Workflow sidebar, or a toolbar button. always available
on-connect A session opens for a connection the trigger is bound to (e.g. "on every prod-web-1 connect, run the login-banner workflow"). session lifecycle → per-connection binding
hotkey A user-assigned keybinding is pressed while a session is focused. keybinding registry

Illustrative schema (TypeScript sketch)

type WorkflowStep =
  | { kind: "send-command"; command: string }
  | { kind: "run-script"; script: string; perLineDelayMs?: number; sourcePath?: string }
  | { kind: "run-macro"; macroId: string }
  | { kind: "wait"; delayMs: number }
  | { kind: "run-local-process"; program: string; args: string[] }; // guarded

type WorkflowTrigger =
  | { kind: "manual" }
  | { kind: "on-connect"; connectionIds: string[] }
  | { kind: "hotkey"; binding: string };

interface Workflow {
  id: string;
  name: string;
  description?: string;
  tags: string[];
  steps: WorkflowStep[];        // ordered; add / remove / reorder in the editor
  triggers: WorkflowTrigger[];
  createdAt: string;            // RFC 3339
  updatedAt: string;
}

General Handling #

Running a workflow

A workflow always runs against a target session — the active terminal, as with macro playback. The runner walks the ordered steps, dispatching each by kind through the appropriate seam, honouring inter-step and per-line delays (clamped by the same MAX_STEP_DELAY_MS guard macros use). Progress is surfaced in the status bar ("step 2/5"), and a single cancel stops the run between steps and aborts the in-flight step's remaining injections.

On-connect triggers

When a session finishes opening, the runner checks for workflows whose on-connect trigger names that connection and runs them against the fresh session. This is the "standard workflow" case: log in, set the prompt, tail a log — every time you connect to that host. Guard rails: on-connect workflows only fire for interactive shell sessions, run at most once per session open, and are individually toggleable so a failing workflow can be disabled without deleting it.

Script invocation, safely

The primary run-script path streams command text into the session over the existing send_input seam — it is exactly as privileged as the user typing those commands, runs on whatever host the session is on, and needs no new local execution capability. The heavier run-local-process step (spawning a local helper) is genuinely different: it executes code on the user's machine. It is therefore gated behind an explicit opt-in and a confirm-on-first-use, and may ship after v1. See Open Questions.

Editing vs recording

Workflows are authored, not recorded. The editor's step list is the source of truth: users add typed steps, paste or reference scripts, drop in an existing macro, and reorder freely. A convenience path — "promote a macro to a workflow" — seeds a new workflow with a single run-macro step so users can grow a recorded macro into a richer procedure.

Preliminary Implementation Details #

Based on the architecture at concept-creation time (post-#1670). The engine deliberately mirrors the shipped macro module so most seams already exist. This is a sequenced sub-epic, not one PR — the modules below share appStore.ts, a new backend module, and the session-open path, so they land in order (foundation → runner → editor UI → triggers → script step) to avoid merge collisions, exactly as #1670's children were sequenced.

Limitations & Open Questions #

  • Local script execution security model. Does v1 include run-local-process at all, or ship send-into-terminal only? If included: what gates it (global opt-in setting? per-workflow confirm? allowlist of programs?), and how is an imported workflow that carries a run-local-process step surfaced to the user before it can run? Recommend: v1 = terminal-native only; treat local process spawning as a separate, later, guarded issue.
  • Failure handling. A sent command can "fail" without the app knowing, because there is no output inspection in v1 (see below). "Stop-on-error" is therefore best-effort (injection failures only). Should a step be able to declare a "continue on error" flag?
  • Output-driven expect/send. True conditional workflows ("wait until the prompt returns, then send X") require reading session output — a large capability deferred from #1670. Explicitly out of scope for v1; a natural follow-up epic.
  • Parameterization. Template variables ({{hostname}}, prompt-on-run) would make workflows reusable across hosts. Deferred from #1670; would slot cleanly into the step model later.
  • Broadcast. Running a workflow against several sessions at once waits on broadcast-input (#516); the send_input seam is deliberately shared so this is additive.
  • Scheduling. Time/cron triggers are out of scope; on-connect covers the most-requested automatic case.
