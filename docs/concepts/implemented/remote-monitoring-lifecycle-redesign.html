Overview #

termiHub can show live CPU / memory / disk / load for a remote host in the status bar. The audit (docs/audits/remote-system-monitoring-state-machine.md) found that this is served by two independent state machines that share one global store slice: a legacy pull-based desktop-SSH path (monitoring_open / monitoring_fetch_stats, polled every 5 s from StatusBar.tsx) and a push-based session/agent path (session_monitoring_open → SshMonitoringProvider::subscribe, emitting session-monitoring-stats events every 2 s). Both feed the same five singleton fields (monitoringSessionId, monitoringHost, monitoringStats, monitoringLoading, monitoringError).

This design causes four concrete, user-visible failures:

  • Frozen stats shown as live (G1). When the SSH transport drops mid-stream, neither path surfaces an error state — the last-good CPU/Mem/Disk numbers keep rendering as if healthy. The user trusts stale metrics of a host that may be down.
  • No reconnect (G2). Once the transport dies, monitoring stays dead. The legacy path needs a manual Kill + re-pick; the session path may never recover without switching tabs away and back.
  • Collect can hang forever (G3). The legacy run_remote_command has no timeout, and the 5 s poll fires regardless of whether the previous fetch resolved — a half-dead remote stacks blocking tasks until the pool starves.
  • False "connected" (G4). SshMonitoringProvider::subscribe returns Ok(rx) before the SSH connect is attempted; a connect failure only logs warn!. The UI is told monitoring started and waits forever for a first stat.
  • Single-host-only singleton (G6). Only one host can be monitored app-wide; opening a second SSH tab silently evicts the first tab's monitoring, and Open Connections can only ever show one Monitoring row.

This concept redesigns the monitoring lifecycle around an explicit, observable state machine (Connecting → Live → Stale → Reconnecting → Offline) that both the status bar and Open Connections render, adds the missing user controls (Pause/Resume, Cancel-during-connecting, Retry, interval), and re-keys the store by session/host so multiple hosts can be monitored at once.

Goals

  • G1 — Stale sub-state: a mid-stream drop transitions to an explicit Stale (error-while-connected) state so the UI stops rendering frozen stats as live.
  • G2 — Reconnect: each collector loop performs bounded backoff reconnect after a transport error, surfacing Reconnecting to the UI.
  • G3 — Timeout & in-flight guard: wrap the collect in a timeout and skip a tick while a fetch is still in flight.
  • G4 — Real connect result: perform the initial connect inside subscribe() and return Err on failure so the open lands in the error branch.
  • G6 — Per-session keying: replace the global singleton with a Record<MonitorKey, MonitoringState> map (keyed by the owning session id) so multiple hosts monitor simultaneously and each appears in Open Connections with its own Kill.
  • Missing controls: Pause/Resume, Cancel-during-connecting, stale/offline indicator, per-host Kill, interval control.

Non-Goals

  • Changing what metrics are collected or the wire format of SystemStats / MONITORING_COMMAND.
  • Historical charting / retention of past samples (only the current + a short in-store cache remain).
  • The Windows/PowerShell remote monitoring command variants (out of scope; Linux /proc-based command unchanged).
  • G5/G7–G10 from the audit are addressed only where they fall out of this redesign; the remaining polish items stay tracked in the audit.

Design Decisions #

Decision 1 — Complete the MonitoringProvider migration (retire legacy)

Recommendation: complete the unified MonitoringProvider migration and retire the legacy pull path — do not fix both paths.

The legacy MonitoringSession is already documented as slated for removal (src-tauri/src/monitoring/session.rs:16-21: "will be removed once monitoring is migrated to use ConnectionType"). Fixing both paths would mean implementing G1–G4 twice — once in the frontend poll loop + run_remote_command, once in the provider task — and would preserve the interval mismatch (5 s poll vs 2 s push) and the overloaded store fields that caused the confusion in the first place. The push model is also structurally the right home for these fixes: reconnect/backoff/stale belong in one long-lived collector loop that owns the transport, not split between a React setInterval and a blocking IPC call.

Concretely, both the desktop-SSH and the session/agent surfaces route through a single provider abstraction:

  • The desktop-direct SSH tab (today's legacy path) gets a MonitoringProvider just like the session path already has — the difference becomes "which transport the provider owns", not "which state machine".
  • monitoring_open / monitoring_fetch_stats / monitoring_close and the 5 s setInterval + refreshMonitoring in StatusBar.tsx are removed. The frontend only ever subscribes and receives pushed stats + status events.
  • The provider loop owns the interval, the timeout, the in-flight guard, the stale-detection, and the reconnect backoff — so G1/G2/G3 live in one place and apply to every host.

Staging (below) keeps this reviewable: S1 lands the correctness fixes on the provider path (G4 real connect + G3 timeout/guard), S2 adds the observable Stale state (G1) plus the status-event channel and the UI indicator, S3 adds reconnect backoff (G2) and the per-host keying (G6) and finally deletes the legacy code.

Decision 2 — Per-host / per-session keying model

Recommendation: key monitoring state by a stable MonitorKey derived from the owning session/host, stored in a Record<MonitorKey, MonitoringEntry> on both the backend registry and the frontend store.

The key is the identity the rest of the app already uses to address a monitored target — one unified keying: MonitorKey = sessionId, the id of the owning terminal session, for every monitored tab. Both flows route through the same session-based MonitoringProvider:

  • Session-based (remote-session) tabs: the tab's session id is the key — matches the session-path store keying (monitoringStatsCache is keyed by sessionId).
  • Desktop-direct SSH tabs: also keyed by the owning terminal session id. The tab already owns a live SSH session, so its session id is available at keying time; it auto-connects through session_monitoring_open(sessionId) exactly like a remote-session tab. The human-readable host label rides alongside as host for display. (Earlier the connect-picker pull path keyed these by the user@host:port host key; #1232 retired that legacy path and re-routed desktop-direct SSH through the session-based provider, collapsing the two keyings into this single session-id keying — see the Sync Ledger.)

Each entry holds its own { status, stats, host, error, intervalMs, paused }. The status-bar widget renders the entry for the active tab; Open Connections renders all entries, each with its own Kill / Pause / Retry. Auto-connect no longer tears down the previous host on tab switch — switching tabs just changes which entry the status bar shows. The backend keeps a matching HashMap<MonitorKey, Subscription> so session_monitoring_close(key) kills exactly one host.

UI Interface #

Two surfaces change: the status-bar monitoring segment (per active tab) gains an explicit stale/offline/reconnecting indicator plus Pause/Resume and Cancel controls; the Open Connections modal lists every monitored host as its own row with per-host Pause/Retry/Kill. An interval control lives in the status-bar monitoring dropdown.

General Handling #

Subscribe returns the real connect result (G4)

SshMonitoringProvider::subscribe performs the initial connect_target before returning. On success it returns Ok(receiver) and hands the already-open session to the spawned loop; on failure it returns Err(CoreError), which propagates through start_session_monitoring → session_monitoring_open → connectMonitoring so the store lands in the Offline/error branch with a real message instead of a false "connected". The status bar shows Connecting until the connect resolves; a Cancel control aborts the in-flight connect via a CancellationToken (replacing today's uninterruptible ~75 s handshake).

Mid-stream drop → Stale (G1)

The collector loop counts consecutive collect failures. On the first failure after being Live, it emits a status: Stale event (carrying lastOkAt) but keeps the last stats so the UI can dim them. The status bar renders the Stale arm — warning color, dimmed numbers, "last N s ago" — so frozen data is never shown as live. If a subsequent collect succeeds, the loop emits status: Live and the numbers go bright again.

Reconnect with bounded backoff (G2)

After K consecutive failures the loop stops reusing the dead session, emits status: Reconnecting (with attempt number), and re-runs connect_target under exponential backoff (e.g. 1s, 2s, 4s… capped at 30s, max N attempts). A successful reconnect resumes collection and emits status: Live. If the backoff budget is exhausted, the loop emits status: Offline and idles, waiting for a user Retry (which restarts the connect from Connecting).

Timeout & in-flight guard (G3)

Every collect is wrapped in tokio::time::timeout (default 10 s); a timeout is treated as a collect failure (→ Stale/Reconnecting), never a hang. Because collection is a single sequential loop (not a fire-and-forget setInterval), the in-flight guard is structural: the loop never starts a new collect until the previous one has resolved or timed out, so a slow remote can never stack blocking tasks.

Multiple hosts monitored simultaneously (G6)

Each monitored host is an independent entry keyed by MonitorKey with its own provider subscription and its own state machine. Opening monitoring on a second tab does not evict the first — both loops run concurrently. The status bar shows the active tab's entry; Open Connections lists all entries. Killing one host leaves the others untouched. Pause on one host stops only that loop's collection.

Pause / Resume

Pause sets paused: true on the entry and signals the loop to stop collecting while keeping the transport open (state Paused). Resume clears it and the loop collects immediately. Pause is orthogonal to Stale/Offline — a paused monitor shows a neutral "paused" badge, not stale/live numbers.

Edge cases

  • Underlying terminal session exits. The owning tab's exit still tears down its monitor entry (today's disconnectMonitoring coupling), keyed so only that host's entry is removed.
  • First-sample CPU 0%. Until the second sample arrives the loop reports a "priming" flag; the status bar renders "—" for CPU rather than a misleading solid 0% (audit G10 — folds in cheaply here).
  • Open failure listener leak. With subscribe returning the real result (G4), the store attaches the stats/status listener only after a successful open, or tears it down in the catch — closing the G5 dangling-listener leak.
  • Retry after Offline clears any latched "auto-connect failed" guard so a recovered host can reconnect without a tab switch (audit G7).
