Overview #

termiHub already has a shared Modal primitive (a token-styled skin over Radix Dialog), but the Cancel / confirm-action shape built on top of it is hand-rolled at every call site. Each one re-declares the same footer: a secondary Cancel on the left, a primary/danger confirm on the right, wires onOpenChange back to a cancel handler, and hand-assigns -cancel / -confirm test ids. Because the shape is copy-pasted, the details drift — button order, which variant the confirm uses, whether ESC/scrim maps to cancel, and the test-id naming are all slightly different from one modal to the next.

This concept introduces a single ConfirmDialog primitive in src/components/ui/ that owns the confirm/warn/danger modal shape once: the footer layout, the button order and variants, the cancel wiring, the async confirm lifecycle, and a consistent test-id scheme derived from one base id. Call sites pass intent (title, message, variant, confirmLabel, onConfirm/onCancel) instead of re-assembling the shell. It also adds an optional "don't warn again" affordance so warn-style dialogs can offer suppression without each panel re-inventing it (a natural fit for the Port Scanner large-scan warning from #1348).

Goals

  • One ConfirmDialog primitive that composes Modal + Button — never a new dialog shell or __btn.
  • Consistent footer: Cancel (secondary, left) + confirm (right), with the confirm variant driven by a single variant prop (default / warn / danger).
  • One base data-testid deriving stable -cancel / -confirm hooks, so tests stop hard-coding per-site strings.
  • Async confirm support (the confirm Button drives its idle → pending → success/error lifecycle) so long-running confirms give feedback per the design system's "every action gives feedback" rule.
  • An optional don't warn again checkbox for warn-style dialogs, with the suppression decision surfaced to the caller (the caller owns persistence).
  • Migrate the three known call sites onto it (see the migration table below).

Non-Goals

  • Not a replacement for Modal. Content-rich modals (forms, multi-field editors) keep using Modal directly; ConfirmDialog is the confirm shape on top of it.
  • No global "confirm()" imperative API in this pass — ConfirmDialog stays a controlled React component (open + handlers). An imperative useConfirm() helper is noted as possible future work, not built here.
  • No new persistence subsystem for "don't warn again" — the primitive only reports the checkbox state; where a preference is stored is the call site's concern.

UI Interface #

Visually a ConfirmDialog is a Modal: the same overlay scrim + blur, the same centered card with a title row (and the built-in close button), a body, and a footer of Buttons. The only fixed rules it adds are footer composition and the variant-driven accent. The mockups below use the real app chrome classes (.menu, .menu__title, .menu__row, .menu__footer, .btn) to model the dialog card as it renders over the app.

General Handling #

Anatomy & fixed rules

  • Body — a caller passes either a plain message (string / node, the common case) or arbitrary children (a body slot for a form, as WoL needs). If both are given, children wins and message is ignored.
  • Footer — always exactly two Buttons in a fixed order: Cancel (secondary) then confirm. The confirm variant follows variant: default/warn → primary, danger → danger. Labels default to "Cancel" / "Confirm" and are overridable via cancelLabel / confirmLabel.
  • Cancel wiring — onCancel fires for every non-confirm exit: the Cancel button, the close , ESC, and scrim click (all funnelled through Modal.onOpenChange(false)). Call sites stop re-deriving this.
  • Test ids — one base data-testid (e.g. confirm-delete-dialog) is forwarded to the Modal content; the primitive derives <base>-cancel and <base>-confirm on the two buttons. Existing tests that query port-scan-warn-confirm, wol-save-cancel, etc. keep working unchanged.

Async confirm & disabled confirm

  • If onConfirm returns a Promise, the confirm Button enters its pending state (spinner, disabled) and flashes success — no silent action. The dialog closes when the promise resolves (caller decides via its own state, or the primitive can auto-close on resolve — see Implementation). On rejection the Button returns to idle and surfaces the error (confirmErrorToast, defaulting to Button's own errorToast=true; WoL passes false to report the error itself).
  • confirmDisabled gates the confirm button (WoL keeps it disabled until the device name is non-empty and the MAC is valid).

"Don't warn again" suppression

Warn-style dialogs (like the large-scan warning) can opt into a suppression checkbox by passing a dontWarnAgain descriptor (label + controlled checked/onChange, or an uncontrolled "report on confirm" form). The primitive renders the checkbox row above the footer and includes the final checkbox state in the confirm callback. The call site owns persistence and the gate: before opening the dialog it checks its stored preference; if the user previously chose "don't warn again", the action runs immediately and the dialog never opens. See the suppression flowchart below.

Edge cases

  • Double-confirm — while an async confirm is pending, the confirm Button is disabled (Button lifecycle), so a second click can't re-fire the action.
  • Cancel during pending — Cancel/ESC remain live during a pending confirm; whether that aborts is caller-defined (the primitive just calls onCancel). Default guidance: keep Cancel enabled but let the in-flight action settle.
  • Body-slot forms — Enter-to-confirm inside a form field is the caller's responsibility (as WoL already does), since only the caller knows when the form is valid.

Preliminary Implementation Details #

Built entirely from existing primitives — Modal (src/components/ui/Modal.tsx) and Button (src/components/ui/Button.tsx). No new dependency, no new CSS shell; only token'd classes already in ui.css. Exported from src/components/ui/index.ts alongside the other primitives.

Proposed prop interface

// As shipped in src/components/ui/ConfirmDialog.tsx.

export interface ConfirmDontAskAgain {
  /** Current checked state. */
  checked: boolean;
  /** Called with the next value when the user ticks the checkbox. */
  onChange: (checked: boolean) => void;
  /** Checkbox label. Defaults to "Don't ask again". */
  label?: string;
  /** Test hook forwarded to the checkbox. */
  "data-testid"?: string;
}

export interface ConfirmDialogProps {
  /** Controlled open state. */
  open: boolean;
  /** Heading text. */
  title: React.ReactNode;
  /** Optional description for screen readers (visually hidden). */
  description?: string;
  /** Plain body text (the common case). May be combined with `children`. */
  message?: React.ReactNode;
  /** Body slot for richer content (forms, lists) — what lets the WoL save
      modal compose the primitive instead of a hand-rolled Modal. */
  children?: React.ReactNode;
  /** Confirm button label. Defaults to "Confirm". */
  confirmLabel?: string;
  /** Cancel button label. Defaults to "Cancel". */
  cancelLabel?: string;
  /** Confirm-button variant. Defaults to "danger" for destructive actions. */
  confirmVariant?: ButtonVariant;
  /** Confirm handler. Returning a Promise drives the Button async lifecycle. */
  onConfirm: () => void | Promise<void>;
  /** Called for every non-confirm exit (Cancel / ESC / scrim / X). */
  onCancel: () => void;
  /** Disable the confirm button (e.g. invalid form). */
  confirmDisabled?: boolean;
  /** Forwarded to the confirm Button's `errorToast`. Defaults to true. */
  confirmErrorToast?: boolean;
  /** Opt-in "don't ask again" checkbox. */
  dontAskAgain?: ConfirmDontAskAgain;
  /** Base for the action-button test ids (defaults to "confirm-dialog"),
      deriving `${testIdBase}-cancel` / `-confirm` / `-dont-ask-again`. */
  testIdBase?: string;
  /** Test hook forwarded to the modal content. */
  "data-testid"?: string;
}

The WoL case is deliberately the weakest fit — it is a form, not a pure confirm — so it only consolidates the footer + cancel wiring + test-id scheme via the children slot. If the body slot proves awkward there in implementation, WoL may stay on raw Modal; the two pure-confirm sites (ConfirmDeleteDialog, Port Scanner) are the primary win. That trade-off is a decision for the implementation PR, which must match this concept (concept is authoritative).
