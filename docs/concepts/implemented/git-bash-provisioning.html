Guided Git Bash Installation on Windows

Implemented detect-and-guide, no bundling GitHub Issue: #519 Delivered by #1671, #1672 docs/concepts/implemented/git-bash-provisioning.html

Single-file concept (AI-driven concept workflow). Prose, diagrams, mockups, and the concept↔code reconciliation ledger all live in this one HTML file. The concept is the source of truth; run /sync-concept git-bash-provisioning to reconcile it with the implementation.

Supersedes the retired Embedded Unix Command Environment concept (#519, since removed). Instead of bundling BusyBox-w32 + standalone binaries with the Windows build, termiHub detects Git for Windows and, when it is missing, guides the user through installing it — then uses the installed Git Bash as the Unix-shell + coreutils provider. This mirrors the already-shipped X Server Provisioning pattern (detect-or-guide VcXsrv/XQuartz), reusing its consent/progress UX and the guideTerminalInstall mechanism.

Overview #

Windows users often want a Unix-style local shell — bash with grep, sed, awk, curl, ssh, tar, git, and the rest. Today termiHub offers Git Bash as a local-shell option, but only when it happens to be installed — and detection checks just two hardcoded paths (C:\Program Files\Git\bin\bash.exe and the (x86) tree). A user who has never installed Git for Windows sees no bash option and no guidance; a user who installed it via winget, scoop, or into a user-scope directory is missed entirely.

This concept adds a subsystem that ensures a usable Git Bash exists when the user asks for a Unix shell: it detects Git for Windows robustly, and when it is absent it guides a consent-based install (winget → official installer → portable fallback), then re-detects and offers Git Bash — with no manual PATH surgery and no app restart. The installed Git Bash is the Unix-tools provider.

termiHub needs none of these binaries for its own features. SSH and SFTP run on the russh Rust library (not an ssh.exe); OSC 7 CWD tracking (the file browser) is emitted by the shell prompt and already works with Git Bash (shell.rs treats gitbash as an OSC 7 shell). The embedded tools were only ever a user convenience. Git for Windows already provides the whole list — it is an MSYS2 environment shipping bash, coreutils, curl, OpenSSH, tar/gzip/xz, git, vim, and less from one well-maintained installer — and termiHub already knows how to launch it (resolve_git_bash). Bundling is a heavy, recurring liability (a hosted update manifest, BusyBox-w32's well-known antivirus false positives, and owning CVE response for bundled curl/OpenSSH). Guiding an install pushes all of that onto Git for Windows. Full analysis: #519.

Goals

  • Make a working Unix shell (bash + coreutils + curl/ssh/tar/git/…) available on Windows with guided, consent-based setup — no manual install on the common path, no bundling.
  • Harden Git Bash detection beyond the two hardcoded Program Files paths — registry, winget/scoop, user-scope, and PATH-derived locations (#1671).
  • When Git Bash is absent, guide its install via winget (winget install -e --id Git.Git), with an official-installer link and a portable-Git fallback (#1672).
  • Re-detect Git Bash after the install completes and offer it without an app restart.
  • Frame installed Git Bash as the answer to "I want grep/curl/ssh on Windows" — the Unix-tools provider — in the shell picker and Settings.
  • Reuse the X-server guided-install mechanism — the same consent/progress UX and the existing guideTerminalInstall / openLocalCommandTab helpers — rather than inventing a new install surface.

Non-Goals

  • Bundling or embedding any Unix environment (BusyBox/MSYS2/Cygwin) — that is the retired #519 concept this one supersedes.
  • A package/plugin manager for installing extra Unix tools — that is #521, out of scope here.
  • macOS or Linux (native Unix tools already exist; this subsystem is Windows-only).
  • Replacing WSL — the dedicated WSL connection type is unchanged and remains the answer for running real Linux binaries.
  • Auto-installing MSYS2 or Cygwin — Git Bash is the single supported guided target; a user who prefers another environment can still point a custom shell at it.
  • Managing Git for Windows' version or updates — Git/winget owns that (a strict win over bundling, which would put the update treadmill on termiHub).

UI Interface #

Git Bash already appears in the local-shell picker (connection editor and Settings → General → Default Shell) when detected. This concept adds two things: hardened detection so it shows up whenever Git for Windows is installed anywhere, and — when it is not installed — a "Git Bash (set up…)" entry that launches a guided, consent-based install. Nothing is downloaded or installed without explicit consent, exactly as with the X server.

General Handling #

  • Detection is layered. Beyond the two hardcoded Program Files paths, resolve Git for Windows from: the registry (HKLM\SOFTWARE\GitForWindows / HKCU\… InstallPath), the user-scope install (%LOCALAPPDATA%\Programs\Git), winget/scoop locations, and a PATH-derived lookup (locate git.exe, derive ..\bin\bash.exe). First hit wins; the hardcoded paths remain as final fallbacks. One resolved path feeds both detect_available_shells() and resolve_git_bash() (single source of truth) — #1671.
  • Guidance is lazy & consent-gated. Nothing is installed until the user opens/selects a Unix (bash) shell and confirms the prompt. A user who never wants bash never installs anything — the picker just doesn't show a "set up…" row unless asked.
  • Install strategy (in order): winget (winget install -e --id Git.Git --accept-package-agreements --accept-source-agreements) → official installer link (git-scm.com/download/win) → portable Git (same link; detected afterwards via PATH). winget-absent is a guided terminal install, not a failure.
  • Re-detect after install, no restart. When the install completes (winget command returns, or the guided terminal tab's command finishes), re-run detection and, if found, select Git Bash for the pending connection.
  • Reuse, don't reinvent. The guided-terminal path reuses guideTerminalInstall / openLocalCommandTab (built for the macOS Homebrew→XQuartz flow, #1309/#1312); the consent/progress UX mirrors the X-server prompt.
  • Failure is actionable, never silent. If winget errors, surface its output verbatim with a retry and the manual link. If the user declines, the custom-shell and WSL options remain — termiHub never leaves the user staring at a missing shell with no path forward.
  • Windows-only. On macOS/Linux this subsystem is inert — native shells are detected as today.

Git installed via winget/scoop or user-scope (not in Program Files) Registry / user-scope / PATH probe finds it; appears as a normal Git Bash row (#1671)
Git in a custom directory Registry InstallPath or PATH-derived lookup resolves it
Multiple Git installs Prefer the registry InstallPath; the one resolved path is used consistently
winget (App Installer) absent Guided terminal install + git-scm.com manual link — never silent

Preliminary Implementation Details #

Based on the current architecture at concept-creation time; the codebase may evolve before implementation. The work splits cleanly into two issues: detection hardening (#1671) and the detect-and-guide install flow (#1672), the second building on the first.

Detection (#1671)

Today detect_available_shells() pushes gitbash only if one of the two GIT_BASH_PATHS exists, and resolve_git_bash() launches from the same list. Replace both with a shared resolver that probes, in order: the Git for Windows registry key (HKLM\SOFTWARE\GitForWindows / HKCU\Software\GitForWindows, value InstallPath → \bin\bash.exe); the user-scope install (%LOCALAPPDATA%\Programs\Git\bin\bash.exe); a PATH-derived lookup (find git.exe, derive its sibling ..\bin\bash.exe); then the existing hardcoded paths. Verify the candidate with bash.exe --version before offering it. Keep the change Windows-gated; Unix detection is untouched.

Guided install (#1672)

Mirror the X-server acquisition path. When the user picks "Git Bash — set up…", check for winget; if present, run winget install -e --id Git.Git --accept-package-agreements --accept-source-agreements and stream progress via events; if absent, call guideTerminalInstall(command, "Install Git for Windows") to open a terminal tab pre-loaded with the command, plus a git-scm.com/download/win deep link. On completion, re-run detection (#1671) and select Git Bash for the pending connection. The consent/progress dialog composes from the shared src/components/ui/ primitives.

Licensing

termiHub does not host or redistribute Git for Windows — winget or the user fetches it, and termiHub only runs bash.exe as a separate process (no linking). So Git for Windows' GPL-2.0 terms impose no redistribution obligation on termiHub here; the posture is the standard "we launch a package-manager-installed program," identical to the VcXsrv/winget resolution reached for the X server (#1076/#1056/#1318).

Implementation order

  1. Detection hardening (shell.rs, #1671) — land first; independently useful and the foundation for reliable post-install re-detection.
  2. Backend commands + events (new git_bash.rs, #1672) — git_bash_status / git_bash_install, modeled on the X-server commands.
  3. Frontend consent/progress UI (#1672) — "set up…" row, consent prompt, progress, winget-absent fallback via guideTerminalInstall; re-detect + select.
  4. Docs + manual test steps (guided install is not exercised by per-PR CI on Windows).
