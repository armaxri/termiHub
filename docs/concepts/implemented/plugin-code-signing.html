Overview #

The plugin system ships a fully working install/permission gate, but its very first decision node is a promise the code cannot yet keep. The security flowchart in plugin-system.html opens with “Signature valid?”, then falls through the “No / Unsigned” arm for every package because termiHub has no signing substrate — no keys, no package signature format, no verification chain. #2001 (PR #2016) built only the untrusted-source warning path: core/src/plugin/security.rs::assess_trust unconditionally returns TrustLevel::Untrusted, and PluginManager::install requires an explicit accept_untrusted flag before extraction. Cryptographic verification was left, by name, to this issue.

This matters more for plugins than for most download flows: a native backend plugin is a dynamic library that runs in the host process with the app's own privileges (documented in security.rs). There is no OS sandbox around it, so “where did this .termihub-plugin come from, and has it been altered since?” is the only line of defence a user has before that code executes. This concept designs that line: a signing scheme, an on-disk signature format that stays inside the existing single-file package, a trust-anchoring model, and the evolution of assess_trust into a real verified-identity check that changes the install gate.

Goals

  • A plugin author can sign a .termihub-plugin package with a keypair they control, using a first-party tool.
  • The host can verify, offline, that a package (a) was signed by a specific key and (b) has not been altered since — covering the entire payload, not just the manifest.
  • assess_trust reports a real trust level with a verified publisher identity; the install gate stops warning about packages from trusted publishers and hard-blocks packages whose signature does not verify (tampered).
  • The user can build and manage a trust store of publisher keys — first use establishes trust (with an explicit, fingerprint-visible confirmation), later updates from the same key verify silently.
  • The package stays a single self-contained file; nothing about distribution changes for the user beyond a green badge.

Non-Goals

  • Sandboxing / execution isolation. Signing proves provenance and integrity; it does not confine a signed plugin's syscalls. The in-process direct-syscall bypass documented in security.rs (and the plugin-system sync ledger, row 2) is out of scope and orthogonal.
  • A central certificate authority / online revocation. No termiHub-operated registry that counter-signs publishers, and no OCSP/CRL network calls, in v1. A future registry tier is sketched but deferred (see Key Distribution).
  • Reusing the OS code-signing chains (Authenticode / Apple Developer ID). Those sign the app (see macos-code-signing-notarization.html); plugins are cross-platform data files installed after the app ships, so they need their own portable, in-package scheme.
  • Signing frontend-JS or theme-only plugins differently from backend plugins — one scheme covers all package kinds.

Signing Scheme — Options & Recommendation #

The design axis is what gets signed and where the signature lives. Four candidates, evaluated against the two properties the package format already commits to — it is a single .termihub-plugin file (core/src/plugin/mod.rs), and it is re-zipped deterministically by the packer (pack.rs, which then round-trip-validates its own output).

Option Mechanism Assessment
A. Detached sibling .sig Ship <pkg>.termihub-plugin.sig next to the package; verify the file bytes against it. Rejected. Breaks the single-file property. Worse, a missing sibling is indistinguishable from “never signed”, so the common case (author forgot to attach it) silently downgrades to unsigned rather than failing loudly.
B. Sign the raw ZIP bytes Compute a signature over the whole archive's bytes and append it as a trailer after the ZIP end-of-central-directory record. Rejected. Brittle: the signature covers an exact byte layout, so any normalization or re-pack (exactly what pack.rs does) invalidates it, and reading requires bespoke trailer parsing rather than the ZIP reader the validator already uses.
C. Embedded signature over a content digest (recommended) Add a signature.json ZIP entry carrying a per-entry SHA-256 digest map of every other entry plus one signature over a canonical form of that map. JAR / Android APK-v1 shape. Recommended. Single self-contained file; robust to deterministic re-zipping because it signs content, not byte offsets; verifiable through the exact ZipArchive read path validate_package already uses; the signature entry naturally excludes itself.
D. Sign only manifest.json Signature covers a hash of the manifest alone. Rejected. Leaves the executable payload unprotected — an attacker swaps backend/lib*.so and the manifest still verifies. That is exactly the artifact that runs in-process with app privileges, so it is the one thing that must be covered.

Recommendation: Option C, an embedded signature.json entry whose signature covers a canonical digest of the full package contents. It is the only option that preserves the format's single-file identity, survives the packer's own deterministic re-zip, and protects the whole payload rather than just the metadata.

Algorithm choice

  • Signature: Ed25519. 32-byte public keys and 64-byte signatures, no curve/parameter selection to get wrong, fast to verify, and well-served by the mature ed25519-dalek crate. A short public key is what makes a human-readable fingerprint and a small trust-store row practical.
  • Per-entry digest: SHA-256. Already the integrity primitive used by the agent-update path (remote-agent-update-strategy.html), so it keeps one hash family across the project.
  • Key fingerprint / keyId: sha256(publicKey-bytes), rendered as sha256: + lowercase hex, and shown to users truncated (e.g. sha256:ab12 cd34 … 9f0e). This is the identity the trust store keys on.

On-Disk Signature Format #

A signed package is an ordinary .termihub-plugin ZIP with one added well-known root entry, signature.json (a new constant SIGNATURE_FILE_NAME, sitting beside the existing MANIFEST_FILE_NAME). An unsigned package simply omits it — so the format is backward-compatible and the presence of the entry is itself the “is this signed?” signal. 

my-plugin.termihub-plugin (ZIP)
├── manifest.json           # required — unchanged
├── signature.json          # NEW — present iff the package is signed
├── backend/…               # covered by the digest map
├── frontend/…              # covered by the digest map
├── themes/…                # covered by the digest map
└── README.md               # covered by the digest map

The signature.json body:

{
  "formatVersion": 1,
  "algorithm": "ed25519",
  "digestAlgorithm": "sha256",
  "signedAt": "2026-07-26T12:00:00Z",
  "publicKey": "<base64 of the 32-byte Ed25519 public key>",
  "keyId": "sha256:ab12cd34…9f0e",
  "files": {
    "manifest.json":            "sha256:9f2b…",
    "backend/libk8s_exec.so":   "sha256:04ac…",
    "README.md":                "sha256:1188…"
  },
  "signature": "<base64 of the Ed25519 signature over the signing payload>"
}

What the signature actually covers

The signature is not taken over the JSON text (whitespace and key order would make that non-deterministic). It is taken over a canonical signing payload constructed deterministically from the fields, so the verifier can rebuild the exact bytes regardless of how the JSON was serialized: 

signing_payload =
    "termihub-plugin-signature/v1\n"        // domain-separation tag
  + "algorithm:ed25519\n"
  + "keyId:" + keyId + "\n"
  + for each (name, digest) in files, sorted by name:
        name + "\0" + digest + "\n"
  • The leading domain-separation tag ensures a signature made for one purpose can never be replayed as another (a Plugin signature is not a valid anything-else signature).
  • The files map lists every entry except signature.json itself. Verification recomputes each entry's SHA-256 and requires an exact set match: a digest mismatch, a listed-but-missing entry, or an unlisted entry present in the archive all fail. The last case is what stops an attacker from appending an extra file the signer never saw.
  • publicKey is embedded so verification is self-contained; it is not trusted by being embedded — keyId must equal sha256(publicKey), and trust is decided separately against the trust store (next section).

Size guard. The existing 50 MB MAX_PACKAGE_SIZE_BYTES pre-open check is unchanged; signature.json is tiny and adds nothing meaningful. Verification only reads entries that already had to be extracted, so it does not weaken the “reject before decompressing” property.

Key Distribution & Trust Anchoring #

A valid signature only proves “the holder of key K produced this package, unaltered”. It says nothing about whether K should be trusted. That decision is the trust store's job.

Who signs, and how a key is born

  • A plugin author generates an Ed25519 keypair once, with a new first-party tool termihub-plugin-keygen. The private key stays with the author (a file they guard, or the OS keychain); the public key and a chosen human label (“ACME Terminals”) are what they publish — on the plugin's release page, repository, or website — alongside the fingerprint.
  • Signing is a distinct step from packing: termihub-plugin-pack gains a --sign <private-key> flag (equivalently a standalone termihub-plugin-sign <pkg>) that computes the digest map and writes signature.json into an already-built package.

How the host learns to trust a key

Three anchoring models were considered:

Model Decision
Central registry CA — termiHub operates a root key that counter-signs vetted publishers; the root ships in-app. Deferred. Strongest trust, but needs operated infrastructure, vetting policy, and a revocation story. Sketched as a future tier; not v1.
Trust-on-first-use (TOFU) + explicit pinning — first install of a signed-but-unknown key shows its fingerprint and asks the user to trust it; accepting pins the key. Recommended for v1. No infrastructure, works offline, and matches a pattern already in the codebase — the remote-desktop host-key trust store and SSH host-key acceptance both work this way.
Bundled first-party keys — a small set of termiHub-official publisher public keys ships pre-trusted in the app. Adopt alongside TOFU. Lets official/example plugins verify as Verified out of the box, without the user pinning anything.

Recommendation: TOFU + manual pinning as the primary anchor, seeded with a bundled set of first-party keys, leaving room for an optional registry-CA tier later. The crucial UX rule: establishing trust is always an explicit, fingerprint-visible act — termiHub never silently trusts a key it has not seen.

The trust store

A host-side JSON file, <app-data>/plugins/trust-store.json, is a list of trusted publisher keys. It reuses the app-data + portable-mode redirection every other plugin file already respects. 

{
  "publishers": [
    {
      "keyId":     "sha256:ab12cd34…9f0e",
      "publicKey": "<base64 32-byte key>",
      "label":     "ACME Terminals",
      "source":    "user-pinned",     // or "bundled"
      "addedAt":   "2026-07-26T12:04:00Z"
    }
  ]
}

Managed from Settings → Plugins → Trusted Publishers: view pinned keys, revoke (remove) one — after which packages from that key drop back to Signed (unknown) — and see which are bundled first-party keys (not removable). Removing trust does not uninstall already-installed plugins; it only affects future install and update gates.

General Handling #

Author journey — signing a package

  1. Once: termihub-plugin-keygen --out acme.key --label "ACME Terminals" → prints the public key + fingerprint to publish.
  2. Build & pack as today (scripts/package-plugin.* → termihub-plugin-pack).
  3. Sign: termihub-plugin-pack --sign acme.key … (or termihub-plugin-sign acme.key my-plugin-1.0.0.termihub-plugin) writes signature.json into the package.
  4. Distribute the single signed file; publish the fingerprint next to it.

User journey — installing

  • Trusted key → green “Verified publisher” banner, no risk gate; straight to the permission prompt.
  • Signed, unknown key → amber banner with the fingerprint and a Trust this publisher checkbox. The user compares the shown fingerprint against the publisher's site; accepting pins the key for next time.
  • Unsigned → the existing untrusted-source acknowledgement (unchanged).
  • Invalid signature → hard block, no override — the difference between “unknown provenance” and “provenance was tampered with”.

Update handling

When a plugin is re-installed over an existing one (the manager already replaces by id), the signing key is re-checked. If a new version arrives signed by a different key than the pinned one, it is treated as Signed-unknown, not Verified — a key rotation the user must re-confirm. This surfaces publisher-key changes rather than trusting a silent swap.

Edge cases

  • Extra unsigned file in the archive — an entry not present in the files digest map fails verification (set-exact match), so a signed package cannot be “extended” after signing.
  • signature.json present but malformed (bad base64, wrong formatVersion, keyId ≠ hash of publicKey) → treated as Tampered/blocked, not as unsigned — a broken signature is never downgraded to “no signature”.
  • Future formatVersion the host does not understand → block with an actionable “update termiHub to verify this package” message rather than silently ignoring the signature.
  • Bundled first-party key is always present in the trust store; it cannot be revoked (only user-pinned keys can), so official plugins never regress to a warning.

Preliminary Implementation Details #

Based on the plugin code as it stands after #2016 (commit range of the plugin epic). The signing layer is additive: it extends security.rs and the package read/write paths, and adds a trust-store module and a keygen/sign binary.

File Change
core/src/plugin/signature.rs New — signature.json model (PackageSignature), the canonical signing-payload builder, per-entry digest computation, SIGNATURE_FILE_NAME, and the pure Ed25519 verify() / sign() primitives. Host-agnostic, fully unit-testable (no I/O beyond a passed-in ZIP reader).
core/src/plugin/trust_store.rs New — TrustStore load/save over <app-data>/plugins/trust-store.json, is_trusted(keyId), pin(key, label), revoke(keyId), and the bundled first-party key seed.
core/src/plugin/security.rs Modify — extend TrustLevel with Tampered, Signed { key_id }, Verified { publisher }; make assess_trust actually open the package, run signature::verify, and consult the trust store; add TrustAssessment::is_blocked() and refine requires_acceptance() so only Untrusted/Signed require the gate and Verified does not.
core/src/plugin/package.rs Modify — expose a helper to enumerate entry digests over the already-open ZipArchive, shared by the verifier; keep the size-first ordering intact.
core/src/plugin/pack.rs Modify — optional signing pass: after the round-trip validate, compute the digest map and write signature.json when a signing key is supplied. Unsigned packing is unchanged.
core/src/plugin/manager.rs Modify — install consults the richer TrustAssessment: block on Tampered, honour a new trust_publisher argument that pins the key on a Signed install, keep accept_untrusted for the unsigned path. Thread the TrustStore in.
core/src/bin/plugin_keygen.rs, core/src/bin/plugin_sign.rs New — CLI tools (behind the plugin feature, like plugin_pack) to generate a keypair and to sign a built package.
core/Cargo.toml Modify — add ed25519-dalek (and a CSPRNG for keygen) under the plugin feature; SHA-256 is already available via the existing hashing dependency.
src-tauri/src/commands/plugin.rs, src/components/Plugins/* Modify — surface the trust level in the install dialog's provenance banner (four states), thread the Trust this publisher checkbox into install, and add the Trusted Publishers settings group (list / pin / revoke).
docs/plugin-authoring.md, scripts/package-plugin.* Modify — document keygen/signing and add an optional signing step to the packaging helpers.

Testing notes

  • signature.rs unit tests: sign→verify round trip; digest-mismatch, missing-entry, and extra-entry rejection; bad-signature rejection; keyId ≠ hash rejection; unknown formatVersion rejection.
  • security.rs: assess_trust maps each package shape to the right TrustLevel; Verified vs Signed keyed on trust-store membership; Tampered blocks and cannot be overridden.
  • trust_store.rs: pin/revoke persistence, bundled-key immutability, portable-mode redirection.
  • manager.rs: signed-trusted installs without acceptance; signed-unknown pins on trust; tampered refused; unsigned still needs accept_untrusted.

Implementation Status #

Implemented (#2036). The signing substrate is built end-to-end and matches this design: Ed25519 package signatures over a per-entry SHA-256 digest map, a publisher trust store with trust-on-first-use pinning, an assess_trust that opens and verifies the package, a four-state install gate, keygen/sign tooling, and the frontend provenance banner + Trusted Publishers settings.

One intentional deferral: the bundled first-party key seed (trust_store.rs::BUNDLED_PUBLISHERS) ships empty. The mechanism is fully wired — a non-empty list makes those publishers verify as Verified out of the box — but no key is embedded, by deliberate maintainer decision (#2041, now labelled future): a first-party trust anchor buys nothing until an actual plugin ecosystem exists, while minting and holding a root publisher key now adds secret-custody burden. This is a deferral with no active plan, not a gap awaiting a fix. Enabling it later is a key ceremony plus embedding the public key — no architecture change — and TOFU pinning fully covers real installs meanwhile.
