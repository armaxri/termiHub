Overview #

Add built-in graphical remote-desktop sessions to termiHub for both VNC (RFB — Remote Framebuffer) and RDP (Remote Desktop Protocol). A remote desktop renders inside a termiHub tab on a <canvas> element, alongside terminal tabs, participating in the tab bar, drag-and-drop, and split views like any other connection.

Motivation. RDP (Windows) and VNC (Linux/macOS/Unix) are the two most common remote-desktop protocols and both ship in MobaXterm. Adding them makes termiHub a viable MobaXterm replacement for administrators who keep terminals and remote desktops in one window.

The problem this concept exists to solve — drift. The wire protocols are completely different (RFB vs. the RDP protocol) so the backends legitimately differ, and that is fine. But the two original concepts were written separately and already diverged on the one axis that matters most to the user — how a frame reaches the screen: the VNC concept rendered with the noVNC JavaScript client over a WebSocket-to-TCP proxy (decode in JS), while the RDP concept decoded with IronRDP natively in Rust and pushed frames to a canvas (decode in Rust). Two rendering transports means two canvases, two input-capture paths, two clipboard paths, two toolbars, two resize handlers — they will drift and won't feel the same. This concept fixes that by designing one shared user-facing/session layer that both protocol backends plug into, mirroring how #1335 introduced a protocol-agnostic file-browser session layer that FTP and SFTP both use.

Goals

  • Identical UX across protocols. Connecting, the connection editor, the session tab/toolbar, credentials, clipboard, resize/scaling, fullscreen, disconnect/reconnect, and the Open Connections entry must feel the same whether the session is VNC or RDP.
  • One shared abstraction from the start. A single protocol-agnostic graphical-session layer (frontend + session management + a Rust GraphicalBackend trait). VNC and RDP are thin backend adapters behind it.
  • Inline in a tab. Renders in a <canvas>, never an external window; full tab/split-view integration.
  • Reuse existing infrastructure. Schema-driven connection editor (DynamicForm), the credential store, the connection sidebar, and the SSH tunnel infrastructure — not new parallel systems.
  • Cross-platform on Windows, macOS, and Linux (pure-Rust decoders).

Non-Goals (v1)

  • Multi-monitor remote sessions (single monitor only).
  • RD Gateway / proxy and VNC repeaters (direct connections, or via existing SSH tunnel).
  • Smart-card / certificate authentication (password + NLA for RDP; RFB auth for VNC).
  • Image clipboard (text clipboard only; image is a stretch goal).
  • XDMCP (#515) — parked in future/, designed to plug in later.

Architecture Decision — Rust-side decode for both #

Decision (made by the maintainer): both protocols decode in Rust and emit a single stream of protocol-agnostic frame / cursor / clipboard / state events that one shared frontend canvas renders. The frontend never knows which protocol it is. This generalizes the RDP concept's approach to VNC as well.

Why this is the unifying choice. When decode happens behind the GraphicalBackend trait, the entire frontend — canvas, input capture, toolbar, overlays, resize, clipboard, fullscreen, status-bar segment — is protocol-blind and shared. VNC and RDP cannot drift because there is only one of each of those things. The seam between "same for the user" and "different on the wire" is drawn exactly at the trait boundary.

Option How frames reach the canvas Verdict
Rust-side decode (chosen) Both backends decode in Rust (IronRDP for RDP; a Rust RFB client for VNC) and emit protocol-agnostic dirty-rect frame + cursor events. One shared RemoteDesktopCanvas paints them. Chosen. One frontend surface, identical input/clipboard/resize handling, no WebSocket proxy, no bundled JS protocol engines. Cost: replaces the VNC concept's noVNC plan with a Rust RFB decoder — trades noVNC's maturity for a single shared surface.
JS-side decode (rejected) noVNC decodes VNC in JS; ironrdp-web (WASM) decodes RDP in JS; both over a Rust WebSocket-to-TCP proxy. Rejected. Keeps noVNC's maturity, but leaves two different JS engines, a WS proxy to run and secure, and a much thinner shared surface — the exact drift this concept exists to prevent.
External viewer launch Shell out to mstsc / xfreerdp / a system VNC viewer. Rejected — not integrated, no tab/split-view, poor UX.

Candidate Rust libraries (recommendations, not mandates)

  • RDP → IronRDP — pure-Rust, cross-platform, no native deps, maintained under the Microsoft org; RDP 6+ with bitmap decoding, input encoding, TLS, and CredSSP (NLA). Kerberos and image clipboard are stretch.
  • VNC → a Rust RFB client — a maintained RFB/VNC crate that exposes framebuffer updates and input encoding. The final crate choice is made during implementation (#1681); the requirement is only that it decodes in Rust into the shared frame stream (no noVNC, no WS proxy). Per the repo's "prefer libraries over custom code" rule, a mature crate is strongly preferred over a hand-rolled RFB decoder.

Shared vs. Protocol-Specific #

The dividing line is deliberate: everything the user sees or touches is shared and built once (implementation issue #1680); only wire-level concerns live in the per-protocol backends (#1681 VNC, #1682 RDP).

Shared — built once in the layer (#1680)

  • One tab content type remote-desktop (not separate vnc/rdp types) → one RemoteDesktopTab / RemoteDesktopCanvas component.
  • One canvas surface fed by protocol-agnostic frame + cursor events.
  • One floating hover toolbar: host badge, resolution, Ctrl+Alt+Del, clipboard, scaling, fullscreen, disconnect. Auto-hide.
  • One set of connection-state overlays: connecting / reconnecting (max-3 auto-retry) / view-only, with tab state-dot semantics (amber connecting, green connected).
  • One status-bar segment: type icon, host:port, resolution, encoding/color-depth.
  • One session state machine and lifecycle (below).
  • One input pipeline: keyboard/mouse capture, focus-boundary escape hatch, modifier-release on focus loss, and pointer-coordinate reverse-scaling shared across all scale modes (Fit to Tab / 1:1 Pixel / Match Window).
  • One clipboard model: bidirectional text sync + slide-out panel.
  • One connection editor, rendered by DynamicForm over a shared field base: host, port, username, password (credential store + "Save to store"), scale mode, color depth, view-only, clipboard sync, auto-reconnect.
  • Shared sidebar/UX: connection-list entry with a distinct monitor icon, context menu (Connect / Edit / Duplicate / Delete — no SFTP/file-browser), and an Open Connections entry, identical to other types.
  • Shared credential-store integration and generic Tauri commands/events.

Protocol-specific — in each backend (the backends legitimately differ)

Both forms are the same schema-driven editor differing only in these rows — the user sees one consistent form (mockup below).

UI Interface #

The remote desktop renders as a <canvas> filling the tab content area, in the same tab bar as terminals. A thin toolbar floats at the top-center of the canvas on hover (like a full-screen client's connection bar) and auto-hides when the pointer leaves. The mockups are authoritative for layout; the same chrome is used for VNC and RDP — only the status-segment text and the protocol icon differ.

General Handling #

Key rules that apply to both protocols through the shared layer:

  • Connection-type routing. Terminal types (ssh, local, telnet, serial, docker) still go through the terminal SessionManager. A connection whose capabilities report graphical: true routes to the GraphicalSessionManager and opens a remote-desktop tab instead of a terminal — the same way FTP's terminal: false opens a browser-only tab today. Routing is by capability, not a hard-coded per-protocol branch.
  • Credentials. Password comes from the credential store (master password or prompt) via the existing flow; "Save to store" writes it. Identical for VNC and RDP.
  • Scale modes. Fit to Tab (scale to fill, preserve aspect), 1:1 Pixel (native, scrollbars if larger), Match Window (request a session resolution matching the tab; dynamic resize on tab/split/window resize). Pointer coordinates are reverse-scaled in one shared helper before reaching the backend.
  • Dynamic resize. RDP uses the Display Control Channel (8.1+); VNC uses server-side desktop resize where supported. Servers that cannot resize stay at the negotiated resolution and the canvas scales — the frontend behaves the same either way.
  • Keyboard capture. While the canvas has focus, key events are captured and forwarded; termiHub's own shortcuts are suppressed except a configurable escape hatch (default Ctrl+Alt+Shift) that releases focus back to termiHub for tab switching. Ctrl+Alt+Del is a toolbar button (the OS would otherwise intercept it).
  • Focus loss stops key forwarding and releases held modifiers to avoid stuck keys.
  • Clipboard is bidirectional text (VNC: ServerCutText/ClientCutText; RDP: clipboard channel), surfaced through one shared slide-out panel with an auto-sync toggle. Image clipboard is a stretch goal.
  • Reconnection retries up to 3 times on an unexpected drop, showing the shared reconnect overlay; after the cap, a manual Reconnect prompt.

Edge cases

Scenario Handling
Auth failure Inline error in the tab ("Authentication failed — check credentials"), retry with new credentials.
RDP certificate mismatch Warning dialog with cert details; accept once or permanently for this host.
VNC over an insecure network Offer/encourage the SSH-tunnel option (RFB auth is weak); reuse the existing tunnel infra.
Very large remote resolution Cap framebuffer (e.g. 4096×2160) to bound memory; warn if the request exceeds the cap.
Tab loses focus mid-drag Release all held mouse buttons and modifier keys.
Multi-monitor / gateway / smart-card Out of scope for v1 (see Non-Goals).

Preliminary Implementation Details #

Based on the architecture at concept-creation time. Three implementation issues realize this concept, and their order is strict — #1680 (shared layer) must land before #1681 (VNC) and #1682 (RDP), so no overlapping UI is built twice.

The seam: a GraphicalBackend trait behind a capability flag

termiHub's existing ConnectionType trait (core/src/connection/mod.rs) is byte-stream oriented (write(&[u8]), subscribe_output() -> bytes, resize(cols, rows)) — a poor fit for a framebuffer. The layer adds a sibling, framebuffer-oriented trait and reuses the same registry/editor/sidebar/credential plumbing via a new capability flag, exactly as terminal: false was added for FTP.

  • FrameUpdate carries decoded RGBA dirty-rects + full width/height; InputEvent is a protocol-agnostic key/pointer/wheel union; GraphicalCapabilities declares supported auth kinds, dynamic-resize, clipboard, and view-only.
  • A graphical connection reports terminal: false, graphical: true, flows through the same ConnectionTypeRegistry, connection editor, sidebar, and credential store as every other type.

Anti-collision requirement for #1680. Backend registration must be additive/registry-driven and the editor must be fully schema-driven, so that adding VNC (#1681) or RDP (#1682) means only creating a new backends/<proto>/ module + schema and calling registry.register(...) — no edit to a shared match arm or a hand-written editor switch. If that holds, #1681 and #1682 touch disjoint files and may run in parallel; if not, they must be sequenced. The eventual code follows the repo's .claude/CLAUDE.md and docs/contributing.md (schema-driven forms, prefer libraries over custom code, tests-with-every-change).

Security considerations

  • VNC RFB auth is weak; encourage the SSH-tunnel path and warn on plaintext connections.
  • RDP defaults to NLA (CredSSP); legacy RDP encryption is available only behind an explicit warning.
  • "Ignore certificate errors" is off by default and shown with a warning.
  • Passwords never touch config plaintext — always via the credential store.
  • Cap framebuffer dimensions to bound memory against a hostile/misconfigured server.
