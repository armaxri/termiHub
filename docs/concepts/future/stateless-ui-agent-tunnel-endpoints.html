Overview #

The stateless-UI / agent-centric port (umbrella #2139) lets every service and network tool run on the remote agent, not only on the desktop, behind a shared run-location trait. Its Phase S3 (issue #2155) applies that to SSH tunnels. The parent flagged one thing as unresolved before S3 can begin — its Open Design Decision #5:

Agent-hosted tunnel endpoint semantics. When a tunnel runs on an agent, what do "local" and "remote" mean, and how is that surfaced without confusing users?

This sub-concept settles that. Today the words "local" and "remote" quietly mean "the desktop" and "the SSH server", because the desktop is the only machine that ever hosts a tunnel. Once the agent can host one, that shorthand breaks: a "local" forward hosted on the agent opens its listen port on the agent's loopback, which is not the user's computer. Left unaddressed, a user would ask for a database on localhost:5432 and find nothing listening there. The design below keeps SSH's own semantics unchanged and instead makes the vantage point — which machine hosts the tunnel — explicit everywhere a tunnel is configured or listed.

Settled framing What it means for S3
SSH semantics are invariant; only the host machine moves "Local" and "remote" keep their exact SSH meaning — relative to the machine running the SSH client (the tunnel host). Agent hosting changes only which machine that is. No new forwarding mode, no relabelled flags.
The vantage point is named, never implied A first-class Tunnel host field (This computer | Agent «name») is shown in the editor, the sidebar, and the Open Connections panel. Human-facing endpoint copy names the concrete machine, not a bare adjective.
Loopback-on-agent is allowed but flagged An agent-hosted listener bound to loopback is reachable only from the agent. The UI warns (non-blocking) and offers an explicit "make reachable from this computer" remediation. It never silently rewrites the bind and never hard-blocks.

Goals

  • Give a precise, host-relative definition of every tunnel endpoint (listen socket, SSH server, forward target) that holds for both desktop and agent hosting.
  • Specify exactly what the UI shows so a user always knows which machine a port opens on and who can reach it, before and after starting.
  • Name and defuse the reachability trap (agent loopback ≠ my computer) with a concrete, non-blocking remediation.
  • Give a recommended default for every fork so S3 (#2155) can start immediately, while flagging the one genuinely product-defining UX choice for a maintainer ruling.

Non-Goals

  • Implementing agent-hosted tunnels. That is #2155; this is its gate. Desktop tunnels are unchanged and untouched.
  • Redesigning the tunnel feature. The three forwarding modes, the visual editor, and the existing tunnel concept stand; this adds a host dimension to them.
  • The run-location routing mechanism itself — that is S1 (#2148), which this concept consumes rather than redefines.

The Invariant — Endpoints Are Relative to the Tunnel Host #

Every SSH tunnel involves up to three machines. The words "local" and "remote" are defined by the SSH protocol relative to the machine running the SSH client — never relative to the person. We name that machine the tunnel host and make it the anchor for all three endpoints:

Term Definition (host-relative — this is the key move)
Tunnel host (the vantage point) The machine running the SSH client that owns the tunnel — the desktop today, the agent under S3. "Local" always means this machine's network. Everything else is defined from here.
SSH server (the "via" hop) The SSH endpoint the tunnel connects through (via in the editor). Unchanged by who hosts — it is the far side of the SSH connection from the tunnel host.
Forward target The final host:port traffic is delivered to. Which machine resolves it depends on the mode, not on who hosts (see below).

With that anchor fixed, the three forwarding modes keep their exact meaning. The only thing agent hosting changes is that "the tunnel host" is now the agent instead of the desktop:

Mode Listen socket lives on… Forward target resolved from…
Local (-L) the tunnel host the SSH server's network
Remote (-R) the SSH server the tunnel host's network
Dynamic / SOCKS (-D) the tunnel host chosen per-connection by the SOCKS client; reached from the SSH server

Read the table with "tunnel host = desktop" and it is exactly today's behaviour. Read it with "tunnel host = agent" and it is S3 — no rule changed, only the substitution. This is the whole trick: we do not redefine "local"/"remote"; we make the machine they are relative to a visible, user-chosen value.

What Moves When the Host Is the Agent #

Applying the substitution concretely, here is a side-by-side of an identical tunnel definition hosted on the desktop versus the agent. The rows that change meaning are where user confusion lives — and are exactly what the UI must surface.

Local forward -L 5432 → db.internal:5432 Host = desktop (today) Host = agent «build-box» (S3)
Where the listen port opens 127.0.0.1:5432 on your computer 127.0.0.1:5432 on build-box — not your computer
Who can connect to it apps on your computer (localhost:5432 just works) processes on build-box; your computer reaches it only if the bind is widened
db.internal is resolved from the SSH server's network (unchanged) the SSH server's network (unchanged)
Who pays the SSH-server round-trip latency your desktop ↔ SSH server build-box ↔ SSH server (often much closer — the point of agent hosting)

The forward target's resolution does not move — a frequent source of the opposite confusion. For a local forward, db.internal is always resolved by the SSH server regardless of host. What moves is the listen side: on an agent-hosted local/dynamic forward the port is on the agent, and on an agent-hosted remote forward the traffic is delivered to a target reachable from the agent, not from the desktop. Both are correct SSH; both surprise a user who still pictures the desktop as "local". Naming the host fixes both.

The Reachability Trap #

The single dangerous case is an agent-hosted local or dynamic forward bound to loopback. Its listen socket sits on the agent's 127.0.0.1, so only processes on the agent can use it — the user's desktop DB client pointed at localhost:5432 connects to nothing. This is not a bug; it is exactly what SSH does. It is a mental-model failure: "local" no longer means "my laptop".

The design refuses to paper over it and refuses to forbid it (loopback-on-agent is the right choice when the consumer is another agent-hosted service — e.g. an agent-hosted HTTP monitor hitting an agent-hosted tunnel). Instead, when host = agent and the bind address is loopback, the editor shows a non-blocking warning with two explicit remediations:

  • Widen the bind — change the listen address from 127.0.0.1 to the agent's LAN address (or 0.0.0.0), so the desktop can reach it at build-box:5432. The port is then exposed on the agent's network; the warning says so.
  • Chain a hop to this computer — flagged as an Open Design Decision because it adds a second moving part. This would auto-create a companion desktop-hosted local forward whose target is the agent's port, restoring plain localhost:5432 on the desktop at the cost of a hidden second tunnel.

The user may also just dismiss the warning — loopback-on-agent stays valid. The rule is: never let the port's location be a surprise, but never make the decision for the user.

UI Interface — Surfacing the Vantage Point #

Three surfaces gain a host dimension: the tunnel editor (choose the host, see named endpoints), the tunnel sidebar (a per-row host badge), and the Open Connections panel (same badge, for the kill/inspect view). Desktop tunnels render exactly as today — the host row simply reads "This computer".

Worked Examples #

Example 1 — Agent-hosted local forward to an internal DB (the common case)

The agent build-box sits inside the corporate network, one hop from bastion.corp; the user's laptop is remote. Hosting the -L forward on the agent means the SSH hop is agent↔bastion (fast, in-network) rather than laptop↔bastion. The listen port opens on build-box:5432. Because the user wants to reach it from the laptop, they take the Widen bind remediation: the bind becomes 0.0.0.0:5432 on the agent, and the laptop's DB client connects to build-box:5432. The editor's endpoint line and the sidebar badge both say build-box, so there is no illusion that localhost would work.

Example 2 — Agent-hosted remote forward exposing an agent-side service

A dev server runs on build-box:3000. An agent-hosted -R forward binds a port on the SSH server and forwards back to a target resolved from the agent — here localhost:3000 meaning build-box's own 3000. The endpoint copy makes the resolving machine explicit: "Forwards to localhost:3000 as seen from build-box". The desktop is not involved in the data path at all; a user who assumed "-R exposes my laptop's port" is corrected by the named endpoint before they start.

Example 3 — Agent-hosted loopback dynamic proxy (legitimately dismissed)

An agent-hosted SOCKS (-D) proxy is bound to 127.0.0.1:1080 on purpose: its only consumer is an agent-hosted HTTP monitor, and loopback keeps the proxy off the agent's LAN. The reachability warning fires, the user dismisses it, and the tunnel stays loopback-bound. The design's job here is only to make the choice informed, not to prevent it.

That separation is precisely why the vantage point must be labelled: the machine the user drives (desktop) is not the machine the port lives on (agent).

States & Sequences #

Starting an agent-hosted tunnel routes through the S1 run-location resolver (#2148) and the migrated Phase-2 tunnel domain (#2150). The resolver picks the registry — local core or the agent proxy — from the tunnel's chosen host; the endpoint semantics above decide what the resulting projection reports.

Preliminary Implementation Details #

Based on the architecture at concept-creation time (July 2026); indicative, not binding. This is design only — the code lands under #2155. The semantics here are overwhelmingly a view-model + labelling change layered on the S1 resolver and the Phase-2 tunnel domain; the SSH mechanics themselves are unchanged.

Path Change
src-tauri/src/tunnel/ / core tunnel service A tunnel definition gains a host field (ThisComputer | Agent(id)), consumed by the S1 resolver to pick the local core registry or the agent proxy. The listen/target mechanics are the existing russh logic, run wherever the resolver routes it. Desktop path unchanged.
agent/ tunnel backend The agent already hosts SSH; S3 exposes the tunnel service over the agent RPC so the resolver can start/stop it there. Reports back boundOn (host name) and a reachableFrom classification (agent-only / agent-LAN / SSH server) for the projection.
Tunnel projection view model (parent Phase-2 region) New fields per tunnel: host (for the badge), endpoints (named machine + address per side), and reachabilityWarning?. The whole endpoint-labelling design is these fields; the UI is a pure renderer of them (aligned with the stateless-UI port).
src/components/TunnelEditor/, src/components/TunnelSidebar/ Add the Tunnel host selector (the S1 run-location control), render named endpoint lines from the view model, the per-row host badge, and the non-blocking reachability warning with its two remediations.
src/components/OpenConnections/ Show the same host badge on tunnel rows so the inspect/kill view also states the vantage point.

Recommended Defaults #

Each fork below has a recommended default so #2155 can begin immediately. The one genuinely product-defining choice is escalated to Open Design Decisions.

Fork Recommended default
Meaning of "local"/"remote" under agent hosting Keep SSH semantics; make the host explicit. "Local"/"remote" stay relative to the tunnel host; do not relabel the modes. Add a visible Tunnel host field instead.
Human-facing endpoint copy Name the concrete machine and address ("Listens on agent build-box · 127.0.0.1:5432"), never a bare adjective. Every listen line carries a "who can reach this" note.
Default tunnel host for new tunnels This computer — matches today exactly; agent hosting is opt-in (consistent with S2's "default run-location stays This computer").
Default bind address for an agent-hosted local/dynamic forward Loopback (127.0.0.1), safe by default, with the warning + remediation — do not auto-widen to the agent's LAN, which would silently expose a port.
Loopback-on-agent listener Allow, warn (non-blocking), never rewrite or hard-block. Offer "Widen bind" as the built-in remediation.
Vantage badge on lists Always shown on every tunnel row (sidebar + Open Connections), including "this computer" for desktop tunnels — consistency beats hiding the common case.

Open Design Decisions #

The endpoint semantics and the vantage-surfacing design are settled above and unblock #2155. These remaining choices are genuinely product-defining and want a maintainer ruling — none blocks starting the SSH-mechanics and labelling work; they shape only the remediation surface.

  1. Auto-chaining a desktop hop (the product-defining one). Should the "Chain a hop to this computer" remediation exist — auto-creating a companion desktop-hosted local forward so an agent-hosted loopback port appears at plain localhost on the desktop? It restores the familiar mental model but hides a second tunnel and doubles the moving parts (two lifecycles, two failure modes, a dependency between them). Recommendation: ship S3 without auto-chaining — offer only "Widen bind" first — and revisit auto-chaining as a follow-up once agent tunnels have real usage. Flagged because it is the one choice that changes what the product does, not just what it says.
  2. Terminology on the mode labels for non-SSH-native users. Keep the raw SSH names ("Local / Remote / Dynamic forwarding") or add a plain-language subtitle ("Open a port here → reach a service over there")? Recommendation: keep the SSH names (desktop tunnels are unchanged and users know them) and lean on the named endpoint lines for clarity, rather than renaming modes.
  3. Warn scope. Fire the reachability warning only for agent-hosted loopback listens (proposed), or also when an agent-hosted forward's target is likely desktop-relative (an easy -R mistake)? Recommendation: start with the loopback-listen warning; add target-side hints as a follow-up if usage shows the -R confusion is common.
