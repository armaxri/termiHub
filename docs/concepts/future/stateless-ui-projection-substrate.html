Overview #

The stateless-UI / agent-centric port (umbrella #2139) moves all authoritative state and business logic out of the React UI and into the Rust backend. The UI becomes a thin projection and dispatcher: it renders backend-provided view models and dispatches user intents, holding no authoritative state. The parent concept collapses today's ~206 typed Tauri commands + ~36 event channels into two generic channels — dispatch(intent) and subscribe(region) — plus the untouched terminal byte stream. Everything else in the port depends on the exact shape of those two channels.

This sub-concept is that shape: the substrate contract. It is the load-bearing "Open Decision #1" of the parent, now settled by the maintainer (see #2139, 2026-07-30) and worked into a concrete design:

Settled decision What it means for the substrate
Transport = server-authoritative per-region diff channels Snapshot-on-attach, then ordered per-region versioned diffs, resync-on-reconnect. The backend is the single authoritative writer.
Not a CRDT Clients only dispatch intents; the backend serialises them. There is no concurrent-edit merge — versioning exists to detect loss, not to reconcile conflict.
Multi-client IS in scope N UIs may attach to one backend session. Every region is designed for multi-subscriber fan-out from the start, aligned with remote-client mode.

Goals

  • Define the two envelopes — the intent (UI→backend) and the projection frame (backend→UI, snapshot or diff) — precisely enough to implement Phase 1.
  • Specify per-region versioning: monotonic version, ordered diffs, gap-detection, snapshot-on-attach, resync-on-reconnect.
  • Specify multi-subscriber fan-out: subscription lifecycle, single-writer apply-then-emit, and a consistent snapshot for late joiners.
  • Give region-granularity guidance that keeps projections off the single-threaded IPC bridge's critical path (the parent's top risk).
  • Keep the terminal byte stream a separate untouched channel and let the existing typed commands coexist during a strangler migration.
  • Reuse remote-client mode's transport abstraction rather than fork it.

Non-Goals

  • Migrating any domain. This designs the pipe; porting the ~20 state domains through it is the parent's Phases 2–5.
  • Reshaping the terminal output hot path. It already works the right way and is explicitly left alone.
  • A CRDT, operational-transform, or offline-edit layer. Out of scope by the settled decision.
  • The WebSocket server itself — that is remote-client mode's Phase 2.

The Three Channels #

The substrate carries three independent channels. Two are new and generic; the third already exists and is untouched.

# Channel Direction Carries Ordering / delivery
1 dispatch(intent) UI → backend One serialisable intent; returns an ack (accepted / rejected). Request/response; the backend serialises all intents (single writer).
2 subscribe(region) backend → UI An initial snapshot, then an ordered stream of diffs for that region. Ordered per region; no cross-region ordering guarantee.
3 terminal-output (existing) backend → UI Coalesced raw PTY bytes, base64, per session. Ordered per session; rAF-batched into xterm. Never projected.

The typed command surface does not vanish. Each of today's commands becomes an internal backend function called by an intent handler; each of today's push events becomes a projection diff. During migration both the old and new channels are live at once (see Coexistence).

Envelope Schemas #

All envelopes are transport-neutral: identical whether they ride Tauri IPC (desktop) or JSON-RPC over WebSocket (remote-client mode). Types are given in TypeScript for the frontend; the Rust structs are their serde mirror, exactly as core/src/protocol/ already mirrors its JSON-RPC types today.

Intent envelope (channel 1, UI → backend)

interface Intent<P = unknown> {
  intentId: string;   // client-generated ULID; correlates the ack (and optimistic echo)
  kind: string;       // dotted "<domain>.<action>", e.g. "tunnel.start", "layout.moveTab"
  payload: P;         // kind-specific, serialisable; validated backend-side
  clientId: string;   // which attached client dispatched it (fan-out / audit identity)
}

interface IntentAck {
  intentId: string;                       // echoes the request
  status: "accepted" | "rejected";
  error?: { code: string; message: string };   // present iff rejected
  // Regions this intent advanced, so a client can await the matching diff
  // before clearing an optimistic echo. Empty for no-op / query intents.
  produced?: Array<{ region: string; version: number }>;
}

The ack is a receipt, not the result. The result of an intent is always a projection diff on the affected region(s) — never data returned inline. This is what makes multi-client correct: a change requested by client A reaches client B by exactly the same path it reaches A (the region's diff stream), so no client can hold state another client cannot see.

Projection frame (channel 2, backend → UI)

type ProjectionFrame =
  | SnapshotFrame
  | DiffFrame;

interface SnapshotFrame {
  region: string;      // region id, e.g. "tunnels" or "layout@client-7"
  kind: "snapshot";
  version: number;     // u64 monotonic; the cache adopts this as its baseline
  view: unknown;       // the complete, render-ready view model for the region
}

interface DiffFrame {
  region: string;
  kind: "diff";
  baseVersion: number; // MUST equal the cache's current version, else it is a gap
  version: number;     // == baseVersion + 1 (see Versioning)
  ops: DiffOp[];       // ordered mutations to apply to the cached view model
}

// Default diff shape: an RFC 6902 JSON-Patch subset (add / remove / replace).
// A domain MAY emit compact semantic ops instead (see Open Decisions).
type DiffOp =
  | { op: "replace"; path: string; value: unknown }
  | { op: "add";     path: string; value: unknown }
  | { op: "remove";  path: string };

Subscription control (channel 2 setup / teardown)

// Attach. Returns the current snapshot AND begins the diff stream atomically
// (no diff can slip between the snapshot's version and the first streamed diff).
subscribe(region: string): Promise<{ frame: SnapshotFrame; stream: ProjectionStream }>

// Detach. Idempotent; releases the client's slot in the fan-out registry.
unsubscribe(region: string): void

// Recover. Client asks the backend to re-baseline a region after a detected gap
// or a reconnect. `have` lets the backend skip work if the client is current.
resync(region: string, have?: number): Promise<SnapshotFrame>

Region ids are "<domain>" for globally-shared regions (e.g. tunnels, openConnections) and "<domain>@<clientId>" for client-scoped regions (e.g. a per-client tab layout — see Region Granularity). The @client suffix is the only thing that distinguishes a shared region from a per-client one; the envelope and versioning rules are identical for both.

Per-Region Versioned Projections #

Each region owns a single monotonic u64 version, held backend-side and mirrored in the client's cache. The version is the entire consistency mechanism; because the backend is the only writer, versioning need only detect dropped or reordered frames, never merge concurrent edits.

The three invariants

  • Snapshot-on-attach. subscribe returns a SnapshotFrame at the region's current version V. The client adopts V as its baseline. Attach is atomic with stream start: the backend registers the subscriber and captures the snapshot under the same region lock, so no diff is lost between the snapshot and the first streamed diff, and none is double-applied.
  • Ordered diffs. Every mutation emits one DiffFrame with baseVersion = V, version = V+1. A client applies a diff only if frame.baseVersion === cache.version; it then advances cache.version = frame.version. Delivery is ordered per region on both transports (Tauri per-channel events and a single WebSocket both preserve order), so in the normal case every diff fits exactly.
  • Resync-on-gap / reconnect. If frame.baseVersion !== cache.version (a gap: a frame was dropped, reordered, or the socket reconnected), the client discards the diff, calls resync(region, cache.version), and re-baselines from the returned snapshot. No diff is ever applied out of order.
Version lifecycle for one region 
stateDiagram-v2
    [*] --> Attaching : subscribe(region)
    Attaching --> Live : snapshot @ V (cache.version = V)
    Live --> Live : diff base=V ver=V+1 (fits) -> apply, version = V+1
    Live --> Gap : diff base != cache.version (drop / reorder / reconnect)
    Gap --> Live : resync -> snapshot @ W (cache.version = W)
    Live --> [*] : unsubscribe(region)

Version scope. Versions are per region and monotonic for the life of the backend process's region instance. A region that is destroyed and recreated (e.g. the backend restarts) resets to 0; the client detects this because a fresh subscribe always yields a snapshot, never a diff, so no stale baseVersion comparison survives a re-attach. Versions are never compared across regions.

Multi-Subscriber Fan-Out #

A region may have N subscribers — several tabs in one desktop app, or a desktop plus a browser plus an iPad in remote-client mode. The backend is the single writer: it applies an intent once, bumps the region version once, computes the diff once, and fans that one diff out to every current subscriber. All subscribers of a region therefore step through the identical version sequence.

Subscription registry

The projector holds a SubscriptionRegistry: region → Set<Subscriber>, where a Subscriber is { clientId, sink } and sink is the delivery handle (a Tauri ipc::Channel on desktop, a WebSocket send half in remote mode). Lifecycle:

  • Attach inserts the subscriber under the region lock and hands back the snapshot (invariant 1). First subscriber of a region may lazily instantiate the region's projector.
  • Emit iterates the region's subscriber set and pushes the one diff to each sink. A sink whose client has gone (closed channel / dead socket) is dropped from the set — the emit path is where dead subscribers are reaped.
  • Detach (explicit unsubscribe, tab close, or client disconnect) removes the subscriber. When the set empties, the region projector may be torn down to reclaim memory; the next attach rebuilds it from authoritative state.

Late joiners get a consistent snapshot

A client attaching to a region that is already live does not replay history. It receives a snapshot at the current version, computed from authoritative state under the region lock, and joins the diff stream from there. Because snapshot capture and subscriber insertion happen under the same lock, a late joiner can neither miss a diff that lands during attach nor receive one that predates its snapshot. Every subscriber — first or hundredth — converges on byte-identical view state at the same version.

Region Granularity #

The parent concept's top risk is projection chattiness: naive full-snapshot pushes on every change would flood the Tauri IPC bridge, which is already single-threaded (an architecture ADR risk). Region design is the discipline that prevents it. Four rules:

Rule Guidance
Diff, don't re-snapshot After attach, steady state is diffs only. A full snapshot is emitted only on attach and on resync. A one-field change is one replace op, not a whole view model.
One region per view / domain Split state so a subscriber only receives what its view renders. Candidate regions: conntree (connection sidebar), tunnels, openConnections, servers, transfers, monitors@<host>, layout@<client>. A collapsed panel need not be subscribed at all.
Coalesce bursts The projector debounces a region: many mutations within a tick collapse into one diff (or a fresh snapshot if the backlog is large), advancing the version by one. This mirrors the terminal path's existing coalescing discipline (the 32 KB PTY coalescer + rAF batching) rather than inventing a new one.
Subscribe on demand A client subscribes to a region when its view mounts and unsubscribes when it unmounts. Fan-out cost scales with visible regions × clients, not total state.

Shared vs. client-scoped regions. Authoritative facts that every client must agree on are shared regions (one version stream fanned to all): running tunnels, live sessions, embedded servers, the connection tree. View state that is legitimately per-client — remote-client mode already states each client has an independent tab layout — is a client-scoped region (layout@<clientId>), authoritative in the backend but keyed per client and fanned out only to that client's own subscribers (e.g. its multiple windows). The substrate treats both identically; only the region id differs. Which domains are shared vs. client-scoped is a per-domain product call — see Open Decisions.

Coexistence & Migration #

The terminal byte stream stays separate and untouched

Terminal output is the app's hottest path and already works the right way: the backend coalesces PTY output (up to 32 KB) and emits base64 bytes on the terminal-output event (with terminal-exit for teardown); events.ts's TerminalOutputDispatcher batches per session via requestAnimationFrame and writes straight into xterm.js. This channel never passes through the projector — routing bytes through versioned diffs would add latency and defeat the coalescer. It is channel 3, wholly independent of the substrate; the substrate must not touch it. xterm's scrollback remains view-local render state.

Typed commands coexist (strangler)

The substrate lands beside the existing ~206 typed commands and ~36 events, not in place of them. During migration:

  • A domain that has not yet migrated keeps using its typed commands and events exactly as today.
  • A migrated domain is served by a region; its old commands become internal functions behind the intent handler, and its old events stop firing (their data now flows as diffs).
  • The two never serve the same domain at once — the strangler rule "one domain per phase behind a stable projection boundary" keeps the boundary clean, so there is no double-write.

Because the substrate is additive, the app stays fully working after every phase, and any single phase is independently revertable.

Plugin-runtime interaction

Frontend JS plugins (src/plugins/pluginRuntime.ts) are the parent concept's sharpest exception to "no logic in the UI". Two interactions matter for the substrate:

  • Protocol parsers run transform(data, sessionId) over every terminal chunk. They sit on channel 3, not the projection channel — the preferred path is to move them to the Rust plugin backend (termihub-plugin-api), which keeps them off the frontend hot path entirely. Either way they never see projection frames.
  • Status-bar widgets render DOM in the UI. They become sandboxed (Worker/iframe) consumers that render into a shell-owned slot; if a widget needs backend state it subscribes to a region like any other view, rather than reaching into app state. It never becomes an authoritative writer.

Worked Example — SSH Tunnels #

SSH tunnels are the parent concept's Phase 2 pilot domain (already a self-contained store slice with a clear lifecycle). This walks one region, tunnels, end-to-end across two attached clients and a reconnect.

The region's view model

// region "tunnels" — the whole render-ready list for the tunnel sidebar
{
  "tunnels": [
    { "id": "t1", "label": "db → localhost:5432", "kind": "local",
      "status": "connected", "bind": "127.0.0.1:5432" },
    { "id": "t2", "label": "socks", "kind": "dynamic",
      "status": "connecting", "bind": "127.0.0.1:1080" }
  ]
}

Step by step

  1. Attach. Client A (desktop) and Client B (browser) both subscribe("tunnels"). Each receives SnapshotFrame { version: 41, view: {…} } and registers in the fan-out set.
  2. Dispatch. On A, the user clicks "Start" on tunnel t2. A sends dispatch({ intentId: "01J…", kind: "tunnel.start", payload: { id: "t2" }, clientId: "A" }). A shows an optimistic "connecting…" echo keyed by that intentId.
  3. Apply (single writer). The dispatcher validates, calls the existing tunnel-start logic (now an internal function), and the tunnel store transitions t2 to connecting, bumping the region version 41 → 42.
  4. Ack. A receives ack { status: "accepted", produced: [{ region: "tunnels", version: 42 }] }.
  5. Fan-out. The projector emits one diff and pushes it to both subscribers: 
    { "region": "tunnels", "kind": "diff", "baseVersion": 41, "version": 42,
  "ops": [ { "op": "replace", "path": "/tunnels/1/status", "value": "connecting" } ] }
    A applies it and drops its optimistic echo (the produced version arrived). B — which never issued the intent — applies the identical diff and now shows t2 connecting too. Both caches are at version 42.
  6. Real completion. The SSH layer confirms the bind; the store moves t2 → connected (version 42 → 43). One more diff fans out to both; both reach version 43.
  7. Reconnect + resync. B's browser is backgrounded; its socket drops. While away, the user on A stops t1 (version 43 → 44). B reconnects and calls resync("tunnels", 43). The backend is at 44, so it returns SnapshotFrame { version: 44, view: {…} }; B re-baselines to 44 and resumes the diff stream. B never applied a stale diff and never saw an inconsistent list.

Preliminary Implementation Details #

Based on the architecture at concept-creation time (July 2026); indicative, not binding. The substrate is Phase 1 of the parent concept — the two channels plus a dumb projection-cache adapter, terminal stream untouched.

Rust side — src-tauri/src/projection/ (+ core)

Path Change
src-tauri/src/projection/mod.rs New — the Projector: owns the SubscriptionRegistry (region → Set<Subscriber>), the per-region version counters, and the coalescing/diff step. Exposes subscribe / unsubscribe / resync / emit.
src-tauri/src/projection/region.rs New — a ProjectedStore trait a domain store implements: fn region_id(&self) -> &str, fn snapshot(&self) -> ViewModel, and a change signal. The projector diffs consecutive snapshots (default) or accepts semantic ops from the store (opt-in, hot domains). The natural first seam is the existing app-side authority — SessionManager in src-tauri/src/session/manager.rs already owns the session registry, scrollback and event emitter — which a region wraps rather than replaces.
src-tauri/src/projection/frame.rs New — serde structs for Intent, IntentAck, SnapshotFrame, DiffFrame, DiffOp. Twin of the TS envelopes; lives next to / reuses core/src/protocol/ so remote-client mode speaks the same dialect.
src-tauri/src/commands/projection.rs New — two Tauri commands: intent_dispatch(intent) -> IntentAck and projection_subscribe(region) -> SnapshotFrame, the latter opening a tauri::ipc::Channel<ProjectionFrame> per region for the diff stream (efficient per-region push, avoids a global event fan-in).
core/src/output/ (existing) Untouched — the OutputCoalescer and the terminal-output path stay exactly as-is (channel 3).

TS side — src/services/transport/

Path Change
src/services/transport/index.ts New — transport selector (shared with remote-client mode): window.__TAURI__ present → TauriTransport, else WebSocketTransport.
src/services/transport/TauriTransport.ts, WebSocketTransport.ts New — implement one Transport interface: dispatch(intent), subscribe(region), resync(region, have). Tauri wraps invoke + the ipc::Channel; WebSocket wraps JSON-RPC over the socket.
src/services/transport/ProjectionClient.ts New — per-region cache adapter: holds { version, view }, applies diffs, detects gaps (baseVersion !== version) and calls resync, and re-baselines on reconnect. Emits changes to the store.
src/store/appStore.ts A migrated domain's slice becomes a dumb projection cache: it holds the last view model for its region and notifies React; it computes and decides nothing. Non-migrated slices are unchanged (strangler).
src/services/api.ts, src/services/events.ts Unchanged for non-migrated domains; the terminal TerminalOutputDispatcher path in events.ts stays exactly as-is.

Diff library. Per the repo's "prefer libraries" rule, the default structural diff should use a maintained RFC 6902 JSON-Patch crate (Rust, produce) + npm package (TS, apply) rather than a hand-rolled differ — with the semantic-op escape hatch reserved for domains that measure a hot path.

Alignment with Remote-Client Mode #

This substrate reuses, does not fork, remote-client mode's transport abstraction. That concept already defines src/services/transport/ with an index.ts selector choosing TauriTransport vs. WebSocketTransport, both speaking the same JSON-RPC dialect as the existing desktop↔agent protocol. The substrate lives inside that abstraction:

  • The intent/projection envelopes become additional JSON-RPC methods/notifications (intent.dispatch, projection.subscribe, projection.frame, projection.resync) carried by whichever transport is selected — no second transport layer.
  • Remote-client mode already states sessions are owned by the agent, survive a dropped socket, and re-attach on reconnect, and that multiple clients may connect at once. The substrate's snapshot-on-attach + resync-on-reconnect + multi-subscriber fan-out is the state counterpart of that session behaviour — the same lifecycle, applied to projected view models.
  • Remote-client mode's note that "each client has an independent tab layout" is realised as a client-scoped layout@<clientId> region; its settings/changed broadcast becomes a shared settings region.

Net: remote-client mode owns where the bytes travel (Tauri IPC vs. WebSocket, auth, TLS); this concept owns what state-shaped messages travel over it. They compose; neither duplicates the other.

Open Design Decisions #

The transport and multi-client questions are settled (see Overview). The following surfaced while designing the substrate and need a maintainer call before Phase-1 implementation locks — none blocks starting, but each shapes the API.

  1. Intent-acknowledgement model. This design proposes an explicit IntentAck (accepted/rejected + produced versions) so errors are reported at the dispatch site and a client can correlate an optimistic echo to the diff that confirms it. The alternative is fire-and-forget: no ack, the UI learns of success or failure only by observing the next projection (rejections would need an error region). The ack model costs a round-trip reply but makes error handling and optimistic-echo teardown deterministic. Recommended: explicit ack.
  2. Optimistic vs. pessimistic UI updates. Does the UI echo an intent optimistically (show "connecting…" immediately) or wait for the confirming diff? On the desktop the round-trip is sub-millisecond, so pessimistic is invisible; over a WebSocket it is not. Proposal: pessimistic by default, with opt-in optimistic echo (keyed by intentId, cleared when the produced version arrives) for latency-sensitive interactions like drag-drop and typing. This has real product feel implications and interacts with decision 1.
  3. Diff granularity / format. Default is a generic RFC 6902 JSON-Patch subset (uniform, library-backed, works for any region). Hot or large regions may warrant compact semantic ops (e.g. tunnelStatusChanged{id,status}) to avoid path-diffing cost. Proposal: JSON-Patch default with a per-domain semantic-op escape hatch. The decision is how much to invest up front vs. defer until a region measures hot.
  4. Which domains are shared vs. client-scoped. The substrate supports both; the assignment is a product call per domain. Clear cases: tunnels/sessions/servers/ connection-tree are shared; tab layout is client-scoped (remote-client mode already says so). Ambiguous: selection, active tab, sidebar collapse, filter text — per-client view state, but should a "follow my session" mode ever mirror them? Needs a per-domain ruling as each domain migrates, not one global answer.
