Overview #

An agent-hosted local (-L) or dynamic (-D) forward bound to loopback opens its listen port on the agent's 127.0.0.1. Only processes on the agent can use it — a database client on the user's desktop pointed at localhost:5432 connects to nothing. The endpoint-semantics sub-concept named this the reachability trap and shipped one remediation under #2155: Widen bind, which rewrites the agent listener to 0.0.0.0 so the desktop reaches it at build-box:5432. Widening works, but it exposes the port on the agent's network and abandons the familiar localhost mental model.

This concept designs the second, deliberately-deferred remediation: Chain a hop to this computer. One click auto-creates a companion desktop-hosted local forward whose target is the agent's loopback port, restoring plain localhost:5432 on the desktop while keeping the agent listener loopback-private. The cost — and the reason it was deferred until agent tunnels had real usage — is a second moving part: two tunnel lifecycles, two failure modes, and a dependency between them. The whole job of this design is to make that second part never silent: created explicitly, shown as a linked pair, and torn down together.

The two remediations, side by side Widen bind (shipped, #2155) Chain a hop (this concept)
Where the desktop reaches the service build-box:5432 (the agent's address) localhost:5432 (this computer)
What it exposes the port on the agent's LAN nothing new — agent stays loopback-private; a second SSH hop carries the traffic
Moving parts one tunnel, rewritten bind two linked tunnels (agent parent + desktop companion)
Best when the desktop is on the agent's network and exposure is acceptable the desktop is remote and you want the familiar localhost with no LAN exposure

Goals

  • One-click chain a companion desktop hop from the editor's reachability warning, restoring localhost:PORT on the desktop for an agent-hosted loopback forward.
  • Design the companion-tunnel lifecycle: how it is created, linked to its agent-hosted parent, started/stopped in the correct order, and torn down with the parent.
  • Surface the pair — the companion is never a hidden second tunnel. It appears nested under its parent in the sidebar and as a linked pair in Open Connections, with a combined status.
  • Give a precise, actionable answer to every failure of the dependency between the two tunnels (agent offline, companion can't reach the agent, desktop port in use, one side drops).

Non-Goals

  • Re-designing agent-hosted tunnels or endpoint semantics — those are settled in #2155 and this builds strictly on top of them (the host field, the reachability warning, the ReachableFrom runtime classification).
  • Removing or changing Widen bind. Chaining is an additional, alternative remediation offered alongside it — the user still chooses.
  • Auto-chaining without user action. The companion is only ever created by an explicit click; the app never silently spawns a second tunnel (that was the whole risk the maintainer flagged when deferring this).
  • Generalising chaining to arbitrary N-hop paths. This creates exactly one companion hop (desktop → agent), which is the only case the trap needs.

The Mechanism — What "Chaining a Hop" Actually Builds #

The agent is itself reached over SSH (the desktop↔agent JSON-RPC transport rides an SSH connection). That existing SSH reachability is exactly what the companion reuses: the companion is a desktop-hosted -L forward whose SSH server is the agent's own host, and whose forward target is the parent's loopback listen port resolved from the agent. Traffic then flows through two chained SSH hops:

The dependency is one-directional and unavoidable: the companion's forward target is the parent's listen socket, so the parent must be connected before the companion can bind usefully. That single fact drives the whole start/stop ordering and the combined-status model below.

General Handling — Lifecycle, Linking, Edge Cases #

Creating the link

Chaining is only offered where the trap exists — an agent-hosted -L/-D forward bound to loopback (exactly the condition tunnelReachabilityWarning already tests in #2155). On Create & link, the app derives a companion TunnelConfig (host ThisComputer, mode -L, SSH-via = the agent's SSH connection, target = the parent's loopback host:port, local bind = 127.0.0.1:PORT), stamps a bidirectional link on both configs (parent.companionId / companion.companionOf), and saves the pair. If "Start the pair now" is checked, it starts them in dependency order.

Start / stop ordering (the dependency is one-directional)

  • Start: parent first. The companion's target is the parent's listen socket, so the companion only starts once the parent reaches connected. Starting the companion directly implies starting the parent.
  • Stop: companion first, then parent — the reverse. Stopping the parent always stops the companion (it would otherwise dangle pointing at a dead port).
  • Reconnect: reconnect the parent, wait for connected, then reconnect the companion. A parent flap therefore transiently degrades the pair rather than erroring the companion permanently.

Combined status model

The pair reports one derived status so the user reasons about "does localhost:5432 work?" rather than juggling two rows:

Parent Companion Pair status What the user sees
connected connected Linked · connected localhost:5432 works; both dots green
connected connecting Linked · connecting parent green, companion amber — almost there
connected error / disconnected Linked · degraded agent port works, localhost does not; warning + inline fix (Retry / different local port)
error / disconnected (forced down) Linked · down parent error surfaces first; companion is held down until the parent recovers

Edge cases

Situation Behaviour
Agent offline / not connected The parent cannot host, so chaining is meaningless. The "Chain a hop" action is disabled with a reason ("Agent build-box is offline"). An already-chained pair whose agent drops goes Linked · down and auto-recovers when the agent reconnects (rides the existing agent-reconnect machinery).
Companion can't reach the agent over SSH The companion's own SSH hop (desktop → agent) fails like any tunnel: the pair is degraded, the companion row shows the SSH error, Retry is offered. The parent is unaffected — the agent port still works for agent-side consumers.
Desktop port already in use The companion's 127.0.0.1:PORT bind fails. The pair is degraded with "localhost:5432 is already in use" and two fixes: Use a different local port (then the desktop reaches at the new port, shown explicitly — the localhost:PORT promise is honoured at whatever port actually bound) or Retry.
Hop already chained Chaining is idempotent per parent. If a companion already exists the warning shows “Chained ✓ · reveal” instead of the create action — never a second duplicate companion.
User widens the parent bind later A widened parent is no longer loopback, so the companion is redundant (and its target address is now wrong). The app flags the companion as redundant and offers to remove it. The two remediations are mutually exclusive by intent.
Parent host changed to This computer A desktop-hosted parent already gives localhost:PORT; the companion is redundant and offered for removal, same as widening.
User stops / deletes the companion directly Allowed, but confirmation warns it breaks localhost:5432 while leaving the agent port running. Deleting the companion clears the link on the parent (the warning's action reverts to "Chain a hop").
Parent deleted Cascades: the delete confirmation names both tunnels and removes the companion with the parent — no orphan desktop tunnel pointing at a dead agent port.

Preliminary Implementation Details #

Based on the architecture at concept-creation time (Sep 2026); indicative, not binding. Chaining is almost entirely additive: it composes two tunnels that already exist as first-class objects (desktop-hosted -L and the agent-hosted forward from #2155/#2185). The new work is the link field, the ordered pair lifecycle, the combined status, and the UI to create/surface the pair. SSH mechanics are untouched.

Path Change
src-tauri/src/tunnel/config.rs · src/types/tunnel.ts Add a link field to TunnelConfig: companion_of: Option<TunnelId> on the companion (and/or a derived companion_id on the parent). Optional, defaulted on load, so existing configs round-trip. A companion is a normal desktop-hosted -L config plus this link.
src-tauri/src/tunnel/tunnel_manager.rs Ordered pair lifecycle: start = parent-then-companion (gate the companion on the parent reaching connected); stop/remove = companion-then-parent (cascade). A parent status transition drives the companion (start on connect, hold down on parent error). Reuses the existing status-emit choke point.
src-tauri/src/tunnel/projection.rs The tunnels region already carries configs + per-tunnel TunnelState. Add a derived pair/combined status to the view model (or compute it in the frontend from the link + both states) so the UI renders one "Linked · …" status. New intents may be thin (tunnel.chain to create+link, tunnel.unchain to remove the companion) or the existing tunnel.create/remove can carry the link.
Companion derivation (new pure helper, e.g. src/utils/tunnelChain.ts) A pure function deriveCompanion(parent, agentSshConnectionId) that returns the companion TunnelConfig (host ThisComputer, -L, via the agent's SSH connection, target = parent loopback host:port, bind 127.0.0.1:port). Unit-tested directly, mirroring the pure style of src/utils/tunnelHost.ts.
src/components/TunnelEditor/TunnelEditor.tsx Add the second action beside the existing handleWidenBind in the reachability block — "Chain a hop to this computer" → open the preview → dispatch chain. Disable it when the host agent is offline or a companion already exists (show "Chained ✓" instead).
src/components/TunnelSidebar/TunnelListItem.tsx · TunnelSidebar.tsx Render a companion nested under its parent with the link badge and its own host badge; show the combined "Linked · …" status and the degraded inline fix. Extends the existing host/reachability rendering (reportedReachability).
src/components/OpenConnections/OpenConnectionsModal.tsx Group the pair; primary stop acts on the pair; stopping the companion alone warns it breaks localhost.
agent/src/tunnel/mod.rs No change. The agent hosts the parent forward exactly as today (#2185); the companion is entirely desktop-side. Chaining adds no agent protocol.

Recommended Defaults #

Fork Recommended default
Is chaining automatic? No — explicit, click-and-preview only. The app never spawns a companion without the user seeing the preview and confirming. This is the core concern the maintainer raised when deferring.
Companion's SSH-via Derived from the agent's SSH connection, not user-picked — the agent is already SSH-reachable, and deriving it keeps the action one click.
Companion local port Same as the parent's port (preserve the localhost:PORT promise); fall back to a user-chosen port only on a desktop port conflict, shown explicitly.
Visibility of the companion Always shown, nested under the parent with a link badge — never a hidden second tunnel (the issue's explicit requirement).
Lifecycle coupling Cascade. Start/stop/delete the parent cascades to the companion in dependency order; the companion cannot outlive its parent.
Status shown Combined "Linked · …" status so the user reasons about whether localhost:PORT works, with a distinct degraded state when only the companion is down.
Relationship to Widen bind Mutually exclusive remediations. Widening a chained parent marks the companion redundant and offers removal; the two are never both active.

Open Design Decisions #

The parent endpoint-semantics concept escalated one product-defining question — "should the chain-a-hop remediation exist at all?" This concept answers how it should work if built; the whether/when remains the maintainer's call (currently: keep deferred until agent tunnels have real usage). These are the remaining shape decisions.

  1. Whether/when to build (maintainer-gated). Per #2186's comments the feature stays deferred even though its dependency #2185 landed. Recommendation: build once agent-hosted tunnels see real use and the loopback trap is hit often enough that "Widen bind" alone is insufficient.
  2. Where the companion's SSH-via comes from when the agent has several SSH reachability paths. Derive from the primary agent SSH connection (proposed), or let the user pick in the preview? Recommendation: derive silently from the agent's primary SSH connection; expose an override in the preview only if usage shows multiple paths are common.
  3. Combined status home. Compute the "Linked · …" status in the Rust projection view model, or derive it in the frontend from the link + two states? Recommendation: derive in the frontend initially (pure, testable, no region schema change); promote to the projection if other clients need it.
  4. Depth cap. Restrict chaining to exactly one desktop hop (proposed), or allow a companion to itself be chained? Recommendation: cap at one hop — the trap never needs more, and deeper chains multiply the failure surface.
