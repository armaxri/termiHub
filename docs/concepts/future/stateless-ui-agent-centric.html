Overview #

Two convergent principles restructure termiHub around a strong backend and a thin frontend:

  1. Stateless UI. Move all business logic and authoritative state out of the React frontend into the Rust backends — the Tauri desktop layer (src-tauri), the shared termihub-core crate, and the remote agent. The UI becomes a thin, stateless projection and dispatcher: it renders backend-provided view state and dispatches user intents, holding no authoritative state and no business logic of its own — only view-local ephemera (scroll position, focus, hover, in-progress text input, xterm's own render buffer).
  2. Agent-centric services & tools. Let every service and network tool be executed by the remote agent, not only the desktop: the embedded servers (HTTP/FTP/TFTP), the network utilities (ping, traceroute, port scanner, DNS lookup, HTTP monitor, Wake-on-LAN), SSH tunnels, and system monitoring. Each becomes a service/tool behind a shared trait that both the desktop host and the agent host implement, so the user can choose where a service or a diagnostic runs — from their laptop or from a build server three hops away.

These are one idea seen from two ends. A stateless UI can only dispatch intents to a backend that owns the corresponding capability; agent-centric services require that capability to be modelled as a location-agnostic backend object rather than as logic baked into a desktop component. Both push the same work the same direction: out of the WebView, into a location-agnostic Rust service model.

The good news — quantified in Current Architecture Map — is that termiHub is already half-way to both. The shared core crate already defines the ConnectionType, MonitoringProvider, and FileBrowser traits and the network diagnostics; the agent already exposes network.* diagnostics and proxies files and monitoring over JSON-RPC; and the terminal hot path is already a backend-push / UI-render pipeline. The redesign generalises patterns that exist, rather than inventing new ones.

Goals

  • The frontend holds no authoritative state. Every durable fact (connections, sessions, tunnels, servers, workspaces, layout, monitors) lives in a backend store; the UI subscribes to a projection of it.
  • The frontend contains no business logic — no state machines, no reconnect/retry/backoff math, no panel-tree algebra, no validation, no reconciliation. All of it moves to Rust.
  • A single intent → command / state → projection contract replaces the current ad-hoc mix of 206 typed IPC commands + 36 event listeners + a 8.3k-line store.
  • A shared service/tool trait lets the embedded servers, network tools, tunnels, and monitors run on either the desktop host or the remote agent, selected per instance.
  • The migration is strangler-style: the app stays fully working after every phase; no big-bang rewrite; one domain moves at a time behind a stable projection boundary.

Non-Goals

  • Not a UI redesign. The VS Code-inspired look, the design system, and the component tree stay; only where the logic lives changes.
  • Not a rewrite in a different framework. React + Zustand + xterm.js remain; Zustand shrinks to a projection cache.
  • Not the same as remote-client mode (future/remote-client-mode.html), though it is the enabling substrate for it — a truly stateless UI over a transport-agnostic backend is exactly what a browser / iPad client needs. That concept is a downstream consumer, not a prerequisite.
  • Not moving credential secrets or OS-keychain access to the agent (see Open Decisions — the trust boundary is a deliberate exception).

Target: Stateless UI #

The split — what the UI keeps vs. what moves

Stays in the UI (view-local, ephemeral) Moves to the backend (authoritative + logic)
Rendering (JSX → DOM), xterm.js canvas + its scrollback buffer All session/connection/tunnel/server/monitor/workspace state
Raw input capture (keystrokes, mouse, drag gestures) → dispatched as intents All state machines: connect/reconnect/backoff, restore cohorts, transfer queue, tunnel lifecycle, broadcast membership, workflow runs
Focus, hover, scroll position, selection, in-progress unsubmitted text The panel tree & tab model (today's panelTree.ts algebra + workspaceLayout.ts)
Which projection to subscribe to; optimistic echo of an in-flight intent All validation, schema defaults, SSH-config / inventory parsing, ReDoS-safe regex, keybinding resolution
Animation, theming CSS variables (values still authored backend-side) All derivation: filtered/sorted trees, counts, badges, reconciliation of pushed events against prior state

The test for "does this belong in the UI?": if the app were driven by a second client (a browser tab, an automation script) the fact would still have to be true and consistent → it is authoritative → backend. If it evaporates when you close the window and no one else could ever care about it → view-local → UI.

State flow — backend-pushed projections

The UI subscribes to view models — projections the backend computes and pushes. A projection is a serialisable, render-ready snapshot of one screen region (the connection tree, the tab bar for a window, the tunnel list, the Open Connections table). The store (appStore) survives only as a dumb projection cache: it holds the last snapshot the backend sent and notifies React; it computes nothing and decides nothing.

Intent flow — UI dispatches, backend decides

Every user action becomes an intent — a small serialisable message ({ kind, payload }) sent to the backend. The backend validates it, runs the business logic, mutates authoritative state, and the resulting state change flows back as a projection push. The UI never mutates state directly and never branches on business rules; at most it renders an optimistic echo (e.g. a pending spinner) that the next projection confirms or replaces.

Intent flow: the one-way round trip 
sequenceDiagram
    participant U as User
    participant V as UI (stateless)
    participant B as Backend (authoritative)

    U->>V: click "Reconnect" / drag tab / type command
    V->>B: intent { kind: "session.reconnect", id }
    Note over V: optimistic echo only (pending state)
    B->>B: validate + run logic (backoff SM, panel-tree edit, …)
    B->>P: state changed
    P-->>V: projection push (new view model)
    V->>U: re-render from projection

This collapses today's 206 typed commands + 36 event channels into two generic channels — dispatch(intent) and subscribe(region) → viewModel — plus the terminal byte stream (below). The typed command surface does not disappear; it moves behind the intent boundary as internal backend functions.

What happens to the 8.3k-line appStore

It is dismantled, not deleted. Each domain's authoritative half moves to a Rust store + projector; the frontend keeps a thin per-region cache. Concretely:

  • Panel tree / tabs / layout → a Rust LayoutStore (the panelTree.ts 16-function algebra and workspaceLayout.ts port almost verbatim). The UI receives a flat render list of panels + a tab bar per window; drag-drop becomes a layout.moveTab intent.
  • Terminal connect/reconnect → the driveAutoReconnect state machine and reconnectBackoff.ts math move into the session manager (which already owns the real session). The UI renders a status the backend computes.
  • Restore cohorts, transfer-queue reconciliation, broadcast membership, workflow runs → each is a backend state machine emitting a projection; the store's reducers (settleRestoreCohort, reconcileTransferQueue, refreshBroadcastMembership) delete.
  • Promise-resolver fields (password prompt, unlock gating, spawn picker) → replaced by request/response intents with a correlation id; the UI shows a dialog when a projection says "awaiting input", and answers with an intent.

The terminal hot path stays fast (it is already stateless)

Terminal output is the one channel that must not be reshaped into projections. It already works the right way and is left alone: the backend coalesces PTY output (up to 32 KB) and pushes bytes; events.ts's TerminalOutputDispatcher batches via requestAnimationFrame and writes straight into xterm.js's canvas. xterm's scrollback is view-local render state, explicitly allowed. The redesign preserves this byte pipeline as a third dedicated channel alongside intents and projections — it does not route terminal bytes through the projector.

The plugin-frontend runtime — the hard exception

Frontend JS plugins (src/plugins/pluginRuntime.ts, #1998) are the sharpest collision with "no logic in the UI". A frontend plugin is JavaScript injected into the shared WebView context that registers:

  • Protocol parsers — transform(data, sessionId) runs over every chunk of terminal output before xterm. This is arbitrary third-party logic sitting in the hot path, in the frontend.
  • Status-bar widgets — render(): HTMLElement, i.e. plugins that build DOM directly in the main context.

A stateless UI cannot host arbitrary business logic, yet the plugin API's entire value is letting third parties add exactly that on the client. This concept resolves it by declaring the sanctioned client-plugin surface an explicit, sandboxed exception, not by pretending it moves:

  • Protocol parsers should prefer the existing Rust plugin backend (core/src/plugin, the termihub-plugin-api ABI v4) — a Rust parser in the backend output pipeline is both faster and compatible with the stateless model. The frontend parser extension point becomes a fallback for presentation-only transforms.
  • Status-bar widgets remain client-side but move into a sandboxed runtime (Worker / iframe, already flagged as future work in #1998) with a message-passing API — they render into a slot the stateless shell owns, they do not reach into app state.

This is the one place the "all logic in the backend" rule is deliberately bounded, and it must be decided explicitly (see Open Decisions).

Agent-Executed Services & Tools #

Today a service or tool is either "on the desktop" (embedded servers, tunnels, HTTP monitor) or "on the agent" (sessions, network diagnostics) by accident of where its code was written. The target makes location a runtime property: each service or tool is a location-agnostic backend object, hosted by whichever host the user picks.

The abstraction — a Service / Tool trait pair in core

Mirroring the existing ConnectionType pattern, two new trait families live in core and are hosted by both the desktop and the agent:

  • Service — a long-lived, stateful daemon with a lifecycle: start / stop / status / subscribe_events, a settings_schema() and capabilities() exactly like ConnectionType. Implementors: the HTTP/FTP/TFTP embedded servers, SSH tunnels, the HTTP monitor, system monitors. A ServiceRegistry (twin of ConnectionTypeRegistry) registers factories at startup.
  • Tool — a one-shot or streaming invocation with no persistent lifecycle: run(params) → stream<result>. Implementors: ping, traceroute, port scan, DNS lookup, Wake-on-LAN. These already exist as plain functions in core/src/network; the trait just gives them a uniform host + a cancellation token.

Both host processes populate their registry from the same core implementations, gated by cargo features — exactly the mechanism that already lets desktop and agent share backends. The desktop additionally decides reachability: a service on the agent is driven through the same JSON-RPC proxy the sessions already use (RemoteProxy / agent_manager), extended with service.* and tool.* namespaces.

Feasibility, Scope & Risks #

Verdict

Feasible, but a multi-quarter restructure that touches nearly every file — and it must be sequenced, not attempted at once. It is feasible because the hard architectural seams already exist: the shared-core trait model, the JSON-RPC agent proxy, the backend-push terminal pipeline, and mostly-pure logic utils that port cleanly to Rust. It is dangerous because the authoritative state is concentrated in one 8.3k-line store whose reducers are load-bearing across the whole app, and because the backend is the least-tested layer (the pre-release audit flagged exactly this) — moving logic into the least-tested layer without first building test scaffolding would trade UI bugs for silent backend bugs.

Rough scope / effort

Workstream Rough effort
Projection + intent substrate (the two generic channels, projection cache, one pilot domain) 1–2 months
Port each state domain (~20) to a Rust store + projector, deleting store reducers 6–10 months (incremental, parallelisable across domains that don't share files)
Service/Tool trait + registries + agent service.*/tool.* dispatch 1–2 months
Port embedded servers + HTTP monitor into core services; wire network-tool run-location 2–3 months
Agent-hosted tunnels (semantics + impl) 1–2 months, last
Backend test scaffolding (must lead, not trail) ongoing, front-loaded

Order-of-magnitude: ~12–18 months of focused work, spread across many independently-mergeable PRs. No single PR should be large; the value of the strangler approach is that the app ships working the entire time.

Top risks

Risk Why it bites Mitigation
Backend is least-tested Logic moving in lands in the thinnest safety net; regressions become silent (no UI to visibly break). Front-load backend test scaffolding: unit tests for every ported state machine (the JS tests port alongside the logic — appStore.plugins.test.ts etc. are a head start), plus the Python bridge harness asserting projections. A domain does not migrate until its backend tests exist.
Terminal-latency regression If terminal bytes ever get routed through the projector, the 40-terminal hot path dies. Keep the raw byte stream as a dedicated third channel, untouched. Benchmark before/after each phase near a terminal.
Projection chattiness / over-rendering Naive full-snapshot pushes on every keystroke will flood the IPC bridge (already single-threaded, ADR risk). Diff-based projections, per-region channels, coalescing — the same discipline the terminal dispatcher already uses.
Plugin-frontend runtime collision Frontend plugins run arbitrary JS logic in the WebView, in the terminal hot path — the antithesis of a stateless UI. Sanctioned bounded exception: prefer Rust backend parsers; sandbox client widgets (Worker/iframe, #1998). Decide explicitly.
Big-bang temptation The store is so interconnected that a "just rewrite it" push is tempting and would strand the app half-migrated. Hard rule: one domain per phase behind a stable projection boundary; never two colliding domains in flight (mirrors the coordinator's no-colliding-files rule).
Agent-hosted tunnel semantics A tunnel's "local" and "remote" ends are relative to a host; moving hosts silently changes meaning. Treat tunnels last; specify endpoint semantics in a dedicated sub-concept before coding.
Offline / desktop-only capabilities Credentials/keychain, spawn rendezvous, local file watch cannot and should not move to an agent. Explicitly scope them as desktop-host services; the run-location selector simply omits "agent" for them.

Test scaffolding needed first

  • Rust unit-test coverage for each state machine before it moves (backoff, restore cohort, transfer queue, panel-tree algebra — the latter has a clean pure-function shape ideal for property tests).
  • A projection-assertion harness in the Python bridge: drive an intent, assert the pushed view model. This becomes the contract test for the stateless boundary.
  • Integration coverage for agent-hosted services (the service.* path) — noting per-PR CI does not run integration tests, so these need local container runs.

Phased Migration #

Strangler-style. Each phase is independently shippable and leaves the app fully working. Phases 0–2 build the substrate; 3+ move domains; the service/tool track (S1–S3) can run in parallel once the trait lands.

Phase Deliverable Keeps app working by…
0 · Test scaffolding Backend unit-test harness + projection-assertion bridge tests. Port the pure logic utils (panelTree, reconnectBackoff, restoreMode, schemaDefaults) to Rust with their tests, dual-run against the TS versions. Nothing changes for the user; Rust ports run behind the existing TS.
1 · Substrate The two generic channels — dispatch(intent) and subscribe(region) — plus a dumb projection-cache adapter in the store. Terminal byte stream stays as-is. Old typed commands still work; the new channels sit beside them.
2 · Pilot domain Migrate one self-contained domain end-to-end (candidate: SSH tunnels — already sliced, already a slice file, clear lifecycle) to Rust store + projector; delete its store reducers. Only the tunnel slice changes; everything else untouched. Proves the pattern.
3 · Layout & tabs Move the panel tree + tab model to a Rust LayoutStore (biggest single win — the panelTree.ts/workspaceLayout.ts ports from phase 0 activate). UI renders a flat panel/tab render-list. Drag-drop becomes an intent; visuals identical.
4 · Session lifecycle Connect/reconnect/restore/broadcast/workflow state machines move server-side; the UI renders projected status. The real sessions already live backend-side; only the state machine relocates.
5 · The long tail Remaining domains (connections tree, file browsers, transfers, agents, monitors, settings) one at a time. Each is one PR; the store shrinks monotonically.
S1 · Service/Tool trait Add Service/Tool traits + registries in core; agent service.*/tool.* dispatch; desktop run-location resolver. Existing desktop services keep working through the new trait locally.
S2 · Tools + servers to agent Wire network-tool run-location (agent already exposes network.*); lift embedded servers + HTTP monitor into core services; add the run-location selector UI. Default run-location stays "This computer" until the user opts in.
S3 · Tunnels to agent Agent-hosted tunnels, after the endpoint-semantics sub-concept. Desktop tunnels unchanged; agent hosting is additive.

Open Design Decisions #

The maintainer must settle these before the target design is finalised:

  1. Projection granularity & transport. Per-region diff channels over Tauri events? A single reactive document (CRDT-like)? Something like a query/subscription layer? This is the load-bearing choice; everything else follows from it.
  2. How stateless is "stateless"? Is a small amount of derived, non-authoritative caching allowed in the UI for render performance (e.g. memoised filtered lists), or is the rule absolute (every derived value comes from the backend)?
  3. Frontend plugin API future. Do protocol parsers move to the Rust plugin backend (breaking the current JS extension point), stay as a bounded client-side exception, or both (Rust preferred, JS fallback)? This decides the plugin ecosystem's shape.
  4. Desktop-only boundary. Confirm the permanent desktop-host set: credentials/keychain, spawn rendezvous, local file watch, OS-window management. The run-location selector omits "agent" for these.
  5. Agent-hosted tunnel endpoint semantics. When a tunnel runs on an agent, what do "local" and "remote" mean, and how is that surfaced without confusing users?
  6. Multi-client consistency. A stateless UI over an authoritative backend invites multiple clients (remote-client mode). Is that in-scope now (shapes the projection design) or explicitly deferred (single-client projections first)?
  7. Migration appetite vs. feature work. A 12–18-month restructure competes with feature delivery. Is this a background strangler (slow, safe) or a funded push?
