Overview & the three pillars #

termiHub already ships a real design-token system (src/styles/variables.css, ~125 tokens: a 4-8-12-16-24 spacing scale, a radius scale, semantic status colors, connection-state colors, spring transitions) and a clean theme engine with four themes. Scrollbars were recently unified into one auto-hide style. The foundation is strong — the problem is adoption, not architecture.

There is no shared component layer: every dialog re-implements its own button, every form rolls its own input, and most non-terminal actions give the user no feedback at all. This concept fixes the shared layer once — so the whole app inherits the improvement — and encodes the rules into CLAUDE.md + a ui-design subagent so future work can't quietly regress.

The three pillars

Pillar Concept Fixes
Clean One shared primitive layer (Button, Input, Field, Select, Modal, Toggle, Checkbox, NumberInput, Progress, Tooltip, Toast) + strict token discipline. No component invents its own colors, radii, shadows, or scrollbars. 14× button dup, 33 dialog one-offs, light-theme text bug
Reactive A global feedback system: a Toast hub + an async-action lifecycle (idle → pending → success/error) baked into the button. silent CRUD (save/delete/folders/tunnels/unlock/deploy)
Modern One motion language, one focus ring, one scrollbar, a tightened spacing rhythm — respecting prefers-reduced-motion. snap transitions, the last scrollbar straggler

Goals

  • A shared, token-driven primitive layer in src/components/ui/ that every screen composes from.
  • Immediate, honest feedback for every mutating/async action.
  • One motion language and one scrollbar; consistency enforced by tokens + a subagent + CLAUDE.md.

Non-Goals

  • No screen-by-screen visual redesign — the layout is good. This is a systemic change to the shared layer.
  • No new custom UI machinery where an installed library already fits (see Implementation Details).

General Handling #

The core rule: no mutating or async user action may resolve silently. It must (a) show an immediate pending state, and (b) confirm success or surface a recoverable error. Which mechanism to use:

Situation Mechanism Why
Button-initiated mutation (Save, Delete, Apply) Async Button state + error toast Feedback at the point of action; no eye travel
Background / long-running (agent deploy, tunnel start, import) Loading toast → resolves in place User keeps working; progress stays visible
Field-level problem (invalid port, bad key path) Inline Field error Anchored to the offending input
Blocking connection lifecycle (SSH/serial connect) Connection overlay Full-surface state with cancel + contextual hints
Success confirmation (saved, copied, deleted) Success toast (auto-dismiss) Acknowledge without interrupting

Consistency rules (always on)

  • One scrollbar. Scrollbars are styled globally (auto-hide, global.css); components never re-style them. Fixes the one straggler (TabGroupChips.css forcing scrollbar-width: none).
  • One motion language. Dialogs and toasts share one enter (fade + 8px rise) and exit, using the --transition-* tokens; all motion wrapped in @media (prefers-reduced-motion: reduce).
  • Tokens only. No raw hex, no rgba(0,0,0,…) overlays, no pixel radii — add a token if one is missing.

Preliminary Implementation Details #

Aligned to the current architecture (React 18 + TS, Zustand, component-local CSS, Radix for overlays). The design-system work is largely wrapping libraries already in package.json, not building new machinery — per the repo's "Prefer Libraries Over Custom Code" standard.

Build on installed libraries

Need Already installed Verdict
Modal / Select / Tabs / menus @radix-ui/react-dialog, -select, -tabs, -dropdown-menu, -context-menu wrap, don't build
Form state + validation react-hook-form + @hookform/resolvers + zod wire Field/DynamicForm; don't reinvent
Long lists (tree, 2k-line LogViewer) @tanstack/react-virtual headless windowing; drives the FileBrowser list (#1514)
Color / charts / icons react-colorful · uplot · lucide-react in use
Toast / notifications (the one gap) none add sonner (recommended) — or @radix-ui/react-toast as the zero-new-vendor fallback

sonner is recommended because its promise/loading toast that resolves in place maps 1:1 onto the agent-deploy pattern, and its imperative toast.success() API means no store to build. Two optional accessibility add-ons: @radix-ui/react-tooltip (replace bare title attrs) and @radix-ui/react-switch (the Toggle). Net new dependencies: one required, at most two optional.
