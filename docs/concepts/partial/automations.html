0. Summary #

  • termiHub has two automation types today. Macros type recorded or hand-written input into a terminal and are always visible. Workflows are typed step lists with triggers, parameters, branching and error policies, and sit behind the experimental flag. Each has its own sidebar, editor, history file, palette entry kind, IPC set and import format. Schedules can run either one.
  • A macro is a workflow with one kind of step and no trigger. The gap is mostly in how the two are presented. The engines differ on only three points: per-step recorded timing, lock-step multi-terminal delivery, and raw bytes with no added newline.
  • Proposal: one type called Automation. A macro becomes an automation with one Type keys step that holds the recorded chunks byte for byte. Record becomes an editor and toolbar action that produces such a step. Triggers are optional, and none means "run it yourself". The product has one sidebar, one editor, one history, one palette entry kind and one schedule action.
  • Migration copies macros.json and workflows.json into a new automations.json. Ids are kept, so schedules, history, palette keys and run-macro steps still resolve. The old files are left in place as a frozen snapshot that an older build can still read. A reconcile pass pulls in changes an older build makes to them.
  • 12 slices. Each one can merge on its own and each adds a product-run grade in a new file.

1.3 Execution

  • Both inject input through one seam: sendInputToTerminal → send_input, registered via registerTerminalInputInjector in macroPlayback.ts. Both therefore work the same on local, SSH, serial, telnet and agent-hosted sessions. Neither has any agent-side code. The agent only sees terminal input. run-local-process always runs on the desktop, behind a master opt-in, a confirmation on first run and a machine-local allowlist (LocalProcessAuthDialog.tsx, workflowRunner.ts around line 270). Its output goes to the inline WorkflowRunOutput panel.
  • Multiple terminals, macros. PROD-042, src/store/slices/macroFanout.ts. Delivery is lock-step: each step reaches every live target before the next one. A target that drops is removed and the run continues. Target choices are the active terminal, the live broadcast set, all terminals, the current panel or a saved broadcast group, followed by a confirmation that names every terminal (MacroPlaybackDialog.tsx, useMacroPlaybackTargets.ts). Receiving tabs get a violet badge (#3446).
  • Multiple terminals, workflows. "Run on…" (WorkflowRunTargetsDialog.tsx, #3418) starts independent concurrent runs, at most 8 at once (WORKFLOW_FANOUT_CONCURRENCY). A "Run in parallel" toggle switches to sequential. Each terminal gets its own Stop button and a "Stop all" covers them. Parameters are asked once. The palette offers "Run workflow on broadcast group" (#3430).
  • A workflow's run-macro step replays a macro with real-time timing (src/store/slices/workflowRunOnTarget.ts:239).
  • Concurrency limits: one macro playback per window. Workflows allow several runs. On-output-match never fires while another workflow is running. A schedule never fires while another run or playback is active in that window (src/store/scheduledRuns.ts).

1.4 Authoring and recording

  • Recording (#1674) works only for macros. The terminal toolbar's "…" menu has Record/Stop with an indicator (TerminalToolbarMore.tsx), and macrosSlice captures each input chunk with the delay since the previous one. Stopping opens MacroRecordSaveDialog (name, description, tags). Palette and keybinding action: toggle-macro-recording, unbound by default.
  • Writing a macro by hand (#3440): MacroEditorDialog.tsx. Each step is a text field in escape notation (\r, \n, \t, \e, \xHH, \\) with an "add Enter" button and a per-step delay. Steps can be reordered and deleted, and untouched steps are saved back byte for byte.
  • Workflow editor: WorkflowEditorDialog.tsx. It covers name, description and tags; a typed "Add step…" menu (workflowStepMeta.tsx: Send command, Run script, Run macro, Wait, Run local process, Condition, Loop, Wait for output); per-step editors (WorkflowStepRow.tsx, 772 lines); error handling (WorkflowStepErrorHandlingEditor.tsx); parameters (WorkflowParametersEditor.tsx); and triggers as on/off chips (WorkflowTriggersEditor.tsx).
  • Promote a macro: the Workflows "New" menu turns a macro into a one-step workflow with a run-macro step (WorkflowSidebar.tsx:124, 377–384). This is the code's own admission that the two overlap.

1.8 Overlap and what is unique

  • Same in both: id, name, description and tags; a step list; run into a terminal through one injector; a history of 200 metadata-only records; import and export through one envelope helper; a palette entry; schedulable; backed up; row actions (Edit, Schedule, Duplicate, Export, Delete).
  • Only macros: recording; raw byte chunks without an added newline; per-chunk recorded delays and a timing mode chosen at play time; lock-step fan-out with a confirmation that names every terminal, plus targets for the current panel and all terminals; the violet tab badge; a 90-day history limit.
  • Only workflows: typed steps; control flow; wait-for-output; local processes; parameters; retry and continue; five trigger kinds plus arm/disarm; concurrent "Run on…"; the run output panel; a backend run projection; connection id re-pointing; the Schedules section in the sidebar.

2. Usability today #

  1. Two names for one idea. A user who wants "type this into the terminal when I connect" has to know that macros cannot be triggered (audit PROD-041 "macros-no-triggers"). Then they have to find an experimental view, then "promote" the macro. Nothing in the Macros sidebar points there.
  2. Two sidebars and two homes for schedules. Schedules are listed in the Workflows sidebar (experimental) and in Settings → Schedules. With experimental off, a scheduled macro can be created from its row but never seen beside its macro.
  3. Two histories with different words and rules. Macros say error and workflows say failed. Macros record one entry per playback with a list of tabs, workflows one per terminal. Macro history expires after 90 days and workflow history never does. A workflow that runs a macro writes into both histories.
  4. Two multi-terminal pickers. "Play on N terminals…" (with a confirmation step, panel targets and all-terminal targets) and "Run on…" (with parallel and sequential modes) do the same job with different options, labels and confirmation rules.
  5. Timing is hidden and inconsistent. A macro's timing is picked each time in the terminal picker. The sidebar's Play and the palette always use real-time, and so does a workflow's run-macro step. The choice is never saved, so the same macro behaves differently depending on where it is started.
  6. The "Manual" trigger chip does nothing. Turning it off does not stop palette, sidebar or button runs (workflowsSlice.ts:414 defaults to manual, and nothing checks for the chip). It looks like a setting and has no effect.
  7. Experimental leaks. Workflow hotkeys and palette entries are dispatched without checking the experimental flag (useKeyboardShortcuts.ts:71, CommandPalette.tsx:203). A user who turns experimental off still has workflows running, but no view to manage them.
  8. Duplicate concepts in the editor. "Send command" versus a macro step. "Run macro" versus just putting the steps in. "Run script" versus a multi-line send.
  9. Nothing to steer the first choice. A new user who opens Macros and wants a conditional or a trigger has no path forward. A new user who opens Workflows and wants to record keystrokes has no Record button.

3. The merged design #

3.1 Name

  • Recommended: "Automations". One automation, run an automation, record an automation. The word covers keystroke playback and triggered multi-step jobs without suggesting either "toy" or "heavyweight". The product run already calls this phase "automations" (test_product_run_automations.py). It reads in sentence case and is not taken by another feature.
  • Alternative: keep "Macros" as the single name, as Keyboard Maestro does, where a macro can have triggers and conditions. The upside is that the always-visible name stays the same. The downside is that "macro" suggests recorded keystrokes only, and on-disconnect jobs with retries are a stretch under that name.
  • In the UI: the sidebar is "Automations". A "Type keys" step uses the word "recorded" for recorded input. The word "macro" survives only as a search alias, so existing muscle memory ("Run macro: …") still finds things.

3.2 Model

Automation {
  id, name, description?, tags[],               // unchanged fields
  steps: Step[],
  triggers: Trigger[],                          // [] = run it yourself; "manual" removed
  parameters: Parameter[],                      // omitted when empty
  triggersEnabled: bool,                        // armed switch, omitted when true
  createdAt, updatedAt,
  legacy?: { from: "macro" | "workflow", version: n }   // provenance, for reconcile/export
}

Step = everything WorkflowStep has today, plus:
  type-keys {
    chunks: [{ data, delayMs }],                // = MacroStep[], byte-identical
    timing?: "recorded" | "fixed" | "instant",  // default "recorded"; fixedDelayMs? for "fixed"
    recorded?: bool                             // true when produced by recording
  }
  run-automation { automationId }               // replaces run-macro; run-macro stays readable
  • **A macro is {steps: [type-keys{chunks: macro.steps}], triggers: []}.** One step and not N. A 40-keystroke recording is one row in the editor, "Type ls -la⏎, 12 keys, recorded". It expands into the chunk list that MacroEditorDialog already edits today.
  • type-keys adds no newline and does not substitute ${param}. That keeps recorded bytes exact, so a recorded ${ stays literal. For typed text with parameters, send-command ("Run command") stays the friendly kind.
  • Timing moves from a choice made at play time to a property of the step. The default is "recorded", which is what the palette, the sidebar and run-macro already use, so behavior does not change for those entry points.
  • Multiple terminals: a single engine, workflowRunner. A type-keys step runs the existing runMacroPlayback scheduler against each target's injector. Runs on several terminals use the workflow model: independent, at most 8 at once, with a parallel toggle. Lock-step delivery goes away (see 5.R3). For pure typing, the two look the same to the user.

3.5 Recording

Terminal "…" → Record automation         ─▶  tab shows ● Recording · [Stop] [Cancel]
Stop ─▶ ┌ Save recording ────────────────────────────────┐

        │ ◉ New automation   Name [            ]         │

Editor "● Record steps" ─▶ the editor collapses to a bar above the target terminal
        ("Recording into 'Deploy prep' · Stop"); Stop inserts a Type keys step
        at the selected position and reopens the editor, with the draft kept.
  • Recording still captures what is typed into the active terminal and nothing else. The dismissal fix from #5201 (dismissing the dialog keeps the recording) carries over.
  • What is recorded: every byte the user's keys, pastes and dropped paths send to the recorded terminal, with the time between them; not what another terminal gets, and not what the terminal itself answers (focus reports, query replies).
  • Passwords: what is typed at a password prompt without an echo is marked while it is recorded, left out when the recording is saved, and stored only when the user asks for that (an automation is stored unencrypted). It is recognised by the text before the cursor, so a prompt that says neither password, passphrase, PIN nor the like is not. Credential dialogs are not terminal input and are never recorded.
  • Lifecycle: a dropped connection pauses the recording and it goes on after the reconnect; the tab moving to another panel changes nothing; the session ending, the tab being closed or moved to another window stops it and asks; closing the window or quitting asks first. A crash or a reload loses it.

3.8 What stays the same

Agents need no protocol change, because the injector is the same. The safety rules for schedules stay as they are: confirmation on first enable, disabled again when the action or targets change, never prompts, connectIfNeeded. The local-process opt-in and allowlist stay. So do the output-trigger limits and connection id re-pointing.

  • Ids are kept as they are. macro-<ulid> and workflow-<ulid> cannot collide by construction. The converter still checks for collisions, because imported or older ids can be arbitrary. The rules are deterministic, so a rerun of the migration (and the reconcile pass) always produces the same ids:
    • Workflows claim their ids first, then macros, each in file order. The first entry with an id keeps it.
    • A later entry with a taken id gets automation-<old id>, or automation-<old id>-2, -3 and so on when that is taken too. A new id never equals any id in either legacy file, so re-iding one entry cannot push another one off its id.
    • Every reference is rewritten in the same pass: run-macro steps now, schedule actions and history from the returned id map (slices 2 and 10).
    • A run-macro step that names no macro at all, but whose id now belongs to a converted workflow, is pointed at missing-macro-<id>. It keeps failing as it does today instead of silently running the workflow.
  • Because ids are kept, palette keys, the schedule-to-run links and the history filter chip all keep resolving.

4.2 Procedure (backend, at boot, before any manager loads)

  1. If automations.json exists, skip to step 5. Otherwise read both legacy stores through their existing VersionedStore gates. A newer or corrupt file is salvaged or refused as it is today.
  2. Convert both, write automations.json atomically, and record a provenance block: migratedFrom: {"macros.json": {version, sha256}, "workflows.json": {version, sha256}}.
  3. Copy each legacy file to <name>.pre-automations.bak, once.
  4. Leave the legacy files where they are. The new build never writes them again.
  5. Reconcile (the round trip). On every boot, if a legacy file's hash differs from the provenance block, an older build has edited it. Merge entries by id: new ids are added, and for changed ids the newer updatedAt wins. When both sides changed, keep both and name the copy "<name> (from older version)". Then update the hashes and report "Automations: merged N changes made by an older termiHub version" in the recovery warnings.
  6. Migrate schedules v2 → v3 under the same lock. The PER-004 gate already stops a v2 build from overwriting a v3 file.

4.3 What older builds see

  • A build from before the merge ignores automations.json and automation-runs.json. It reads the frozen macros.json and workflows.json and sees the library as it was when the migration ran. Anything it edits there is merged back on the next upgrade (4.2 step 5).
  • Automations created after the merge are invisible to older builds. This loses nothing, because they live in automations.json.
  • schedules.json v3 is refused for overwrite by a v2 build, as already happens with any newer version. A v2 build therefore shows its own schedules as unreadable instead of discarding them. This is the accepted behavior for every versioned store.
  • A backup from a new build restored into an older build: the older build skips the unknown automations section ("not known to this version", backup/restore.rs:319). During the transition the new build also includes the frozen legacy files as macros and workflows sections, so an older build still restores something useful.
  • Reversibility: deleting automations.json (or restoring .pre-automations.bak) puts things back exactly as they were before. A later explicit "Export as legacy macros and workflows…" is possible but not planned, since everything is pre-v0.1.0.

Risky parts

  • R1: migration correctness. This is user-authored data. The safeguards are golden fixtures from real files, byte-identical type-keys chunks, provenance hashes, .bak, and never writing the legacy files. Slice 2 must include an "edited by an older build" test.
  • R2: reconcile conflicts. "Keep both" is safe but can produce duplicates. Do not try to merge step lists.
  • R3: losing lock-step fan-out. Today a macro on 5 terminals advances them in lock-step. Per-target runs can drift by a few milliseconds, and a slow target no longer holds the others back. That is a behavior change, but no test or grade depends on lock-step. If it matters, a hidden lockStep engine mode for automations that contain only type-keys steps can be added later without changing the model.
  • R4: the experimental boundary. Today's always-visible Macros view becomes a view that contains formerly experimental features. Question 2 decides what stays gated. Slice 11 closes the existing leaks (2.7).
  • R5: the 90-day limit now applies to former workflow history. Old workflow runs older than 90 days are dropped at migration. Either log it or exempt migrated records; the recommendation is to apply the limit, since it is metadata only.
  • R6: the projection. Macro playback state moves into the workflow-run@<clientId> region, which can be renamed later. The region becomes the single source for "running" markers. Watch the stateless-UI faithful-mirror tests.

6. Open questions for the maintainer #

  1. Name. Recommended: "Automations". It covers both typing and triggered jobs, and the product run already uses it. The alternative is to keep "Macros" as the single name, so the always-visible name stays the same.
  2. Experimental scope after the merge. Recommended: the merged Automations view is always visible, with typing, commands, waits, conditions, loops, parameters, triggers and schedules all graduated. Only the Run local process step stays behind "Allow experimental features", because it is security-sensitive. The alternative is to keep triggers experimental too.
  3. Timing of typed input. Recommended: make typing speed (as recorded, fixed, instant) a saved property of each Type keys step, set in the editor, so an automation behaves the same from every entry point. The run picker then drops the per-run timing choice that the terminal's Play dialog has today. The alternative is to keep a per-run override under "More".
  4. Where schedules live. Recommended: keep schedules as their own entries (they carry targets, the confirmation and history), listed in the Automations sidebar and in Settings → Schedules, and also shown as "On a schedule" links in the editor's "When it runs" section. The alternative is to make a schedule a kind of trigger stored inside the automation, which is more uniform but would mean rewriting the schedule safety model.

Maintainer decisions (2026-11-23) #

  1. Name: Automations. The palette keeps "Run macro:" / "Run workflow:" as search aliases.
  2. Experimental: only the Run local process step stays behind the experimental switch. Everything else graduates.
  3. Typing speed: saved per Type keys step. The play dialog no longer asks.
  4. Schedules: stay separate entries, listed in the sidebar and Settings, and linked from "When it runs".
